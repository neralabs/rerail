Decision report · Rerail pull request #974

A hook no longer waits for the disk at each daemon commit

1. The one question

May Rerail's store commit with synchronous = NORMAL, so hooks no longer wait for the disk at each commit, with three repairs for a power cut?

  1. After a power cut or a system crash, the last seconds of records may go. Changes the intent.

We recommend: approve it: a power cut or an operating system crash can take the last seconds of records, nothing is lost when only Rerail stops, and the next start and open repair the records it leaves.

5. The changes

Each line opens its card.

ACommits without waiting for the diskMedium riskBusy disk, one commit: 46 to 55 ms median on main, 0.1 ms here.
Problem
Each commit of the store waited for the disk to confirm it, inside the hook that made it: one before an Edit, three after it, while another program kept the disk busy.
Who meets it
Every session, at every tool call: Claude Code waits for the hook before and after each one. Source: the measure behind #971 and the runs here.
What it does
prepareWriter opens every writer of the store with synchronous = NORMAL, the write-ahead log kept: a commit returns once it is in the log, which a checkpoint syncs when it copies it into the file. Its comment says what that keeps and what it gives up.
Risk
Medium. The last seconds of records can go in a power cut or a system crash; SQLite keeps the file whole and the earliest commits, and nothing goes when only Rerail stops.
Check
Is the loss of the last seconds of records, after a power cut or a system crash, a price the store may pay? docs/reference.md and the release note say it to a person upgrading. Every writer, the daemon's, the hook process's and the CLI's, opens through prepareWriter.
BRepairs for what a loss leavesMedium riskAfter a cut: no check left running, no event left unsent, the lost events named.
Problem
After a lost tail of commits, a gone daemon's check read as running for good, events after the loss took numbers a remote held and were never sent, and the history missed events without a word.
Who meets it
Every person after a power cut or a system crash; the check left running also after a kill or a machine restart. Source: the cases here, in the state SQLite's recovery leaves.
What it does
The next start closes the gone daemon's running checks as interrupted. A store's first session open moves its counter past every number a remote may hold, which the outbox writes before each batch goes. A session's next open writes one events-lost record from its ledger, and a session whose row went starts at its ledger's first event.
Risk
Medium. Each repair decides by a fact: the owner row's writer, a remote's cursor, a row present or not. A wrong fact would close a live check or mark a reset history as lost; cases hold both.
Check
In endSessionsOfEndedOwners, can a live daemon's check be closed? In keepEventNumbersPastRemotes, can the counter move back? In lostEvents, can a reset's deleted history read as lost? recordLostEvents writes one record per stretch, at its last event's time.

6. The decisions

Which way removes a hook's wait for the disk at each commit?

We chose synchronous = NORMAL with the write-ahead log: of five ways measured or sized, it alone removed the wait in every pairing.

Would change our mind: A maintainer who wants every answered hook on disk whatever it costs: then the store's writes on a thread of their own, FULL kept.

8. What is not covered

  • The slowest hooks remain: a commit that runs a checkpoint, about one in 140, still syncs the log and the file on the daemon's thread, 23 to 311 ms beside a busy disk.
  • A session that never opens again keeps no record of its lost events: the record is written at the session's next open.
  • macOS never ran.
Three smaller gaps, two limits that stay
  • A steer receipt the loss takes leaves the footer, the feedback and the evidence one steer short: the record itself is what went.
  • A session the gone daemon left open ends at the idle limit after its newest event the loss left, earlier by the span of the lost commits.
  • A session whose every record the loss took gets its start time back from its ledger, but reports no loss: a reset leaves the same state.

Limits that stay.

  • The outbox's record of each batch waits for the disk on the daemon's timer, once per batch. If a loss takes the cursor's last move, the remote receives events it holds again, the same records under the same ids.
  • rerail status says nothing was recorded since a hook failure later than the newest event the loss left, as at main, until the next event is recorded.
