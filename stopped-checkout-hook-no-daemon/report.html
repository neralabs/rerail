Decision report · Rerail pull request #674

A stopped checkout's hook answers without waiting for a busy daemon

1. The one question

May a hook repeat the daemon's last answer of stopped for its folder, for up to 30 minutes, when the daemon is 75 ms late?

  1. A stopped checkout's hook repeats a late daemon's last answer. Changes the intent.
  2. The reference drops "never contact the daemon". Changes the intent.

We recommend: answer #670 first, then read "What is not covered": it names the states where a hook repeats stopped for up to 30 minutes while the daemon reads started.

5. The changes

Each line opens its card.

AAsk first, repeat after a graceMedium riskHook beside a busy daemon: 1,548 to 1,806 ms at main, 86 to 196 ms here (Linux x64).
Problem
In a checkout where Rerail is stopped, every Claude Code, Codex and Cursor hook asks the daemon whether Rerail runs there and waits up to 2 s. A daemon busy with other checkouts holds each one, for an answer of {}.
Who meets it
A person who stopped Rerail in some checkouts while sessions in others keep the daemon busy: every hook there. How many people work this way is not known. #670 reports one laptop with about 40 such sessions.
What it does
hookRerailStarted asks the daemon first. daemonAnswer finds the start mark (markBeforeAsking), asks through the hook's HookAsk, and waits the grace out (settlesWithin). An answer in time is kept (keptAnswer). Past the grace, stoppedEndingRequest asks knownStopped whether the last answer may be repeated; if so, the hook answers stopped, marks its request (abandoned) and ends it. Elsewhere it waits.
Risk
Medium. This check decides whether a hook does anything, for three coding agents. By itself it only repeats stopped or throws on its own fault, once the daemon is late or a check of the folder waits there.
Check
Is stopped the only answer daemonAnswer gives by itself? When the check throws anything but SQLite's error, stoppedEndingRequest ends the request and the hook answers {} with a line on stderr, in a started checkout too; at main it waits for the daemon there. The mark is found before the ask, so a start that commits while the daemon answers leaves nothing to repeat. A hook that does not ask (unasked) answers stopped only where knownStopped held.
BThe kept answer and its checksMedium risk30 minutes of ordinary running: 60 of 60 later hooks repeated, 163.3 ms against main's 533.7 (Linux x64).
Problem
A hook cannot place a folder as Git does from the disk alone. Earlier heads of this branch decided stopped from the folders and the database, and each differed from the daemon in some state.
Who meets it
Every hook in a stopped checkout beside a late daemon takes the kept answer. A wrong stopped leaves a started checkout unrecorded and unchecked for up to 30 minutes. Source: our reading of the code.
What it does
keepStartAnswer writes the answer of stopped whole, per folder, with file ids, clone id and start mark. repeatsStoppedAnswer repeats it only while stillHolds: under 30 minutes old, the same folder, top and .git, clone id (cloneIdAt) and database files (sameDatabaseFiles), and a database that reads stopped (stillStopped). A starting daemon makes the folder (makeAnswersFolder) and removes earlier answers (removeEarlierAnswers).
Risk
Medium. A wrong stopped leaves a started checkout unchecked. Each check can only turn a kept stopped into not known, and the hook then waits as on main. Nothing is read or written through a link.
Check
Does stillHolds miss anything the daemon reads again on every answer (lookupAt)? cloneIdAt finds the clone id file as Git does, from .git, a gitdir: line and commondir, never through a link or on a server. smallFileText opens without waiting, so a named pipe reads as no answer. On Linux an answer is kept only where the daemon holds the database's three files open (daemonHolds). Name a state the tests lack and it gets a test.
CThe start markMedium riskA database copy written in place after a start: no event sent without the mark, every event here.
Problem
The daemon answers from what its connection read. An older copy of the database written over the live file, after a start the daemon read, leaves the file saying stopped while the daemon answers started. Nothing in the file tells.
Who meets it
Anyone who restores or copies rerail.sqlite in place while the daemon runs, after a start of Rerail. How often that happens is not known. Without the mark, hooks there sent no event for up to 30 minutes.
What it does
renewStartMark renames a new file over stopped-answers/start-mark in one try without waiting, only where a daemon made that folder. Refused, it writes start-mark-stuck and tries again for 2 s. Eight writers call it after their commit. startMarkFound gives its device, file id and times. startMarkHolds compares them and refuses beside a stuck mark or a folder that takes no file.
Risk
Medium. Every start, stop and move of a checkout now calls it, the daemon's among them. A failure is never the writer's: its change has committed. A mark that cannot be renewed makes hooks wait, as on main.
Check
Does every writer that can turn an answer from stopped renew after its commit, never inside the transaction? A test of six writers checks it through a proxy of the connection. A renewal that returns with no mark and no stuck mark leaves kept answers holding: renewStartMark returns so at a link in place of the folder, and where the folder refuses both files. On Windows access reads no folder permissions.
DThe check's open of the databaseMedium riskWindows 11, a byte-range lock on the database: 1,527 to 1,579 ms at 2a88553c5, within 16 ms of main here.
Problem
The hook's check reads the database beside a running daemon. An ordinary open would run schema steps, wait up to 5 s on a lock, wait on a named pipe, or follow a link to another file.
Who meets it
Every repeat opens the database once. A wait there would hold a hook that main answers after the daemon's delay alone. Source: our runs with a held lock, a pipe and a link at each name.
What it does
openRerailDatabaseAsIs takes besideDaemon. With it, wholeNow refuses a missing -wal or -shm and any of the three files that is not a plain file, and on Windows reads the first page and the WAL's header first (readsNowOnWindows). openReadOnlyAtOnce then connects with a busy timeout of 0 and runs openChecked's read-only steps. connectSqlite gains that timeout as a parameter.
Risk
Medium. src/engine/storage/ is a high-risk path. No schema, migration or stored data changes, and the defaults leave every other caller as on main. A refusal only sends the hook back to the daemon.
Check
Does openChecked stay untouched, and does any caller but the hook's check pass besideDaemon? wholeNow closes no descriptor of a database file on POSIX, where that would drop SQLite's locks in the process; it opens the files itself only on Windows. A lock past the first page still meets SQLite's own retry, about 1.4 s.
EMarks of given-up start checksMedium riskAfter a killed hook, a started checkout's hook kept 0 of 4 events at 4662bd526, all here (Linux x64).
Problem
A hook that repeats stopped ends its request, which stays in a busy daemon's queue and is served though nobody waits. On Linux the daemon admits one connection per turn, so a burst queues ahead of every other checkout's hooks.
Who meets it
Sessions in started checkouts beside a busy daemon, once stopped-checkout hooks gave up. At 667ab68a3, before the marks, 8 such hooks made a started checkout's next hook give up at 12 s and lose its 4 events (Linux x64).
What it does
HookAsk.beforeAsking makes the hook's pending mark, <name>.<hook>.asking, or answers that a check of the folder waits (.waiting). abandoned renames it to .waiting once sent said the request reached the OS on a new connection; a sent check with no mark is never ended (mayEnd). ServedAsks.served removes the folder's marks as the daemon serves a start check there.
Risk
Medium. A mark that outlives its request lets the hooks of its folder skip asking. They then repeat the kept answer only while it holds, so a mark alone never reads a started checkout as stopped.
Check
Can .waiting exist with no request of the folder queued at the daemon? abandoned renames only after sent, which Node's finish gives for a new connection; served removes pending marks before .waiting, so a rename after it finds nothing. An ask its hook ended (abandoned, done) marks and sends nothing. Is servingStartCheck right to count only a GET /api/presentation with repository and no sessionId? This change's lines in daemon.ts are 39 of 50, and in session-presentation.ts 40 of 73.
FOne kept connection per processMedium riskA read that gives up leaves the daemon two connections at main, one here (a test on both systems).
Problem
Node's bundled fetch opens a second connection when a request gives up, and sends nothing on it. A busy daemon admits each empty connection in a turn of its loop, ahead of later hooks' requests.
Who meets it
Every hook and command that gives up waiting on a busy http: daemon. After a burst of 24, the first hook at 4662bd526 took 2,068 to 2,144 ms, past the 2 s read limit (Linux x64).
What it does
daemonFetch sends requests to an http: daemon through agentFetch over Node's http client and one keep-alive agent per process (KEPT_CONNECTIONS), and the pinned https client through the same function. sendOnce tells sent at Node's finish, only on a new connection. A GET or HEAD whose kept connection closed before any answer is sent once more; a POST never.
Risk
Medium. Every client of an http: daemon sends through it. A request the daemon takes twice would be the harm: only a GET or HEAD is sent again, and only where its kept connection closed before any answer.
Check
Does anything that reads fetch's behaviour differ: bodies (a string or bytes only), headers that repeat, statuses with no body, a signal's own reason on abort? Is 4 s (KEPT_CONNECTION_MS) under the daemon's keep-alive of 5 s? Node unrefs a kept connection, so it holds no process open. This commit, a88b29ed6, is also a change of its own, not open yet; this branch adds sent to it. Of daemon-control.ts's 86 lines, 61 are this change's and 25 the stop signal's.
GThe hook ends its requestLow riskA suspended daemon: 2,134 ms per hook at main, 199 ms here (Linux x64).
Problem
Node keeps a process alive while a socket or a pipe is open. A hook that answered first would still exit only when the daemon answered or the read's 2 s limit ended its request.
Who meets it
Every hook that repeats stopped under change A. Without this change it would have its answer early and its process would end no sooner. Source: our reading of Node, and the mutation that leaves the request open.
What it does
readStartAnswer is new: the daemon's answer with the folder, the checkout and the daemon it rests on. Low. Each new parameter is optional and only the hook's start check passes one. The status line, the dashboard and every other reader take main's path.
Check
