Decision report · Rerail pull request #674

A stopped checkout's hook answers without waiting for a busy daemon

1. The one question

May a hook answer stopped by itself, from the database and the folders on disk, when the daemon has not answered within 75 ms?

  1. Beside a late daemon, a stopped checkout's hook answers stopped by itself. Changes the intent.
  2. The reference no longer says these hooks never contact the daemon. Changes the intent.

We recommend: approve it once a maintainer answers yes in #670: over 40 folder shapes the hook never answers stopped where the daemon reads otherwise, and beside an idle daemon hook times stay inside main's spread.

5. The changes

Each line opens its card.

AAsk first, answer after a graceMedium riskHook beside a busy daemon: 1,793 ms at main, 160 ms here (Linux x64).
Problem
In a checkout where Rerail is stopped, every Claude Code, Codex and Cursor hook asks the daemon whether Rerail runs there and waits up to 2 s. A daemon busy with other checkouts holds each one, for an answer of {}.
Who meets it
A person who stopped Rerail in some checkouts while sessions in others keep the daemon busy: every hook there. How many people work this way is not known. #670 reports one laptop with about 40 such sessions.
What it does
hookRerailStarted still asks the daemon first. daemonAnswer waits the grace out (settlesWithin). Past it, stoppedEndingRequest runs the hook's own read (knownStopped). Where that shows stopped, the hook answers stopped and ends its request. Elsewhere it goes on waiting. SQLite's error sends the hook back to the daemon; any other error is thrown. A test may hold the grace open (graceMs).
Risk
Medium. This check decides whether a hook does anything, for three coding agents. By itself it can only answer stopped, or throw when its own read faults, and only once the daemon is late. Every other path is main's.
Check
Is stopped the only answer daemonAnswer gives by itself? When the hook's own read throws anything but SQLite's error, stoppedEndingRequest ends the request and the hook answers {} with a line on stderr, in a started checkout too; at main it waits for the daemon there. The timer starts when the request starts, so on a slow machine the hook can answer before its request reaches the daemon. An explicit database path never asks the daemon, as on main.
BThe hook's own readMedium riskOf 80 folder checks the hook answers 26 by itself; the daemon reads none otherwise.
Problem
A hook that answers by itself must give the daemon's answer. main's read for a hook with no daemon runs Git in the agent's environment, where a ceiling variable or a config file can move its answer.
Who meets it
Every hook in a stopped checkout beside a late daemon takes this read's answer. A wrong stopped would leave a started checkout unrecorded and unchecked for as long as the daemon stays late. Source: our reading of the code.
What it does
gitSearchEnds walks up to the first .git Git takes (takenGitDirectory: HEAD, objects, refs, no core.worktree) and names where Git's search can end: that checkout, or outside Git. stoppedWithoutGit is true only when every end reads stopped in the database (statusWithoutRemote), which is never written. A checkout with no clone id, an open walk or an unreadable database gives false.
Risk
Medium. A wrong stopped leaves a started checkout unchecked and unrecorded. Every doubt gives false, and the hook then waits as on main. No path REVIEW.md lists as high-risk is touched: storage is only called.
Check
Does takenGitDirectory take exactly the .git that Git takes? Our runs found two shapes the walk read wrongly: an objects folder Git may not search, and a Linux top the kernel names in another letter case. Each now ends open, so the hook waits. statusWithoutRemote shares lookupAt's lookups before the remote (repositoryWithoutRemote). Name a folder shape the tree test lacks and it gets a row there.
CThe hook ends its requestLow riskDaemon 1.8 s late: 1,892 ms per hook at main, 158 ms here (Linux x64).
Problem
Node keeps a process alive while a socket or a pipe is open. A hook that answered first would still exit only when the daemon answered or the read's 2 s limit ended its request.
Who meets it
Every hook that answers stopped by itself under change A. Without this change it would have its answer early and its process would end no sooner. Source: our reading of Node, and the mutation that leaves the request open.
What it does
readRepositoryState takes an optional stop signal and passes it to daemonRepositoryState, readableDaemon and get, where endedBy joins it to the 2 s limit. recordedDaemonStatus passes it to Windows' question to the engine, and engineCapabilityProof hands it to the request, which then ends as refused. A stopped read returns null. No other caller passes a signal.
Risk
Low. Each new parameter is optional and only the hook's start check passes one. The status line, the dashboard and every other reader take main's path.
Check
On Windows a stopped proof answers refused, which recordedDaemonStatus reads as gone. Only readableDaemon passes a stop, and it then returns false, so the read returns null and no state file is touched. In get, a stop is not the time limit, so it is not reported as NotAnswering.

6. The decisions

Ask the daemon first and answer after a grace, or read first? ask 1

We chose ask first: beside a prompt daemon a hook costs what main's does.

Would change our mind: an answer of no in #670: the fix then moves into the daemon.

8. What is not covered

  • macOS never ran. A test injects its two realpath answers.
  • A real case-insensitive Linux folder never ran. A test emulates one with links.
  • A real session beside a busy daemon never ran. Every timing is a hook process against a stand-in daemon.
  • A daemon whose Git reads otherwise: one started with GIT_DIR set, for one. Late, the hook can answer stopped where that daemon reads started. Read, not run.
Six smaller gaps, eight limits that stay
  • A loaded Windows machine with few cores was not run. Each letter-case check asserts that the stand-in daemon got its request, and fails by name where the hook gave up before sending it. It passed 50 of 50 on Windows 11 beside four busy processes, on 32 logical processors.
  • One mutation turns no test red. It changes the default open of readOnly in repository-start.ts, a line main and this head share: the status line would then refuse a database that lacks a schema step. main has no test for it either.
  • Test callbacks over complexity 6. The rules scan reads no test file. By lizard 1.24.0, two callbacks this change adds in hook-host.test.ts count 12 and 10: the stand-in daemon's request handler and the tree test's body.
  • Timings at an earlier head. The hook figures are from 120f63573. At 5000fa904 a paired run of a stopped checkout's hook is within 1.1 ms of it on both systems, inside the spread. 6993ee854 changes one test file.
  • The first twelve commits hold an earlier design. They read the database first, through Git. 104944b0c and f75a4e3c3 replaced that code. Read the diff against main, not commit by commit.
  • Codex and Cursor hooks were not timed; the event stream not run. Their tests check the answer in a stopped checkout beside a busy daemon, as Claude Code's do. The event stream calls the same hookRerailStarted per event (event-stream.ts line 133); no test runs it beside a late daemon.

Limits that stay.

  • A Git repository Rerail never recorded and a new clone wait for the daemon: 1,794 ms on Linux x64 and 900 to 901 ms on Windows 11 beside a busy one, at main and here. Only their remote places them.
  • A started checkout beside a busy daemon waits as on main: 3,593 ms per hook on Linux x64 and 2,703 ms on Windows 11, at both.
  • With a stale daemon.json or none, the hook reads through Git, as on main: 10 s with a Git that hangs, at both, and an agent's ceiling variable still moves that read, by the code.
  • A database this version has yet to upgrade, or one the hook cannot read, sends the hook to the daemon, as on main.
  • An idle daemon whose answer lands just after the grace costs the hook its own read: median 7 ms on Linux x64, 8 to 9 ms on Windows 11. 0 of 1,800 and 0 of 1,200 idle asks did.
  • On a slower, shared Windows 11 virtual machine, at an earlier head, 8 of 900 idle asks fell in that band, each a median 15 to 22 ms slower.
  • On Windows 11 the hook beside a busy daemon stays at 219 to 232 ms: the hook process itself costs 128 to 206 ms there.
  • In 17 of the tree test's 80 checks on Linux x64 and 14 on Windows 11 the hook waited though the daemon read stopped: it answers only where every end of Git's search reads stopped.

9. What we ask of you

Asks 1 and 2 rule on answers 1 and 2.

  1. On #670: may a hook answer stopped by itself beside a late daemon? We recommend yes: in no tested folder did the daemon read otherwise.
  2. May the reference drop "never contact the daemon"? We recommend yes: main already asks first.
  3. Is the grace right for the Windows machines you see? We recommend keep it until a machine shows otherwise.
