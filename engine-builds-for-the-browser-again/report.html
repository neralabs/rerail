6. The decisions

Should the browser build leave out the reads' JIT, or take the stand-in?

We chose to leave it out: it only serves tests, which do not run on wasm.

Would change our mind: A maintainer who wants every crate to follow one pattern for the JIT on wasm.

Options and evidence
OptionWhat a user getsCostWhat it breaks
Leave jit out on wasm chosenThe browser build; nothing on wasm that could only fail there; Cargo.lock unchanged.Two lines of manifest and one cfg.rerail-clif differs from the other crates, which take the stand-in.
The stand-in in rerail-clif, as the other cratesThe browser build, in the same form as the other crates.A new dependency and a change to Cargo.lock.jit::Reads::new would compile on wasm and panic at its first call.

Evidence. rerail_clif::jit is used by rerail-clif's and rerail-tape-format's tests and one engine test, never by the engine; the browser check passes here with it left out.

Which C toolchain should CI's browser check use?

We chose wasi-sdk 34, pinned by its digest: the same toolchain on every run.

Would change our mind: A maintainer who wants CI to run the README's Homebrew steps as written.

Four limits that stay

Limits that stay.

  • cargo clippy -- -D warnings for this target stops on warnings main has: an unused variable in rerail-blocks and four in the engine. No check lints this target.
  • rerail-logic's example versions calls libc::mmap with no Unix gate, so cargo check -p rerail-logic --all-targets fails on Windows 11, at main as here. A dependency line cannot fix it: Windows has no mmap.
