Decision report · Rerail pull request #671

Code rules: a closed session's folder keeps only its own observations

1. The one question

Is every change a later session meets still seen and checked as before, with closed sessions' observations and lookups dropped?

  1. A session reopened in a closed folder reads the other worktrees again. Changes the intent.
  2. After a runtime's last close, the next session looks every folder up again.

We recommend: approve it if the trade #661 asks about is acceptable: a later session's steers and records match main's in our test, and a closed folder keeps 561 KB where it kept 36,091 KB.

5. The changes

Each line opens its card.

AA close keeps its own observationsMedium riskKept per closed folder: 36,091 KB at main, 2,996 KB with A, 561 KB with B too.
Problem
Each folder a session closed in keeps an observation of every file of every worktree until its runtime closes, 15 minutes after its last session. Nothing reads them unless a session reopens in the folder.
Who meets it
A person whose sessions end in several folders of a repository with many linked worktrees inside 15 minutes, as with one worktree per task. How often is not measured. #548 lists this among its causes.
What it does
close() calls #shareOwnObservations before it clears the session. It filters the folder's shared map in one pass and keeps a path when inSessionFolder says the folder's own walk covers it: no .. in front, and under no worktree root. The other worktrees' sources go, and so do files a tool wrote outside the folder.
Risk
Medium. A later session in the folder starts from less. A trim that keeps too little costs it file reads. Its edits are judged against its own observations, never the shared ones.
Check
Four places read the shared observations, all in a walk's scan: staleStamp skips a read, knownDigest carries a digest, observedText decides whether the walk keeps a file's text, failFolder marks known sources under an unreadable folder. Without the worktrees' entries the last two answer as in a new folder: acceptable? Can a second session live in the folder lose anything when the first closes? Does inSessionFolder keep wt/w1-notes when wt/w1 is a worktree?
BA runtime forgets its folder lookupsMedium riskLookups held: 15,471 folders live, 191 after the last close.
Problem
A session's walk of the other worktrees looks up the owner of every folder of every worktree. The runtime keeps each answer after its sessions end, until it closes 15 minutes later.
Who meets it
The same person as A: sessions that end in several folders of a repository with many linked worktrees. With A alone a closed folder keeps 2,996 KB; these answers are most of it.
What it does
forgetFolders clears #roots and drops every #confirmed entry that is not a top level Git confirmed. closeSession calls it once #sessions is empty, after the bridge has closed. cachedFolders counts the folders held; only the test calls it. #submodules and #plainRoots stay.
Risk
Medium. The next session there looks its folders up again. A forget that dropped the confirmed top levels would cost a Git process per checkout. A lookup decides which checkout's rules judge a file.
Check
After the forget, a lookup starts from the confirmed top levels alone. Is keeping them and #submodules safe, as main keeps them? Answers that said a folder holds no checkout go too, so the next session asks again: a folder that became a checkout meanwhile gets its own answer, where main keeps the old one. #abandonSession also removes a session and does not forget: that session ran no walk. cachedFolders is public for the test alone.

8. What is not covered

  • Windows 11: a reopened session's slowest hook: 1,481 and 1,430 ms, 1,259 and 1,134 at main, one busy run.
  • observedText and failFolder then answer as in a new folder, in log-mode records only: read, not run.
  • Lookups after the last close ask again about a folder that held no checkout: no test.
  • The field: no count of closes in many folders inside 15 minutes.
  • macOS never ran.
Six smaller gaps, six limits that stay
  • The Windows 11 run. Its first session, the same code at both, took 84.4 s of CPU at main and 81.2 s here: the machine was busy. A second run could not be compared: main's half ran beside five other runs. A quiet run in alternating order would settle it.
  • The two walk decisions. observedText keeps a file's text only when its digest differs from the one seen before. failFolder gives each source under an unreadable folder its read error. Without the worktrees' entries both answer as in a new folder, in the worktrees' walk alone, which steers no session.
  • A refused .git entry. forgetFolders drops every answer that is not a confirmed top level. A folder whose .git entry Git refused then costs its Git process again in the next session. Read in the code, not measured.
  • #548's report. It gives 4 GB of heap in under ten minutes at about 190 worktrees and lists this among its causes. We have not checked whether that build had the 15-minute limit.
  • The Windows run of the 31 files. It ran at a commit with the head's tree but for the release note's text. CI's two Windows unit jobs ran the head itself and passed.
  • Main since the base. Main moved to c438bc813 after this head's base, f277c6e29. The trial merge is clean, and the four source files quoted here are the same at both. No run of ours tested that merge.

Limits that stay.

  • Main frees all of this when the runtime closes, 15 minutes after its last session. This lowers the heap inside that window. It ends no leak that lasts the daemon's life.
  • A live session's memory does not change: it holds an observation of every file of every worktree while it runs, 41,214 KB at this shape against 41,338 KB at main.
  • After each walk the bridge still copies the session's whole map into the shared one: 10 to 12 ms at 95,500 observations, about 300 ms at 955,000, in a new process on Linux.
  • A session reopened in the folder inside the 15 minutes reads the other worktrees' files again on its first walk and looks its folders up again: about 15,000 at this shape, one lstat each.
  • The trim runs inside the close, in one pass: a daemon's first closes block the event loop about 17 to 22 ms longer, and the session-end hook takes 17 to 60 ms longer. Once warm, a close equals main's.
  • Files a tool wrote outside the folder leave the shared observations too. No walk covers them. The later-session test pins a tool write there against the text the file held at the call.
