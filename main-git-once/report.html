Every session in a repository with many worktrees makes the daemon start one Git process per worktree at each change of the recorded checkouts. The daemon answers nothing while Git runs.
Who meets it
Everyone with linked worktrees, at every start and every newly recorded worktree. A preload on the daemon counted 2,648 processes in a five-minute start at main 7ff56e15e on Linux x64 and 2,781 on Windows 11.

placementInputs reads what Git reads to place a folder. linkedWorktreeFromFiles places a linked worktree of a repository Git placed. repositoryIdentityLocation keeps Git's answer while its stamp holds. worktreeRegistry keeps one list per repository.
Risk
Medium. A wrong placement would have a file judged by another checkout's rules, or by none.
Check
Can Git's answer move while the stamp stays the same? The stamp holds both real paths, the texts of .git and commondir, the config lines that place a checkout, whether HEAD, objects and refs make a Git folder, and the owners of the real folder, its .git and its Git folder, read at every use. A checkout those files cannot describe keeps Git's acceptance for the list under the raw facts Git reads there.

8. What is not covered

  • CI runs the whole set on the pull request; the runs here are the changed modules' test files.
  • The start on a Windows 11 machine with every core busy ran at main only: 96.6 s without an answer and 685 failed hooks, one daemon.
  • macOS never ran.
Seven limits that stay

Limits that stay.

  • Another account's folders, which Git takes only through safe.directory, are asked of Git at every placement, as on main: no gain there, and nothing kept that Git could refuse.
  • CheckoutOwners' own answers are as on main: after core.bare is set in config.worktree, a file's owner stays until the recorded checkouts change.
  • A worktree registered by a relative path (Git 2.48) under a link retargeted at a renamed folder keeps its old list until a worktree is added or removed.
  • Under a lookup variable the list's kept acceptance follows the checkout's own files and the variables' values, not the folders they name, as main keeps its first answer.
  • A folder between a checkout and the repository above that already holds a HEAD file and later gains objects and refs keeps the old list until a worktree is added there, as on main.
  • Where a repository's core.worktree names a folder inside it, its .git moving away keeps the old list in a checkout below until that registry changes, as on main.
  • A checkout whose own facts cannot be read (its real path refused, or on Windows an engine that cannot read owners) has Git list its registry at each ask: one Git process a list, where main reuses its first answer.
