A selection's unit shards follow its recorded test time

1. The one question

6. The decisions

Read the weights by importing the split's module, or from a JSON copy?

We chose import shard-split.ts and the times: one rule for what a file weighs, which Node 24 runs with types stripped.

Would change our mind: A Node version for CI without type stripping.

The larger of the two counts, or the count by time alone?

We chose the larger: the times leave out each file's import and collection, which a shard of many light files pays.

Would change our mind: CI's logs of light selections' shards showing the time share alone keeps them well within 15 minutes.

Count the first shard's step in both shares?

We chose yes: the sequencer starts the first shard holding it, so each shard of a selection carries its part.

Would change our mind: A first shard that no longer runs that step.

8. What is not covered

  • Stale times a file that grew slower counts at its old time, so a selection can again get fewer shards than its time needs, never fewer than its count's.
  • One long file no count splits a file; service-stop.test.ts takes 266 s of a Windows shard's 858 s.
One limit that stays

Limits that stay.

  • The count bounds a shard's test time by a whole run's shard, not its wall time: a runner slower than usual still takes longer.
