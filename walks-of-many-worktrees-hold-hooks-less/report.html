Decision report · Rerail pull request #1110

Walks of many worktrees hold hooks less, with less CPU and memory

1. The one question

May the daemon take each walk one worktree at a time, keep worktree places until the tree watch reports a move, and share rule copies?

We recommend: approve it: with many worktrees and several sessions, a hook then waits for one worktree's audit, not a whole walk's, and the daemon asks the disk and the database far less.

5. The changes

Each line opens its card.

AA walk taken worktree by worktreeMedium riskA hook at the end of a first pass waits for one worktree's audit, not every worktree's.
Problem
At the end of the daemon's first pass, each watching session read the walk at once with the others and audited every worktree's findings in one turn of its queue, which its hooks waited behind.
Who meets it
Anyone with many worktrees and several sessions, at each daemon start. Load run, Windows 11, 190 worktrees, 8 sessions: a 6.7 s hook as the first pass ended.
What it does
#takeWorktreeWalk reads the take in the walk's turn (ReadTurn, WorktreeWalks.#inTurn); #applyTake applies takeParts: one part per worktree with something to audit, one for the rest; #beginTake lists the worktrees once; the last part keeps the observations once.
Risk
Medium. Every walk's findings go through the split; a part must hold exactly its worktrees' entries, records and answered reads.
Check
Does splitTake put every entry of a take in exactly one part? Does a failed part leave the parts after it with their records? Is a closed session's take stopped between parts?
BA folder's places resolved onceMedium riskA walk's 12 folders: 12 real-path look-ups at main, none here; 50 version reads: 50, then 1.
Problem
Every walk of every session looked each worktree up on disk again, and each folder's owner look-up asked the disk its real path and read every row of the recorded checkouts.
Who meets it
Anyone with many worktrees, after the first pass, at every walk of every session. Load run, Windows 11: the daemon used 46 % of a core on average.
What it does
FolderPlaces keeps a worktree top folder's place until the tree watch says its watch ended or lost notices; walkView(root) takes folders below the start as their own real paths (ownerOfReal); recordedCheckoutsVersionReader reads again only after data_version or total_changes() moves.
Risk
Medium. A kept place is wrong if the watch misses a move: nothing is kept through a link, for a missing folder, on macOS, or below a folder the engine cannot follow.
Check
Can a move reach a kept place before a notice? Does flush in the take report the kernel's queue in order? Is a let-go Windows root lost until reopened?
CThe worktree registry read onceLow riskRegistry files read to record 16 worktrees: 256 at main, 16 here.
Problem
Recording each worktree asked every recorded checkout's registry again, reading every entry and resolving the listed worktrees: n worktrees cost n times n reads on the daemon's thread.
Who meets it
Anyone with many worktrees, at each session start. Load run, Windows 11: a 4.1 s hook in the first minute as 8 sessions started.
What it does
WorktreeRegistryPass reads each registry once for a read that records many worktrees; the router reads eligibility in one refreshAll, and a session's first list does it in groups of 16 with a turn between.
Risk
Low. A pass answers what the registry held at its first question; the next pass reads it again.
Check
Can a worktree removed during a pass be recorded? Is the list read before the first turn, in the learn step's run?
DThe first walk yields, documents sharedLow riskPack rules serialized again for a second checkout's catalog: every one at main, none here.
Problem
Each catalog build made a new running document of every rule for every checkout, so each was serialized and hashed again, and a first walk started a wave's reads, each building a checkout's rules, at once.
Who meets it
Anyone with many worktrees, at the end of the first pass. Load run, Windows 11: a 6.7 s hook as the first pass ended.
What it does
runningDocument keeps one document per rule object and mode; ruleSourceText keeps a rule's text and digest by the rule; #startReads gives the thread back after each first-sight read starts.
Risk
Low. A shared document changed in place would change every checkout's: none is.

6. The decisions

Apply a walk's take whole, or one worktree at a time on the queue?

We chose one part per worktree with something to audit, one for the rest: a hook waits for one audit.

Would change our mind: A run where the turns themselves cost a hook more than the audits they split.

Options and evidence
OptionWhat a user getsCostWhat it breaks
The whole take in one turnNothing new.A hook waits for every worktree's audit at the end of a first pass.Nothing.
One part per audited worktree, one for the rest chosenA hook waits for at most one worktree's audit; few turns when little changed.A split of the take's entries, each once.Nothing a case shows: each part records and steers what the whole take did for its worktrees.
One turn per worktree, quiet ones tooThe same wait.A turn per worktree at every walk.Nothing, but each turn copies the observations unless kept for the last.

Evidence. Cases count the take turns the walks publish (1, 1 and 3 for two changed of five) and hold a session's audit while its tool call begins. A failed part leaves the parts after it, with their records, to the next walk.

Ask the disk for a worktree's place at each walk, or keep it?

We chose keep it while the tree watch shows nothing moved it, on Linux and Windows only.

Would change our mind: A move the engine's watch can miss on a supported system, shown by a case.

Options and evidence
OptionWhat a user getsCostWhat it breaks
Ask the disk at each look-upNo kept answer.A real path, a stored path and an existence check per worktree per walk of each session.Nothing.
Keep it until the watch's notice chosenNo disk look-up for a watched worktree's top folder.A user of the shared watch, flags only.Nothing kept through a link, for a missing folder, on macOS, or below a folder the engine cannot follow.
Keep it for a fixed timeFewer look-ups.None.A moved worktree served stale until the time passes.

Evidence. The places cases move, remove, replace by a link and retarget a worktree folder: each next look-up gives the disk's answer. A walk's own folders are their own real paths for that walk only.

One running document per checkout, or one per rule and mode?

We chose one per rule object and mode: nothing changes a rule document once read.

Would change our mind: A code path that changes a rule document in place.

Evidence. A case gives a rule a Log setting in one worktree: each checkout runs it at its own mode, and the other rule's document is the same object in both.

Two smaller gaps, one limit that stays
  • Kept place within a stretch. The watch's notices are taken once per stretch of synchronous work, so a move made after that take is answered from the kept place until the stretch ends.
  • Reads in turn. A session whose read of a walk is slow holds the other sessions' reads of that walk until it ends or fails; it holds no session's queue.

Limits that stay.

  • After this change main still opens every file at the first read after a restart on Windows, and asks Git's ignore rules at each walk; both are other changes.
