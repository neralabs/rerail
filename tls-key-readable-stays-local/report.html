1. The one question

  2. The start reads that key once, to tell it from another file.
  3. A TLS start on loopback only then exits 0, on http.

5. The changes

Each line opens its card.

ALoopback startHigh riskExposed key, remote start: no daemon at main, a loopback daemon here.
Problem
A person starts the daemon for other machines with a TLS key other accounts can read. The start exits 1, and under RERAIL_AUTOSTART=0 no hook starts a daemon, so no session on the computer is checked or recorded.
Who meets it
Whoever starts the daemon themselves for other machines, at every start while others can read the key. On Windows a key under C:\certs inherits such an ACL. Source: issue #664. We have no count of these people.
What it does
loadDaemonTls throws TlsKeyExposedError only for a file this account reads that parses as a private key (readPrivateKey) and whose certificate would serve (certificateServes). serveRerailDaemon catches it, and serveLoopback runs the daemon with loopbackArguments after it writes those arguments and --remote-refused with the reason into process.argv. A daemon launched with --remote-refused serves loopback from its start. runRerailDaemon loses only its export.
Risk
High. It decides whether a daemon with an exposed key is reachable from another machine, it reads that key on the refusal path, and it rewrites T9 of the threat model.
Check
loopbackArguments must drop every argument that binds off loopback or names a public host; parseArguments takes only --option value. --remote-refused can only narrow: remoteRefusal strips it and serveLoopback filters the rest again. readPrivateKey runs only after openToOthers found other readers; its bytes go to certificateServes and nowhere else. Any error but TlsKeyExposedError still ends the process with exit 1. certificateServes throws what an https start throws for that certificate, and never reads a FIFO.
BExit code and noticeMedium riskHolds refactor 11cb52c2a. Loopback TLS start: exit 1 at main, exit 0 here.
Problem
A daemon that serves this computer alone looks like any running daemon. A script or a remote client that asked for other machines must not take the start for started as asked, and a person must learn the key's fix.
Who meets it
The same person, and any script that starts the daemon and reads its exit code. Source: condition 2 of the ruling on issue #664.
What it does
remoteAccessExit returns 1 and writes one stderr line when the start had --allow-remote or --public-host and the daemon it started or found has remoteRefused. printDaemon prints loopbackOnlyNotice for the start and rerail status. DaemonState gains an optional remoteRefused. First, 11cb52c2a moves the launch options and dashboard link into daemonStartLaunch, daemonStartReach and printDashboardLink: 49 lines added, 26 removed, no behaviour change.
Risk
Medium. A wrong exit code tells a script that other machines are served when they are not. The refactor moves the checks of --host and of the transport, and must keep their order.
Check
Is exit 1 right while a daemon runs, or a code of its own (the description's decision 2)? Main gives 1 to this command line. remoteAccessExit reads --allow-remote and --public-host; --host off loopback needs --allow-remote, so it is covered. A TLS start on loopback only exits 0 on http: ask 3. In 11cb52c2a compare the old body with daemonStartLaunch and daemonStartReach: assertHostBindable, parsePublicHosts, parseDaemonTransport, then parsePort, as at main. A reader that does not know remoteRefused ignores it.

8. What is not covered

  • No code owner has read e3e22bd70.
  • Reach from another machine: measured at 646270e08, not since.
  • Hand starts: Linux x64 only.
  • macOS never ran.
Six smaller gaps, eight limits that stay
  • A forwarder the person runs. Behind one, the loopback daemon answers plain http, a request naming the public host gets 421, and every route but the page's files needs the access capability. Rerail's clients send it only once the pinned certificate matches, which an http listener never presents.
  • --remote-refused with remote options. No test launches a daemon with both. Read from the code: remoteRefusal strips the argument and serveLoopback passes the rest through loopbackArguments. One unit case would close it.
  • The state reader's check of remoteRefused. At 646270e08, with that line removed, every test passed. The line is unchanged, and no test at the head writes a daemon.json whose remoteRefused is not a string.
  • The refactor's order of checks. That 11cb52c2a keeps main's order rests on one reading and on the CLI tests that already start a daemon. No test compares the launch options before and after.
  • A real restart on Windows. The restart test relaunches through Node's spawn. A daemon's own restart there goes through the native launcher, with a reason that holds double quotes. That path did not run.
  • The whole suites. The whole suites ran only in CI. Outside CI at e3e22bd70: the 49 unit test files and 15 integration files that import a changed module, start a real daemon or run status, and on Windows 11 the 49 and three of the 15.

Limits that stay.

  • A forwarder the person runs in front of the port reaches the loopback listener, as it reaches any daemon started with no options.
  • A script that reads exit 1 from rerail daemon start as no daemon is wrong for an exposed key: the loopback daemon runs. It can read stderr, rerail status or remoteRefused in daemon.json.
  • From 0.1.4: a Windows daemon that served other machines with such a key serves this computer alone, and a macOS or Linux start that failed leaves a loopback daemon. To serve them, fix the key and start again.
  • The key is checked once, at the start. A key fixed while the daemon runs changes nothing, also across a restart at the heap ceiling, until rerail daemon stop and a new start.
  • An exposed key costs one more start attempt, one read of the key and one of the certificate: 432 ms at e3e22bd70 against 421 ms at main for the remote start on Linux x64, one start each.
  • runRerailDaemon stays at complexity 15: this branch removes its export and nothing else.
  • With an exposed key beside a --tls-cert that would not serve, the start exits 1 as at main and names the certificate, where main names the key. The key's refusal shows at the next start.
  • A defect of main, not changed here: with a private key and a FIFO as --tls-cert, the daemon blocks reading it and rerail daemon start gives up after 15 s. This change never reads a FIFO beside an exposed key.
