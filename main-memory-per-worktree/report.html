Problem
A session's first walk asks of every file of every worktree whether a rule reads it. main opens a rule engine in each worktree to answer, with the checkout's rules, a content store and its Git index.
Who meets it
Everyone who opens a session in a repository with many worktrees, once per daemon start. #726 measured 846 MB with 110 worktrees on 0.1.5.
What it does
#accepts answers for a worktree with no engine by an open engine at the same rules version (#laneWithRulesOf, rulesVersion, readsPath), through that worktree's own Git ignore rules; its catalog is read again with the engines' own.
Risk
Medium. The answer comes from another engine: a rule whose reach depended on more than its catalog version would read differently. None does at main.
Check
Is a catalog version enough to say two worktrees read the same paths, and is every worktree answered by another read again when the rules are?

Problem
A Git ignore reader holds its checkout's Git index. At main each session opens one in every worktree it asks about.
Who meets it
Every session after the first in a repository with many worktrees.
What it does
GitIgnoreMatchers hands a checkout's reader to a router while sourcesUnchanged holds: the engine reads Git's configuration again and compares three files' bytes. The reader keeps the index's stamp only where it tells every later write (NTFS, APFS, HFS+ at once; other local volumes once the clock leaves its times; network shares never), else compares the index's checksum.
Risk
Medium. A stale reader would hide files from the rules or check ignored ones; the engine reads the configuration again as its own open does and compares what the rules come from.
Check
Does Sources hold everything a reader opened now would read differently, and does refresh see every write of the index? It compares the worktree, the common Git folder, the excludes file, the pattern case, precious parsing and three files' bytes; the index by its stamp where the volume lets a stamp tell, else by its checksum.

6. The decisions

Which engine answers a walk's questions about a worktree with none open?

We chose an open engine at the same rules version, which reads the same paths, so no engine opens to answer.

Would change our mind: A rule whose reach depends on the worktree beyond its catalog version; none exists at main.

8. What is not covered

  • Later sessions still grow the daemon about as at main: this is part of #726.
  • Daemon CPU beside busy worktrees read within 3% of main's either way; the job's readings fell 25% from its first case to its last.
  • Windows 11, the first session's walk ended later: 85 against 70 s at main (medians of seven pairs, before the engine change), on no more CPU.
  • macOS, FAT, exFAT, ReFS and network shares never ran on such a volume; the cases stand in for each. #726 was measured on macOS.
Three limits that stay

Limits that stay.

  • An engine that has opened keeps the ignore rules it read for the rest of the session, as at main.
  • Where no stamp is kept (a read within its file's clock step, an index time ahead of the clock, a network share), each question reads the index's 20-byte checksum; under index.skipHash, which writes none, it parses the index.
  • The volume is found once per reader by its file system's name: a driver that reports NTFS, APFS or HFS+ while giving a new file an earlier one's identity would keep a stamp that cannot tell them.
