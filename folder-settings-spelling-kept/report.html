Decision report · Rerail pull request #676

A folder keeps its settings under the spelling an earlier version stored

1. The one question

Do you want an earlier version's rows copied to the spelling Windows stores, with a table of spellings, or moved with no table?

  1. Log and a silent status line 0.1.4 saved apply; a folder outside Git lists once.
  2. 0.1.4's own repository list shows each copied folder outside Git twice.
  3. On Windows a start-state check first copies rows waiting on its drive. Changes the intent.

We recommend: answer on #666 first, since it can change the copy rule; in 262 kinds of reading on Windows 11 beside 0.1.4, none of this build's is below main's.

5. The changes

Each line opens its card.

AThe step copies and keepsHigh risk0.1.4's Log, read back: 0 of 26 at main, 26 of 26 here.
Problem
After the update a folder a person set to Log is steered again, and a status line they turned off is drawn. Their settings sit under the spelling the session gave, where this version no longer looks.
Who meets it
A person on Windows who updates from 0.1.3 or 0.1.4 with settings saved in a folder reached as c:\…, through a mapped or subst letter, or outside Git as typed. How many installs hold such rows is not known.
What it does
lookUpPathKeys reads every key and looks each up before the write lock. Under it, respellPathKeys records each spelling that moved in path_key_spellings, and copyKeyedRows copies a folder's rows in five tables to the stored spelling where that key holds none. The earlier rows stay. A folder that is gone keeps its key. On macOS and Linux the step reads nothing.
Risk
High. A database step under src/engine/storage/, a high-risk path in REVIEW.md. A wrong copy changes whether the agent is told about a broken rule, and no later open repairs it.
Check
Can copyKeyedRows overwrite a row under the stored spelling? Its NOT EXISTS reads the other primary key columns from PATH_KEYED_TABLES: is each list whole? Does keyOrStored leave a key waiting for every error that can pass, and keep it only for a folder that is gone or unreadable? Under the lock respellPathKeys reads the audit history only past the lookups' last row: can a key written in between be missed? No lookup on disk may run under the lock.
BTriggers carry later changesHigh riskA scope 0.1.4 sets later, read back: 0 of 5 at main, 5 of 5 here.
Problem
An older install's hooks keep writing under their own spelling. Without the triggers this version goes on reading the copy as the step made it: a later stop, Steer or compact set by 0.1.4 does not reach it.
Who meets it
A person who runs two versions on one database: after a downgrade, or with a coding agent whose hooks come from an older install. How many do is not known.
What it does
13 triggers on five tables run inside an earlier version's own writes. copyOfOld matches this version's row only while it still holds every value the earlier row held; for a preference, which keeps no time, also only a row made after preferences_before. A checkout carries only its start state. A write under any other key costs one primary key lookup.
Risk
High. The triggers are part of the schema applied at every writable open and run in every write to five tables, an earlier version's included. A trigger that failed would fail that write.
Check
Can any trigger statement fail the write that runs it? They use no conflict clause and set only values the earlier row holds. Does each values list in CARRIED_TABLES name every column that tells a copy from a row saved apart? CREATE TRIGGER IF NOT EXISTS keeps an old body, so a build that changes a trigger must drop it in a database step. Does setCheckoutStarted still set its value, now that the nested rows go first?
CDrives and the write lockHigh riskStart-state check, write lock held: 25.8 ms at main, 30.8 ms here.
Problem
A key on another disk, a mapped drive or a share cannot be looked up from anywhere: a share whose host is gone holds a read about 21 s. And a reader that copies must not wait on a writer.
Who meets it
A person whose folders sit on a drive other than the system drive, or behind a mapped or subst letter. A hook that no daemon answers and rerail state make the check.
What it does
readableRoots lets an open look keys up on the system drive and its caller's drive only, 1 s per drive. The others wait. openRerailDatabaseIn copies them when a caller first works on their drive, and copyKeysWaitingIn takes the write lock only when free. The daemon copies before it answers, for a coding agent only on its own checkout's drive.
Risk
High. Every writable open on every platform now passes readBeforeLock and migrateLater, and the check a hook makes before anything else can write. A reader that waited or failed here would hold a coding agent up.
Check
On macOS and Linux, does applySchema do what main's does? Can openRerailDatabaseIn return a closed connection, or leave one open, on any path through keysWaitHere? copyKeysWaitingIn repeats a writable open's three steps with a lock wait of 0: does it stay in step with openChecked? Can a coding agent make the daemon look up a drive it does not work on (copyWaitingKeysFor)? requestedFolder sends the session's spelling on Windows only.

Problem
With the earlier rows kept, every list that reads a keyed table would show a copied folder twice. And a start state must still follow a stop 0.1.4 makes in the same folder under another letter case.
Who meets it
Anyone who opens the repository list, the repository audits or the presentation preferences after the step. The stopped folder: a person who stops Rerail with 0.1.4 after this version first ran there.

8. What is not covered

  • 0.1.4's own repository list doubles each copied folder outside Git. The narrower copy rule waits for #666's answer.
  • Shown by unit tests only: a later start by 0.1.4, its changes to rule settings and repository audits, and its deletions.
  • Four lines have no test that fails without them.
  • Not run: macOS, the whole suite, real daemons at cc6afc0b2 (its source is fe4da2b09's), a merge with #708 or #674.
Six smaller gaps, eight limits that stay
  • rerail settings alone on another drive. On a drive other than the system drive it reads Steer until a hook or rerail start, stop, status or state has run there. Shown at 8ad35c3d2, on a path no later commit touches.
  • A first session under a held write lock. It waits about 5.9 s and is not told Rerail runs, at main and here: 5,858 and 5,870 ms on Windows 11, 5,256 and 5,261 ms on Linux x64. It reads Steer; the next session copies and reads Log.
  • A case-only rename. After a folder is renamed in letter case only, both versions read Steer for it and list two rows, at main and here.
  • A link to a gone share. A key on the system drive whose folder became such a link would be looked up at each writable open from that drive: not measured. One such lookup took 21,030 ms. 0.1.4's own keys never reach that state: it stores a link's target.
  • Row ids across rerail scrub. The preference rule relies on SQLite keeping the row ids of presentation_preferences through VACUUM. If that changed, copies would stop following 0.1.4's later changes; no row that stood would start following.
  • The four lines, named. The filter in parentCheckouts, which no longer serves the start state; path_key_spellings among a headless scan's configuration tables; the folder readLiveResponse sends; and the filter in pruneCheckouts, which nothing in src calls. Not checked again at this head.

Limits that stay.

  • A later change by an earlier version carries only while this version's copy still holds what the step copied. Once this version changes the copy, it keeps its own values, as at main.
  • What an earlier version first saves after the step under a spelling the step never saw is not read here, as at main.
  • Where 0.1.4 saved a folder under both spellings, the row under the stored spelling stays for both versions, and this version reads it under every spelling, as main does: Steer where only the other spelling held Log.
  • A presentation preference removed here is removed for the earlier version too. Its status line through a drive letter applies what it saved under the letter, where at main it is drawn.
  • Cost on Windows 11: a writable open takes 60 to 140 µs more than main's (0ed1ad013), and a session start through real hooks 16 ms more at the median of pairs, from 47 less to 67 more (8ad35c3d2).
  • Writes to five tables run a trigger, not timed on its own.
  • The audit history is never rewritten, no floor is raised, and an earlier version still opens the file. On macOS and Linux the step reads and copies nothing.
  • Two sentences of docs/windows.md rest on unit tests only: this version reads a start an earlier version makes later, and a row saved under the stored spelling before the step copied the folder keeps its values.

9. What we ask of you

Asks 1 to 3 rule on answers 1 to 3.

  1. The copy with its table of spellings, or a move with no table? We recommend the copy, as built; rule on #666.
  2. May 0.1.4's list double a copied folder until #666 is answered? We recommend yes, for now.
  3. May a start-state check write on Windows? We recommend yes: it never waits on a writer.
  4. May a Migration read before the write lock, and run at later opens? We recommend yes: no lookup then holds the lock.
  5. Where 0.1.4 saved both spellings, does the stored spelling's row stay? We recommend yes, as at main.
