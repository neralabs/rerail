Intro: where the port stands

The branch checks three things about how a rule program is split into a per-file part and a cross-file part. Positions are not identities (0649). A relation that spans files is declared (0652). No node id goes into the cross-file part, because every edit of its file renumbers it (0677). Each check fails a pack's test when a rule breaks it, except for the relations in three lists, which may only shrink.

Decision 1: the branch's points-to (fix 3e)

What it is

Call targets and value types for Python come from a points-to analysis that runs over every file. On main it is the typing program's third phase, typing/programs/calls_p3.rerail (1,625 lines). It hands its answers on by path and byte span. Inside, it joins nodes of different files, which is where the 85 entries come from.

On the branch the same analysis took a different road. It is a library, python/points-to.rerail, which several hub merges and t32 changed. Stage 8 of t32 made it read other files by symbol, and main does not have that stage. Fix 3e (b754ec6c93) then split it in two: per-file rules (points-to-file, 847 lines), and a phase points_to over terms (points-to-solve, 1,319 lines) whose nodes are symbols or places. It also rewrote the four policies so that their walk is symbol-only.

On the branch, fix 3e took Django from 136 entries to 38. On 143 posthog files it ran 8% fewer instructions, and peak memory went from 1.18 to 1.40 GB.

Port it here

  • Main's calls_p3 is replaced by the branch's points-to, with t32 stage 8 first.
  • Django's list drops by about 117, as on the branch.
  • This replaces a program the Typing line owns. The two lineages share no history, so this is a rewrite, not a merge.
  • It needs the typing oracle tests rerun, on top of the 30 the commit names.

A pull request of its own recommended

  • This PR merges with the 155 listed. The list can only shrink, so no new crossing gets in meanwhile.
  • The P3 swap is reviewed as what it is: the Typing line's program replaced by the branch's.
  • I can start it right after this PR, on top of it.

Decision 2: a producer for spec_resolved

What it is

Node's import rules (n-no-missing-import, n-no-missing-require, n-no-unpublished-*) need to know which file a specifier resolves to. The library declares spec_resolved(n, file) as an input that core should provide. Nothing provides it, on main or on the branch, so it is bound empty.

With it empty, n-no-missing-import and n-no-missing-require report every import as missing. Before this PR they did not run at all: they were among the 25 policies not run.

Main already has the resolver: import_target, a port of enhanced-resolve with eslint-plugin-n's options, which the JSON rules' importTarget uses. What is missing is a route into a rule program. A file's resolution depends on other files (a target appearing, a package.json, node_modules), so a file's own part cannot answer it without going stale.

A phase, like tsx_names recommended

  • The per-file part states each file's specifiers by symbol: path, name and style. These are the strings in import and require positions, a superset of the library's node_target.
  • The phase answers them natively through import_target, on the engine's request route (the one dir_entry uses).
  • It hands the answers on by path, a setting such as tsx_names__target_at. node-resolve reads them at the file's own path.
  • No node crosses, and a file's memo entry is keyed by its own rows.
  • Cost: a new phase and a request with a key of three parts.

Resolve in the cross part

  • A request answered in the cross-file part, joined to the specifier node there.
  • Less work.
  • Every import node of every JavaScript and TypeScript file then sits in the cross part: new node-list entries, against 0677.

Until a producer lands, the two rules could go back to not running, so that they report nothing rather than everything. I have not done that: it would add to a list that may only shrink.

My recommendation: decision 1 as its own pull request after this one, and decision 2 as a phase, built in this PR.
