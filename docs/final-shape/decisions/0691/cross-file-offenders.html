Cross-file offenders on main

Intro

The new checks on main list three kinds of offender in main's packs and data-layer policies. Undeclared crossings: a relation that spans files without a cross_file declaration. Node crossings: a relation of the cross-file part that holds a node id. Policies that do not run: they fail for an error of their own, so their programs go unchecked.

Each entry is put in one of three buckets, by comparing it with the branch where the same rules were fixed:

  • port Fixed on the branch: the branch no longer lists it. The fix is a rule rewrite, a split fix in the engine, or a new phase. It needs porting, not designing.
  • known Fix known: still listed on the branch, and its fix is a documented pattern (key a value table by its node, resolve by symbol, add a producer).
  • redesign Needs a redesign: a whole-program analysis that walks other files' nodes. Each needs its own symbol-keyed design before it can be rewritten.

How the buckets were assigned: by the branch's final list of node crossings, its rule files and its decision record. "Fixed on the branch" is by relation name in the same pack. The fix that cleared it is named where the record names it; the rest cleared through rule edits and split fixes the record describes together. "Redesign" is a judgement from each rule's shape, and each such policy will be read again before it is changed.

React and Node: why they do not run

Seventeen of the 25 policies that do not run are React's 9 and Node's 8. They fail because three repository inputs that their libraries read have no producer in the engine:

  • tsconfig_for, with tsconfig and tsconfig_path. lib/core.rerail declares them as core inputs. The repository reader makes file, package, package_field and package_for, but none of the tsconfig rows. A React policy reads them through lib/tsx/names.rerail, which follows tsconfig paths aliases to resolve where React was imported from. The branch added the producer; port it.
  • npm_ignored and spec_resolved. The Node libraries declare these themselves, marked "proposed core input", because they need native code: npm's publish rules, and Node's module resolution with node_modules. Nothing makes them, and the engine stops at an input it has no columns for. The branch binds them empty. That makes the policies run, but an empty spec_resolved means every import fails to resolve, so n-no-missing-import would report every import. The fix is two producers. spec_resolved comes from the engine's own resolver (import_target, already used by the JSON policies), and npm_ignored from a reader of package.json files and the ignore files.

Python: in this change

Python accounts for most of the list: python-main 2,473, python 333, Django 250 node crossings. Two roots cover most of it, and both have branch fixes to port, in this order:

  1. value_type (248). The JSON-to-.rerail translator wrote a value's type test as value(n, x), value_type(x, T): a table keyed by the value's text, shared by "12" and 12. That is a join of every file's types, and it gives false findings. The translator now writes value_type_of(n, T), the node's own type, and the generated python-main files are written again.
  2. resolve_export (2,387). Python's import resolution becomes an earlier phase, py_names, over symbols. It hands on reads_at(p, m), exports(m, x, q), class, defined and public. python/names.rerail splits into its per-file half (scopes) and a reader of the phase, so sym_of and everything that reads it stay per-file. The class hierarchy, Django's models and points-to follow the same shape on the branch (ancestor, a model's fields, Meta and hooks by symbol, the points_to phase), and are ported with it for Django's entries.
  3. The engine faults that rewrite exposed on the branch, ported with it:
    • rules that can never hold, with unset at a location;
    • a gated negation's ask that read an unbound variable;
    • the factorizer keying a join on a node;
    • a pushed join handing on its id-range bound;
    • a row located by a name built from its path.
  4. Main's phases and the memo. Main runs phases (sources, types, values) but has no per-path scoping of a phase's rows in a file's memo key. Without it a change to any module's exports would run every file again. The branch's scoping (SETTINGS_BY_PATH, SETTINGS_BY_FOLDER) is ported with py_names. Whether main's memo keys a file by the phase rows it reads at all is checked first, since that would be a correctness gap, not just a cost.
