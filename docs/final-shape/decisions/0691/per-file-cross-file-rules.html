Per-file and cross-file rules

Which facts may leave a file, how to say that a relation spans files, how rules break that by accident, and how to fix each kind of break. For people writing .rerail libraries and packs, and for the models that write them.

Intro

The problem. Rerail keeps its findings current as files change. It can only do that cheaply when most of the work belongs to one file: edit a.py and only a.py's rules run again. Work that combines files is kept up to date over the whole repository, so everything that flows into it is paid for at every edit of every file it came from.

The worst thing that can flow there is a node id, the engine's name for one syntax node. A node id belongs to its file and to its place in that file. Add a line at the top of a file and every node below it gets a new id. Any cross-file fact that held one of those ids changes, for every reader, though nothing changed in meaning.

What changes. Three rules now say what may cross from the per-file work to the cross-file work, and the engine checks them on every program it prepares:

  • no relation spans files unless it is declared cross_file;
  • no node id, and no value computed from one, crosses;
  • no cross-file rule reads a node's position (its line, column, order).

One example. JavaScript's capitalised-name check was a table of every identifier's text that starts with a capital letter. The table kept the text and dropped the node, so it held every file's texts in one place. Each rule that asked "is this identifier's name capitalised?" then had to join its node to that table across files, and the engine moved it, node and all, into the cross-file work. Keyed by the identifier node, the same test stays in its file:

Before: crosses files
// every identifier text in the run,
// without the node it came from
.decl capital(x: symbol)
capital(x) :- kind(n, "identifier"),
    text(n, x),
    c = @slice(x, 0, 1), c != @lower(c).
After: stays in its file
// the identifier node itself:
// each row is one file's
.decl capital_id(n: node)
capital_id(n) :- kind(n, "identifier"),
    text(n, x),
    c = @slice(x, 0, 1), c != @lower(c).

Status. The checks run on every program; they print what they find, or refuse the program, when asked (Checking). Every pack's offenders are listed in the repository, and each list can only shrink: a new rule that adds an offender fails its pack's test.

How to read this. The two parts and Where a relation runs explain the model. The three rules and Declaring cross_file are the reference. How violations happen walks through each way rules break them, the non-obvious ones included. Taxonomy and Fix recipes are for fixing a reported offender. The two parts of a program

The engine splits every program in two. The per-file part runs over one file at a time. Its results for a file are kept, keyed by that file's content, and reused until the file changes. The cross-file part runs over the whole repository and is maintained from changes: when a file's per-file results change, the cross-file part takes in the difference.

What passes from one to the other is a set of handed-on relations. Each of their rows names the document it came from, so the engine can replace exactly one file's rows when that file changes.

Where a relation runs

You do not say where a relation runs. The engine decides, from its rules, and the decision spreads through the program. A relation is per-file when every rule for it reads one document's rows: every relation it reads has a location (a node, or a document) and the rule ties all those locations together, through shared variables, docof(n, d), or a node relation that holds both.

A relation is cross-file when any of these holds:

  1. It is declared so: .decl r(...) cross_file.
  2. One of its rules joins two documents. Two reads whose locations nothing ties together: the split's message is joins 2 documents: {c} {f}, one group of variables per document.
  3. One of its rules reads a document's rows with no location: a table that kept a value but not where it came from. The message is reads X with no location.
  4. One of its rules reads a cross-file relation. It follows that relation: reads cross-file X. This is how placement spreads.
  5. The engine moved it. A relation whose rows name no document, read by a later cross-file rule, is moved there with its per-file readers (moved by locate).

Some reads place nothing, so they never make a rule cross-file on their own: facts written in the program, the run's options, settings handed on by an earlier phase, and text tests.

This is why one small table can pull thousands of relations across. On main, a single symbol table of Python's import resolution is the root of about two thirds of every node crossing: each rule that looks up a name's definition reads it, follows it into the cross-file part, and takes its own nodes along.

The three rules

1. Declared, or per-file

Every relation is per-file unless it is declared cross_file. A relation that is cross-file for a reason of its own (a join of two documents, a read with no location) and is not declared is a violation.

Followers need no declaration: they are cross-file because a declared relation is. Helpers the engine makes for a relation share its declaration.

2. No node ids across

No relation of the cross-file part holds a node id: no column typed node or loc, and no value computed from a node (@to_string(n), n + 1, a min over nodes).

Cross-file facts are keyed by symbols, paths, document keys and values. A node's document, text and digest are values, so they may cross. Findings keep their node: it is where the finding is written.

3. No positions across

No cross-file rule reads line, col, end_line, node_order, visit_index or ast_depth, unless its head is an output. An edit above a node moves all of them.

Compare positions in the file's own rules, and hand on the answer.

Declaring a cross-file relation

Declare a relation cross_file when spanning files is its job: a module's exports, a class hierarchy over the repository, a call graph. The word goes after the columns, as the other declaration words do:

// exports(m, x, q): module m exposes name x, which denotes q.
// Keyed by symbols only: no node, no position.
.decl exports(m: symbol, x: symbol, q: symbol) cross_file

// A file's own rule reads the answer back at its own node:
// sym_of is per-file, because n and the import both belong to this file.
.decl sym_of(n: node, q: symbol)
sym_of(n, q) :- import_name(n, m, x), exports(m, x, q).

What the declaration does and does not do:

  • It allows the relation to span files, and places it in the cross-file part.
  • It does not allow node ids. A declared relation with a node column is still reported by rule 2. Declare only relations keyed by symbols, paths and values.
  • It is kept when a program is printed and read again.
  • A relation the engine moved itself is not declared. Its rows are checked as undeclared once something reads them on.

Declare as little as you can. Each declared relation is maintained over the whole repository. A declaration that only silences the checker hides a join that the next reader pays for.

How violations happen

Each case below shows a rule as someone wrote it, what the engine sees, what the checker reports, and the fix. The first three are the common ones. The fourth is the one people miss.

join Two documents joined by a value

Two reads share a value (a name, a kind) but nothing says they are in the same file. The rule then pairs every file's rows with every other file's.

// Intended: a call to a function defined in the same module.
// Written: a call to ANY function of that name, in any file.
.decl local_call(c: node, f: node)
local_call(c, f) :- call_name(c, x), def_name(f, x).
local_call: joins 2 documents: {c} {f} local_call: holds a node in local_call.c, local_call.f
Fix, if same-file was meant
local_call(c, f) :- call_name(c, x),
    def_name(f, x),
    docof(c, d), docof(f, d). // one file
Fix, if other files were meant
// resolve by symbol, then read back per file
// (recipe: a phase over symbols)
calls_sym(c, q) :- call_name(c, x),
    resolved(x, q).

table A table of values that dropped its node

The most common break, and the easiest to miss. A helper computes a fact about some node's text and keeps only the text. The table now holds every file's texts, with no location. Every rule that asks the table about its own node joins across files, and moves into the cross-file part with its node.

// the text of every zero literal, from every file
.decl zero_number(t: symbol)
zero_number(t) :- kind(n, "integer"), text(n, t), t = "0".

// a per-file rule asks about its own node: now cross-file
start_zero(s) :- assignment_value(s, v), text(v, t), zero_number(t).
start_zero: holds a node in start_zero.s (in the cross-file part under zero_number)

Rule 1 lets the table itself through: it is a union of each file's values. The reader is caught by rule 2, because it takes its node across, and the report names the table as the crossing it is under.

Fix: key the table by the node
.decl zero_lit(n: node)
zero_lit(n) :- kind(n, "integer"),
    text(n, "0").
start_zero(s) :- assignment_value(s, v),
    zero_lit(v).
Or test the value where it is read
// a pure function of the text: no table
start_zero(s) :- assignment_value(s, v),
    text(v, t), t = "0".

A table that is a pure function of its value (case, prefix, a regex split) never needs to be a table. Write the test in the reading rule. A table that also gives wrong answers this way is common: "is this name capitalised" became "does any file have a capitalised identifier with this text".

no location Reading every file's rows at once

A count, a min, a negation or an existence test over a per-file relation, with no variable that names the file, reads all files.

// "this module is the only one that defines main": every file's defs
lone_main(f) :- def_name(f, "main"),
    k = count : { def_name(_, "main") }, k = 1.
lone_main: reads def_name with no location

If the answer really is about the repository, compute it as a declared cross_file relation over symbols or paths (main_modules(p)), and test it in the file's rule. If it is about the file, add its location: docof(f, d) and the same d inside the aggregate.

same file Same-document joins the engine cannot see

The non-obvious case. You know two nodes are in one file, but the rule does not say so in a form the split reads. The split trusts only what ties locations together: one variable shared by two node columns, docof(a, d), docof(b, d), @doc(a) = @doc(b), a tree relation that holds both nodes (child, field, within), or nearest.

// You mean "a and b are in the same file". The split sees two documents.

// 1. Joined by the path's text: two documents may share a path value
pair(a, b) :- kind(a, "class"), kind(b, "def"),
    docof(a, d), doc(d, p, _), docof(b, e), doc(e, p, _).

// 2. Linked only by a comparison: a test filters, it does not join
pair(a, b) :- kind(a, "class"), kind(b, "def"), a < b.

// 3. Same file "by convention": a name both sides share
pair(a, b) :- class_name(a, x), def_owner(b, x).
pair: joins 2 documents: {a d} {b e} pair: joins 2 documents: {a} {b}
// The forms the split reads as one document:
pair(a, b) :- kind(a, "class"), kind(b, "def"), docof(a, d), docof(b, d).
pair(a, b) :- kind(a, "class"), kind(b, "def"), @doc(a) = @doc(b).
pair(a, b) :- kind(a, "class"), within(b, a).        // b inside a
pair(a, b) :- field(a, "body", s), child(s, b, _).   // a tree relation

Comparisons do not tie anything: a != b and a < b only filter rows that the other reads already joined. A rule whose only link between two groups of reads is a comparison is a cross product of every file with every file, even when you only meant positions in one file. Add the docof pair and the comparison becomes a filter inside one file.

follower A per-file rule that reads a cross-file answer at its node

The rule itself is fine. But it reads a cross-file relation, so it follows it into the cross-file part, and its own node goes with it. One cross-file table read this way by a library helper that every rule includes moves thousands of relations.

// resolve_export(q0, q) is cross-file: it follows imports across modules.
// sym_of is a per-file question ("what does THIS name refer to?")
// but it now runs over every file, holding every file's nodes.
sym_of(n, q) :- qn(n, q0), resolve_export(q0, q).
sym_of: holds a node in sym_of.n (in the cross-file part under resolve_export) … and about 2,400 more relations under resolve_export

Fix it at the root, by moving the cross-file answer into an earlier phase over symbols. The phase runs first, over every file, and hands on its answers keyed by module or path. The main program reads them as settings, which place nothing, so sym_of stays in its file (recipe 4).

node value A value made from a node

A node id turned into a number or a string is still a node id. The checker follows values through arithmetic, @cat, @to_string, and min, max or sum over nodes.

// a "key" for the definition: still its node id, as a string
def_key(k, x) :- def_name(f, x), k = @to_string(f).

// "the first def": a min over node ids orders them by file and slot
first_def(x, m) :- m = min f : { def_name(f, x) }.
def_key: holds a node in def_key.k

Use a key that means something outside the file: the path and qualified name (@cat(p, "::", q)), or the place as text ("src/a.py:12") when a finding must name another file's line. These are allowed: @doc(n), text, @tree_digest, @unparse, @place.

position Positions in the cross-file part

// cross-file because it reads exports; and it compares lines
late_import(i) :- import_of(i, m), exports(m, _, _), line(i, l), l > 10.
the cross-file part reads positions, which every edit moves: late_import reads line

Compute the position test in the file's own rule (late(i) :- line(i, l), l > 10) and read late(i) in the cross-file one. Outputs may read positions: a finding is written once, at its place.

fine Things that look like violations and are not

  • One plain read of a per-file relation in a cross-file rule: all_defs(f) :- def_name(f, _). Each row is one file's, so the relation is a union of the files' rows. It still must not carry a node if it is read on.
  • Reading a declared cross-file relation. The reader follows it and is not named.
  • Facts, options and settings (option("max", m), an earlier phase's exports): one value for the run, no location.
  • An output holding a node: that node is where the finding is shown.
  • Text tests (match, prefix) over a value: they filter.

Fix recipes

1. Key the table by the node, or drop the table

If a helper's answer is a function of one node, its first column is that node. If it is a pure function of a value, it is not a table: inline the test where the value is read.

2. Say "same file" in a form the split reads

Share the node variable, or use docof(a, d), docof(b, d) or @doc(a) = @doc(b), or a tree relation (child, field, within, nearest). A shared path text, a shared name and a comparison tie nothing.

3. Repository facts without nodes

When a rule needs a fact about the whole repository (a package's dependencies, which modules define main), compute it keyed by paths or symbols, declare it cross_file, and test it in the file's rule. Only the small fact crosses.

4. Cross-file resolution as an earlier phase over symbols

This is the shape for names, imports, types and class hierarchies. Split the work in three:

  1. Each file states its own facts by symbol. Which module it is, what it defines (by qualified name), what it imports. Its nodes stay with it.
  2. A phase resolves symbols against symbols. It runs first, over every file, to a fixed point, and holds no node. It hands on answers keyed by module or by path: exports(m, x, q), reads_at(p, m), ancestor(m, c, b).
  3. Each file reads the answers back at its own nodes. In the main program the phase's exports are settings: they place nothing, so the reader stays per-file. Read them by the file's own path, or by a module the file's own rows name, so that an edit misses only the files whose answers changed.
// per-file: this name node, its dotted name, and this file's path
export_at(n, q) :- qn(n, q0), split_dot(q0, m, x), docof(n, d), doc(d, p, _),
    py_names__reads_at(p, m),        // the phase: p can see module m
    py_names__exports(m, x, q).      // the phase: m exposes x as q

5. Re-key a meant crossing by symbol

A call graph, an inheritance chain or a "first definition" across files: replace each node with its symbol (a qualified name), or with @cat(path, "::", qualname) when two files may define the same name. Run the closure over the keys, and let each file's rule find its own node by its own key. When a finding must point into another file, name the place as text ("src/a.py:12"), read in that file.

6. Compare positions where the nodes are

Decide "earlier", "on the same line" or "after line 10" in the file's own rule, and hand on the yes/no answer.

7. Declare it, with a reason

When a relation spans files on purpose and holds no node, declare it, and say in a comment what it is and why it is keyed as it is. A reviewer should be able to check the claim from the comment.

Checking your rules

Every program the engine prepares is checked. By default the checks report nothing unless asked, and refuse nothing. These switches change that:

SwitchEffect
RERAIL_SHOW_CROSSINGS=1Print each undeclared crossing with its rule, and each node crossing by the root it is under.
RERAIL_STRICT_CROSSINGS=1Refuse a program with an undeclared crossing, naming each relation, why, and its rule.
RERAIL_STRICT_NODES=1Refuse a program whose cross-file part holds a node id.
RERAIL_STRICT_POSITIONS=1Refuse a program whose cross-file part reads a position.

The pack tests run every pack's policies, split as a real run splits them, and compare what they find with three lists in the engine's sources: split_crossings.txt, node_crossings.txt and policies_not_run.txt. A relation new to a list fails the pack's test. A relation you fixed must leave the list in the same change; the test fails until it does.

# from native/: one pack, printing what it finds
RERAIL_SHOW_CROSSINGS=1 cargo nextest run --lib --no-capture \
  --ignore-default-filter -E 'test(/pack_split_tests::the_react_pack/)'

Reading a report: fix the root first. A line ending under X is a follower of X. Lines ending under - are roots of their own. A run of one policy alone can place relations differently from a run of its whole pack, so both are checked for the data layer.

Checklist for models writing rules

Paste this into the instructions of a model that writes or edits .rerail rules.

Before writing or changing a .rerail rule:

1. Every helper relation about a node takes that node as a column.
   Never keep a node's text or name without the node, unless the table
   is declared cross_file on purpose.
2. A pure function of a value (case, prefix, split, regex) is written
   inline in the reading rule, not as a table.
3. Two reads in one rule are tied by a shared node variable,
   docof(a, d), docof(b, d), @doc(a) = @doc(b), or a tree relation
   (child, field, within, nearest). Equal names, equal path texts and
   comparisons do not tie them.
4. A count, min, max or negation over a per-file relation binds the
   file inside it.
5. No relation that spans files has a node or loc column, or a value
   made from a node (@to_string(n), n + 1, min over nodes). Key it by
   qualified name, path, or @cat(path, "::", qualname).
6. Cross-file questions about names, imports, types or classes are
   answered by symbol, and read back per file at the file's own node.
7. Positions (line, col, end_line, node_order, visit_index, ast_depth)
   are compared in the file's own rules.
8. Declare a relation cross_file only when it spans files on purpose
   and holds no node; add a comment saying why.
9. Run the pack's split test with RERAIL_SHOW_CROSSINGS=1. It must add
   nothing to split_crossings.txt or node_crossings.txt; remove any
   entry the change fixed.
