# 0208: HTML's scripts and styles, and Markdown's inline content, are guest documents

Status: built (user, 2026-11-14: "Markdown's inline content as guest documents … HTML <script>/<style>
content read as JavaScript and CSS is still open from 0199"). It closes those open items of 0199
and 0205.

## Intro

A file can hold code in another language. An HTML page holds JavaScript in its `<script>`
elements and CSS in its `<style>` elements. A Markdown file's block tree leaves each paragraph's
text as one `inline` node; its emphasis, links and code spans are in a second grammar,
tree-sitter-md's inline grammar.

The engine reads such code as a **guest document** (decision 0055). A library rule declares where
a guest stands and which grammar reads it:

```
embed(d, at, grammar, role)    // node `at` of document d holds a guest, read by `grammar`
```

The engine parses each guest's text with that grammar and places its nodes back in the host file,
so a finding in a guest has the host file's lines and columns. A rule reaches the guest's nodes
through `guest(...)`, or, where the guest's grammar is named by a kind in the rule, directly.

This decision declares HTML's and Markdown's guests and adds what they need: a grammar that no
file suffix selects (the inline grammar), and a guest text made of several stretches of the host
(a quote's `> ` left out of an inline node's text).

```
<script>let a = f(1);</script>   -> a JavaScript program at the script's raw_text
<style>p { color: red; }</style> -> a CSS program at the style's raw_text

> Some *text* and a
> [link](u)                       -> one inline guest: "Some *text* and a\n[link](u)",
                                     its two lines mapped back to their places, `> ` left out
```

## Prior work consulted

- **0055 (guest documents).** **Followed:** `embed` facts in a library's `.rr` file; the guest
  machinery parses, places and hides them. Nothing new in the evaluator.
- **0199 (lean HTML), 0205 (lean Markdown).** Both left these guests open. The host tapes do not
  change: a guest is parsed from the host's text, not from its tape.
- **tree-sitter-md's `MarkdownParser`** (the crate's `parser.rs`): it parses the inline grammar over
  each `inline` and `pipe_table_cell` node's ranges, less its named children after the first. The
  only named child an inline node has is a `block_continuation` (a quote's `> `, a list item's
  indent on a continued line). The guest text is those same ranges.
- **The HTML standard's script types.** No `type`, an empty one, or a JavaScript MIME type (and
  `module`) is a classic or module script; `importmap` and `speculationrules` are JSON. Any other type
  is a data block, and no grammar reads it.

## Decision

### HTML: `lib/html/embeds.rr`

- A `script_element` with no `type`, an empty `type`, or a JavaScript type (`module`,
  `text/javascript`, `application/javascript`, `text/ecmascript`, `application/ecmascript`,
  `text/jsx`, `text/babel`): a `javascript` guest at its `raw_text`.
- A JSON type (`application/json`, `application/ld+json`, `importmap`, `speculationrules`): a `json`
  guest.
- Any other type (`text/template`, …): no guest.
- A `style_element`: a `css` guest at its `raw_text`.

Each is a whole program (role `"program"`). The `raw_text` is a copied stretch of the host, so the
guest's nodes have the file's places.

### Markdown: `lib/markdown/embeds.rr`, and the `markdown-inline` dialect

- Each `inline` and `pipe_table_cell` node is a `markdown-inline` guest, role `"fragment"`.
- **Its text** (`guests::markdown_inline_text`): the node's bytes less its `block_continuation`
  children after the first, as tree-sitter-md gives them. With none, the text is a copied stretch.
  Otherwise it is several stretches (`Placement::Mapped`), each copied, so every guest node still
  maps to its place in the file.
- **The grammar:** tree-sitter-md 0.5.4's inline grammar, vendored at
  `native/grammars/tree-sitter-markdown/markdown-inline` (its `grammar.json` and external scanner),
  generated by the build as the block grammar is. It is a second dialect of the Markdown language,
  `markdown-inline`, tape tag 20.

### A dialect with no file suffix

`languages/*.json` let each dialect name its file suffixes, at least one. A dialect may now name
none: it is read only as a guest's grammar and never selected by a file. A language still needs one
dialect with a suffix (the registry's schema, `scripts/generate/languages/registry.ts`, and the
build's check, `build_languages.rs`).

## Results

- **`markdown_inline_guests_oracle`** (engine test, over the 800 Markdown files of 0205's corpus):
  each inline guest's tree, mapped back to the file, is compared node by node with tree-sitter-md's
  inline tree over the same ranges (`set_included_ranges`). 800 files, none differ.
- **`markdown_inline_guests_are_tree_sitter_mds_inline_trees`**: the same over a hand-written text
  with headings, a block quote over several lines, a list item, and a table.
- **`markdown_inline_content_is_a_guest_at_its_host_places`**: rules over code spans, emphasis,
  strong emphasis and a link destination, in a quote over two lines, give the host's lines and
  columns.
- **`html_scripts_and_styles_are_javascript_json_and_css_guests`**: calls in an untyped and a module
  script, a pair in a JSON script, a declaration in a style; none for `text/template`.

## Open

- **The inline grammar's tape** is tree-sitter's: no lean parser reads `markdown-inline` yet. Its
  guests are short, one a paragraph, and parsed once each by the tape cache.
- **Attributes holding code** (`onclick="…"`, `style="…"`) and Markdown's fenced code blocks by their
  info string are not guests yet. Both are a library rule each, in the same form.
