# 0095a: Run artifacts: rules first, then entries kept by what they depend on

_Numbered 0095 until 2026-11-13, when 2 decisions shared the number; the letter orders them by when each was written._

Status: proposed (2026-11-08). Number not reserved in trunk's register (0094 §9): this branch cannot push there. What
is built is named in each section; the rest is the open items listed at the end.

## Intro

Some facts only a run of the repository's own code can produce. pytest's collection is one: how many tests a
module yields depends on parametrize lists, fixtures and plugins. Rerail never runs repository code, so such facts
come from a file a CI step writes, an **artifact** (data-layer `RUN-FACTS.md`):

```text
// The policy names the artifact and the files whose change makes it stale.
.artifact "test_collection" inputs "**/*.py", "pyproject.toml"
.decl collected_total(n: number)
.input collected_total(IO=json, artifact="test_collection", path="/total")
```

CI runs the producer, `rerail-engine facts-stamp` wraps its output with a digest of the inputs, and the run reads
the stamped file. A missing, stale, failed or malformed artifact gives no rows and one `input_error`, and the rules
that read it through `!` or an aggregate are withheld, so a missing artifact is never a silent pass (O138).

Soufflé has no such thing. Its `.input` reads a file each run and trusts it: nothing says what produced the file
or whether it is current, and nothing is kept between runs. Freshness and caching are ours to design.

As built, they are too coarse to be useful outside CI:

- **One digest per artifact.** `**/*.py` covers every Python file, so any edit anywhere makes the whole
  collection stale. Locally, after the first edit, the artifact is never fresh again.
- **One copy.** The facts directory holds the latest stamp. Switching branches, or reverting an edit, loses a
  stamp that is still valid for the tree in front of it.
- **Its own walk.** The digest is computed by walking the tree and hashing every matching file, each run,
  beside phase 0's observer, which already knows each file's content (t24).

This record says when an artifact is the right tool at all (§1), what its rows are keyed by (§2), where the digest
comes from (§3), how stamps are kept (§4) and how a change reaches the findings (§5). The git facts that the same
policies need are §6: the same rule of keys applies to them.

## Decision

### 1. Rules first: an artifact only for what no rule can derive

An artifact is the last resort. It costs a run of the producer, and it is right only where that run is.

**Test collection is derivable.** The t13 spike modelled pytest's collection from the source and compared it with
real `--collect-only` runs over the data layer:

| Tree | pytest | Static model | Files exact |
|---|---:|---:|---:|
| the 9,010-file corpus | 14,449 | 13,610 (−5.8%) | 1,131 of 1,143 |
| data-layer main | 15,361 | 14,454 (−5.9%) | not recorded |

Without the files whose case lists are computed at import, the model is within 0.3% on both trees. So
`test-budget` counts tests with rules (`python/pytest-collect.rr`, t13 §7), and the `test_collection` artifact
leaves its primary path.

**The one computed list is disabled.** `conform/l5250_matching/test_phase1_case_matrix.py` yields 819 tests from
`_case_matrix_module().PHASE1_MATCH_CASE_MATRIX.enumerate_all()`, a method of an object built when the module is
imported. No rule can count it without running it. The policy names such files, and a named file is not counted:

```text
// Files whose tests are generated by running code: not counted, and reported once each, so the list is visible.
.decl collect_disabled(path: symbol)
collect_disabled("conform/l5250_matching/test_phase1_case_matrix.py").
```

The ceiling applies to the rest, and the check reports each disabled file as a finding of its own, so a disabled
file never hides growth silently. The other gaps t13 names are smaller: a list built by `append` in loops
(66 tests against 13), one built by introspection (73 against 5), and an indexed tuple (18 against 8). They are
lengths a rule can learn (t13 §7, step 4), not reasons for an artifact.

Where a check truly needs a run (behaviour probes, a registry built at import), the rest of this record applies.

### 2. An artifact's rows are entries, each keyed by its own inputs

An artifact is a set of **entries**. Each entry has a key, the files it depends on, and its data:

```text
// Each test module is an entry. Its inputs are the module itself, plus the files every entry shares.
.artifact "probe_results" entries "scripts/probes/*.py" inputs "conftest.py", "pyproject.toml"
```

```json
{"format": "rerail.facts/v2", "artifact": "probe_results",
 "entries": [{"key": "scripts/probes/a.py", "inputs": "sha256:…", "status": "ok", "data": {…}}, …]}
```

- An entry's digest is over its key file and the shared inputs. Editing one probe file makes that one entry
  stale; editing a shared input makes every entry stale. A v1 artifact is one entry.
- Each entry has its own status, so one failed probe is one failed entry.
- The rows of an entry carry its key, so the places a stale entry reaches are exactly its rows' places: the
  Unknown places of FINDINGS-LAYER §2 shrink from the artifact's to the entry's.
- **Imports are not inputs yet.** An entry whose module imports another file goes stale only through the shared
  globs. The exact input set is the entry's import closure, which phase 1's resolution already derives as facts
  (`module_edge`). Using it makes freshness a derived fact: the digest is a join over the closure. That is the
  target, after P0's module graph is a phase output (t24, "not built").

### 3. Digests come from phase 0, never from a walk of their own

The digest of an entry is over `(path, content source)` of its inputs, where the content source is phase 0's
sha256 of the file's bytes (t23 §5). The observer knows it from a `stat` for an unchanged file, and from a Git blob
alias for a clean one (t24): a warm run computes every digest without reading a file. The stamp step uses the same
function, so CI and a local run agree.

- **sha256 of the bytes, not the blob id.** Filters, line endings and `working-tree-encoding` make a blob differ
  from the bytes on disk (t23 §3a); the content source is what the run reads. Today's stamps hash git blob ids
  (`inputs.rs`, `blob_id`); the format version moves to v2 with the change.
- A file that is not a document (`pyproject.toml`) is observed like any read: the observer answers for any path.

### 4. Stamps are kept by digest, not by name

Stamped entries live in the store, keyed by `(artifact, key, digest)`. A run looks up each entry by its current
digest. Any stamp with that digest is valid, whenever and wherever it was made:

- **Branches and reverts.** A tree that returns to an earlier state finds the entries stamped then.
- **Partial freshness.** A working tree with three edited test files uses CI's stamps for the other entries, and
  has three stale ones.
- **Import, not fetch.** The facts directory becomes an import location: a run absorbs any stamped file it finds
  there into the store. The run never uses the network (t21 §7); getting CI's stamps onto a laptop is a separate
  command's job.
- **Retention.** Least recently used entries go first, within the disk budget. An entry used by the current tree is
  never removed.

### 5. A change is a delta: rows out, stored rows in, or Unknown

Artifact rows are phase 0 facts, like a document's. When an input's content changes, each entry's digest is
derived again. An entry whose digest moved deletes its rows, and inserts the stamp stored under its new digest if
there is one. Otherwise it gives `input_error("artifact:NAME", "stale", …)`, its readers under `!` are withheld,
and its places are Unknown. Downstream phases see an ordinary delta (0090); an entry whose digest is unchanged
changes nothing.

**Built.** Phase 0's whole-run cutoff (`reuse.rs`) keeps a run's outputs when every read is as it was. It recorded
documents and resolution reads only, so a run whose `.input` file, artifact or base file changed was kept with
stale outputs (reproduced: `allow.txt` edited, run kept). Every reader's read is now in the record (`input`,
`input_dir`, `artifact`, `base`) and is checked again (`inputs::still`, test in `corpus::reuse`).

### 6. Git facts: object ids are immutable, refs are phase 0's

The policies need these from Git:

| Fact | Used by | Answered by | State |
|---|---|---|---|
| `@git_commit(sha)` | `architecture_rule_docs`: a commit a document cites exists | the object store, by id | built |
| `@git_has(sha, path)` | the same: a path at a cited commit | the commit's tree | built |
| `@git_tracked(path)` | `markdown_docs`: tracked, as against on disk | the index phase 0 reads | built |
| `git_rev("head", sha)` | `at="base"` comparisons | `HEAD`, recorded for the cutoff | built |
| `git_rev("base", sha)` | burn-down lists that may only shrink | the merge base of `HEAD` and the base ref | built |
| a file at the base | `at="base"` inputs | the merge base's tree | built (`--base REV`) |
| content digests | artifact freshness (§3) | phase 0's content sources and blob aliases | built in phase 0 |

**Inline calls, not a subprocess, not enumerations.** `@git_commit` and `@git_has` are functors, evaluated per
row with their arguments bound, like `@ed25519_ok` (`strings/git.rs`). Each is a lookup in gix's pack indexes, in
process; the repository is opened once per run. No check needs "every commit" or "every path at a commit", so
nothing is enumerated. `git_tracked` should be a functor too, `@git_tracked(path)`, over the index phase 0 has
already loaded: rules ask about the paths a document links, not the whole index.

**Why no invalidation is needed for most of it.** An object id names fixed content. A commit's existence, its
tree and a blob's bytes never change, so those answers are kept for the process and never checked again. Only
names move: `HEAD`, the base reference and the index. Those are phase 0's observed reads, so a moved `HEAD` is a
changed read like an edited file. The merge base is then derived from the two commit ids and kept under them.

The merge base uses gix's `revision` feature (`merge_base`), and `at="base"` reads at it. A prefix that later becomes ambiguous, as new objects arrive, is the one answer an id does
not pin. A check should cite full ids; an abbreviated one is accepted, and gives 0 once ambiguous.

## What the prior work says

- **Soufflé**: `.input` reads a file each run, with no producer, freshness or cache. *Departs*: artifacts are
  stamped, checked and kept.
- **RUN-FACTS.md §2–§5 and FINDINGS-LAYER §2**: the envelope, the states and Unknown places. *Kept*, refined to
  entries (§2).
- **t13**: collection is derivable, 1,131 of 1,143 files exact. *The ground of §1.*
- **t23 §3–§5, t24**: phase 0's providers, content sources and blob aliases; the whole-run cutoff. *Adopted* for
  §3 and §5, with the cutoff's missing reads fixed.
- **Decision 0092 §1–§2**: a fact's key is its inputs' content; the leaves are content digests. *Agrees*: an
  entry's digest is its leaves, and an unchanged digest is the cutoff.
- **Decision 0090**: changes propagate as deltas. *Agrees* (§5).
- **Decision 0064**: recording reads per row cost +60%. *Respected*: artifact reads are per entry, hundreds at
  most, as phase 0's file reads are (t23 §4).
- **ast-index-spike history §2.16(d)**: key by what a thing is a function of. *Agrees*: an entry by its inputs, a
  Git answer by the object id.
- **Lessons ledger #14**: each file owns its rows. *Agrees*: each entry owns its rows.
