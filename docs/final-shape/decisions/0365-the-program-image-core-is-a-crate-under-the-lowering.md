# 0365: The program image's core is a crate under the lowering

**Status:** building (the user's choice, 2026-11-17).

## Intro

Decision 0281's step 7b has the lowering write each clause's rules through the program image's `Builder` as the tape
walk reads them, so a module's program is a version from the start, not a `front::Program` encoded afterwards. The
lowering (`rr::lower`) is compiled in `rerail-rr`; the image (`Version`, `Builder`) in `rerail-logic`, which depends
on `rerail-rr`. The lowering cannot name the builder.

Asked how the lowering should reach it (move the image's core down, a rule sink trait in `rerail-rr`, or the lowering
moved up), the user chose: "move it down into a new crate under rerail-rr".

## Decision

1. **A crate `rerail-program-image` between `rerail-rr-syntax` and `rerail-rr`** holds the image's core: the module
   root (`Image`, the writer, `encode`, `decode`, `about_of`), `about`, `build`, `csr`, `encoder`, `extents`,
   `grouped`, `handles`, `show`, `strings`, `tree`, `version`, and `program_facts`, which the about rows are. It reads
   only the AST (`front::ast`, `front::name`) and the profiler. `rerail-rr` depends on it, so the lowering writes
   versions.
2. **The pass manager, the passes and the analyses stay in `rerail-logic`** (`manager`, `passes`, `analyses`, the
   image's tests): they read the planner. `rerail-logic`'s `program_image` is the core's, globbed, with them added,
   as the crate split mounts a module two crates share (`tools/cratify/mounts.py`).
3. **What tied the core upward is cut, not moved:**
   - a version's analyses: `Version` keeps a type-erased slot, which the manager fills with its `Store` on first use
     (`manager::analyses`), in place of a `Store` field of the manager's type;
   - `Version::part` and `Version::part_rules`, which run passes: a trait beside the passes (`passes::Parts`);
   - `front::operator`, which `program_facts` reads: in `front::ast`, beside the AST, with the parser's punctuation;
   - `program_facts`' tests that read text through `rr::parse`: moved to the image's tests, which stay above.
4. **The files stay where they are**: the new crate mounts them in place (the crate split's `proposals/crate-split/in-place-plan.md`), its lib.rs
   generated by `mounts.py` from `crate-map.tsv`.

## Log

- **Step 1** (11ea23e99): the ties upward cut in place (item 3).
- **Step 2**: the crate (`native/crates/program_image`), mounting the core's files in place; `rerail-logic`'s
  `logic.rs` mounts `program_image` as the core's glob with `analyses`, `manager` and `passes` added, and takes
  `program_facts` from the crate; `rerail-rr` depends on it. What the step found and how it was resolved:
  - the core named `front`'s items through `front` (in `rerail-rr`); they are all `front::ast`'s and
    `front::name`'s, so the core spells them so, and the crate's `front` is those two;
  - `program_facts::document`, which prints facts as `.rr` (`rr::print`), moved to `program_text`, as did its
    test's call;
  - the core's restricted items (`pub(super)`, `pub(crate)`, `pub(in …)`, 75) are `pub`: the modules that read them
    (the manager, the passes, the analyses, the planner) are now in another crate;
  - `mounts.py` cannot regenerate the mounts as a whole any more (`cratify tree` walks the engine as already
    split), so the crate's mounts are written by hand in its shape, and the map (`crate-map.tsv`, `crate_map.py`'s
    DAG, `mounts.py`'s DIRS) records the crate.
- **Step 3a**: in a seeded scope the module's rules leave `link` as the walk wrote them, so the walk can write them
  as a version. The seeds number no helpers and hold no `helper_once` keys, so link's renames and merges never
  fire there; the one rename that could (a Python candidates relation named as a seeds' native) is avoided by
  the walk, which now skips the natives' names as well as the declarations'. `link` says whether it edited the
  rules, and `link_seeded_parts` refuses a module it did. Tests: 489 of 490 lowering, link and scope tests (Q81
  fails, as before); ep2's 317 policies over 10 files, fresh stores, debug: 0 rows.
- **Step 3b**: a text's own rules are written as a version in the walk. The lowerer writes every rule through
  `Lowerer::write`, to `Out::Tree` (`prog.rules`: a module kept as parts, the unseeded link, `lower`) or
  `Out::Version` (`Written`: the builder, and what the walk reads back of what it wrote: a count for the `must`/`may`
  rules' places, a 128-bit content hash of each rule for the demands written once, and the rules of the heads a
  `.shape` names). `lower_module_seeded_written` writes so; `link_seeded_parts` hands the `Written` on, and
  `rr::own_version` sets the module's header on it (`Builder::set_program_header`, which
  `of_program_less_maintenance` now uses too) for `AppendModule`. The rules a statement wrote before the clauses go
  first. `Builder` is `Clone` (the lowerer is). The `rerail-rr` mounts re-export the core.
  - Found on ep2: `link` keyed each `helper_once` helper by its rules, which a written module's header does not
    hold, so two aggregates of one head merged. A written module's helpers are taken as they are, as a seeded link
    takes them anyway (its seeds hold no helpers, and the walk wrote each once).
  - Checks: a debug build lowers each text's tree too and asserts the two versions are one program
    (`lowered_own`); `a_texts_rules_are_written_as_a_version_in_its_walk` (two aggregates of two literals: fails with
    the merge put back). Tests: 550 of 551 lowering, link, scope, image and on-the-version tests (Q81); ep2's 317
    policies over 10 files, fresh stores, debug: 0 rows, every text's walk version the tree's.
- **Next**: the module images (`ModuleParts`) and the seeds read a module's rules as a tree, so `Out::Tree` stays
  until a library module is written as a version too; then `front::Program`'s rules go.

## Consequences

- An edit to the image's core recompiles `rerail-rr` and everything above it; an edit to the manager or a pass does
  not.
- The blocks port (0281, last) replaces this crate's insides; its `Version` interface is the one the lowering writes
  through.
