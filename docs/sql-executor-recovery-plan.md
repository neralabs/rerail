## Root causes and implementation

1. **Projection binding and ownership.** Snapshot binding installs all core fact modules.
   Lowering also emits `kind` and node-only `docof` projection views, so both original CPython programs fail before execution.
   Namespace compiler-generated views privately and rebind their checked references. Keep public core fact tables available to SQL.
   Protect user tables from accidental replacement and cover the original programs without source edits.

2. **Exact values and fact types.** Integer JSON values above `2^53 - 1` lose precision in JavaScript.
   Return tagged decimal integers outside the safe range and accept that tag in parameters and fact rows.
   Accept string fact values as interned symbols, with explicit column types where domains need checking.
   Add dialect-aware kind/field decoding functions; grammar IDs are not symbol atoms.

3. **Static join order and repeated indexes.** Emitted `CROSS JOIN` clauses freeze plans before derived cardinalities exist.
   Two constant-propagation steps consume about 2.8 billion VM steps before constraining the join through `binval`.
   Allow SQLite to order mixed derived joins through the typed query representation.
   Preserve base-source plans and single-delta anchors so recursive rules retain native probes.
   Derive reusable indexes from checked join constraints and expose an index setup API for ad hoc queries.
   Measure whether this resolves the gap before adding expensive statistics scans or a second scheduling architecture.

4. **Delta folding.** The 512-vertex chain spends 96.6% of its VM work in accumulated-state subtraction with `EXCEPT`.
   Replace ordinary set subtraction with indexed probes over new candidates.
   Preserve the distinct update rules for lattices and verify cyclic graphs and stratified readers.
   Require near-quadratic VM scaling on the chain, rather than its measured cubic scaling.

5. **Relation and aggregate representation.** Boolean relations have zero logical columns, but SQLite needs a physical column.
   Represent Boolean presence with one private sentinel column and retain the logical arity in the API contract.
   Permit safe aggregate-only rules without requiring an artificial positive atom.
   Cover counts over empty inputs and reject unbound head variables.

6. **Lattice execution.** The session accepts only flat lattices.
   Add SQL folds for built-in `min` and `max`, including improved-value deltas and zero-key aggregates.
   Keep flat conflict semantics intact. Custom joins require an explicit registered join function and algebraic contract.
   Do not treat arbitrary function names as valid lattice implementations without registration.

7. **Session lifecycle and execution limits.** Repeated programs collide with their old outputs, and all rebinding clears all results.
   Track ownership and dependency edges. Replace a program's outputs atomically and invalidate its dependent programs.
   Preserve independent outputs when one input changes. Expose explicit reset and reusable execution limits.
   Enforce deadlines and VM-work budgets through SQLite progress callbacks, including expensive single statements.
   Remove callbacks before rollback and leave the session usable after interruption.

8. **Corpus SQL table management.** The call workload performs 545 table renames and 1,311 temporary-table creations.
   Renames consume approximately 111 ms of 344 ms in coarse SQLite statement timings.
   Inspect schema ownership and reuse candidate/delta tables where their schema is unchanged.
   Verify paired SQL/native output parity and measure the resulting statement count.

## Implementation results

The implementation covers the eight steps above.
Projection views receive private names only when they collide with bound facts; ordinary output views keep their public names.
Safe scalar rules include global aggregates and Boolean negation without an artificial seed relation.
Min/max folds track improved values and per-key widening counts. The `top` keyword follows the value's lattice through aliases.
Arithmetic transfers preserve top, including min's negative sentinel. Registered custom SQL joins receive the same fold protocol.
The follow-up [shared SQL and updates plan](sql-unification-and-updates-plan.md) replaces the older corpus SQL execution loop with the shared wave kernel.
Both SQL entry points now use its lattice folds.

Output replacement runs inside a savepoint. Failure restores the previous outputs and ownership metadata.
Input rebinding invalidates dependent programs transitively and preserves independent results.
`reset`, `createIndex`, `setLimits`, and `registerLattice` are available through the native API and TypeScript interface.
Request files accept execution limits and result indexes.
Unsafe JavaScript integers use decimal tags in query rows, parameters, and fact bindings.
String facts use batched atom interning. Optional column types check values and rule input declarations.

The first implementation allowed every join to reorder. The wrapper benchmark exposed repeated scans of its full render relation.
The final policy keeps native source plans and single-delta anchors, while SQLite orders mixed derived joins.
Indexes on pinned delta anchors are omitted when a native probe already serves their join.
This avoids the measured wrapper regression without restoring the constant-propagation Cartesian product.

The final optimized measurements use the same fixtures and benchmark requests, except resolved feature probes now require success.
CPU time remains sensitive to shared-machine load. VM counts provide the clearest algorithmic comparison.

Reachability now grows about fourfold in VM work when the vertex count doubles, versus about eightfold before.
At 1,024 vertices it uses approximately 35 times fewer VM steps.
The matched CPython direct-node variant uses approximately 249 times fewer steps and 90 times less CPU.
The original CPython type program now runs unchanged in 834 ms; it previously failed during binding.
Its projection views still cost more than the direct-node variant: 56.4 million versus 15.6 million VM steps.

The corpus SQL call workload fell from 556 to 430 ms CPU.
Its SQL/native CPU ratio fell from 2.09 to 1.36 under equal cross-file bounds.
Profiled table renames fell from 545 to 4; remaining renames materialize views outside the recursive delta loop.
All paired output CSV files remain identical.

These changes have costs. Reusable indexes add maintenance work when results are written.
The one-off derived join uses about 7% more VM steps, while repeated SQL reads avoid rebuilding their index.
Typed JSON fact binding adds parsing and conversion work: the numeric aggregation input's bind CPU rose from 14.6 to 33.6 ms.
Its peak resident memory rose from 45.1 to 56.1 MB.
An unchanged direct-SQL aggregation control also rose from 16.0 to 28.1 ms CPU, so timing differences include machine variability.
The fast aggregation workload's VM count remains effectively unchanged, and the wrapper's count falls by about 18%.

Remaining boundaries are explicit:

- AST matching and source parsing remain native producers. SQL consumes their facts.
- Custom joins require deterministic registered functions and a caller-supplied algebraic contract.
- Deadlines cannot interrupt Rust compilation or a native function before it returns control to SQLite.
- `applyChanges` maintains positive results through insertions and recursive deletions. Eligible scalar aggregates and negation use retained support.
  Lattice joins, tree walks, and unsupported correlations refresh affected strata.
- Row updates currently require explicit `bindRelation` facts. Snapshot replacement still invalidates generated results.
- Full column statistics and adaptive planning remain opportunities, particularly for compiler projection views.
- Typed JSON input and retained indexes have measured ingestion and write costs. They need separate tuning for bulk ingestion workloads.
