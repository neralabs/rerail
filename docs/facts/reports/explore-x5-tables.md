Counts are load-independent (dead code, whole plan): 52.5M rows out, 18.9M fixpoint derivations, 20.8M probes, 20.3M index rows.

Why this counts as the design's per-edit cost:
- In design (e) only the reference graph and the exports persist. Every clause stage is recomputed per edit from those tables.
- Key-scoping is exact only where a changed key bounds the changed output rows. For dead code it does not:
  - `reachable` is a fixpoint from all roots over `reach_edges` (9.0M rows).
  - `annotation_reachable` and `high_confidence` read the whole of it.
  - A deletion can un-reach an unbounded set of symbols.
- So the plan runs from scratch: 928 / 1,050 edits (P3a's `d1-skip-offline.json`) cost ≥ 7.6 s each. That holds even with the linker free and `exported-families` run in parallel.

Second engine checked: the facts-a columnar engine, on the oracle corpus (9,010 files, 3,110 in scope).
- How: `facts-a repo` runs repository partitions on this engine. I added `FACTS_X5_EDGES`, which reads `reference_edges` from native's ground truth instead of refusing `references`. The run is `/tmp/x5/repo-dc`.
- `exported-families`: the repository partition took **326.9 s**. `base_edges` alone took 324.0 s: `b.id = coalesce(<three correlated scalar subqueries>)` is planned as a nested loop, with 257.9M subquery runs. The other stages took 2.89 s, about the same as M2's CPU time.
- Dead code does not compile on this engine: `unreachable-internal-symbols/raw_modules: projection file.module`. The engine has no membership-dependent `module_of`.
- So the facts-a engine is not faster than M2's executor at repository scale.

Best case, not part of design (e): suppose every non-recursive stage were kept as a table and maintained per changed key. That is a materialised-view engine, i.e. M1 with tables. The per-edit floor would then be the global fixpoints: `reachable` + `annotation_reachable` + `resolved_names` + `high_confidence` ≈ 5.6 s wall, ≈ 3.2 s CPU. That is still 6× over the 500 ms gate. Intra-plan parallelism is the only remaining lever (8.6 CPU-s / 8 cores ≈ 1.1 s), and none of the executors has it [INFERENCE].

## 2. The linker's incremental rule (derived from `facts/src/front/{module_path,reference_edges}.sql`)

It is exact by the read-set argument below. I found no counterexample. It was not implemented, because the kill came from § 1.

The linker's stages fall into four classes by what their rows depend on:

| Class | Stages | Row depends on | Maintenance per edit of path `p` |
|---|---|---|---|
| **P**: path set | `in_scope`, `package_dir`, `file_name`, `package_climb`, `package_root`, `module_rel`, `module_name_part`, `module_path`, `module_segment`, `module_text`, `module_of`, `module_prefix`, `file_variant`, `path_refusal` | the path set (and the constant scope globs) | Unchanged by a content edit. When a path is added or removed: that path's rows. If the path is an `__init__.py` in scope, every in-scope path under its directory is recomputed, because `package_climb` reads `package_dir` only at the ancestors of a file's directory. |
| **C**: path-partitioned | `raw_name`, `name_sub`, `refused_path`, `linked_file`, `s_def`, `s_edge`, `s_alias`, `s_opaque`, `s_module`, `s_open`, `s_base_slot`, `last_class_def`, `s_super`, `path_alt`, `spelling` | `cgn_*(p)` and the P-rows of `p` only. Every join is on path equality. | Delete `p`'s rows, insert the new ones. Shareable across worktrees as (path, content) blocks, like the exports. |
| **G**: keyed global | Base tables: `by_name`, `aliases`, `opaque`, `modules`, `supers`, `marker_class`, and the class defs grouped by short name. Derived keyed: `class_key`, `method_def`, `own_name`, `reference_class`, `uniform_alias`, `named_prefix`, `imported_alias`, `prefix_alias`, `base_target`, `base_class`, `bases`, `subclass`, `class_root`, `field_alias`, `type_key`, `type_unique` | A union of C-contributions with multiplicities (base tables). The derived ones read base keys either at the same key, or at keys computed from the row (alias targets, `module.<kind>.short`, `cls.attr`). | Apply `p`'s ΔC with counts. K₀ = keys whose distinct rows changed. Propagate K through each derived view's key map, using reverse indexes for target-keyed reads (`aliases` by target, `supers` by target). |
| **R**: recursive keyed | `order_dist`/`reference_order` (per root), `fq_class` (per name), `class_of_walk`/`class_of` (per start), `link_reach` (demand), `link_result` (per name) | the keys read along the recursion | Affected outputs = forward closure of the changed keys through the recursion's edges, old ∪ new. Recompute those outputs, seeded from the unaffected boundary. Unaffected outputs cannot read affected ones (definition of the closure), so this holds with `min(k)`/`min(dist, seq)` too. |

The per-name core:
- `link_form`, `link_plain`, `plain_prefix`, `prefix_match`, `prefix_first`, `field_*`, `type_demand`, `method_*`, `compose_*`, `link_term` and `link_kid` are all functions of a name (or of a demand key `(cls, field)`/`(root, attr, skip)`) over G and R.
- For a name `n`, R(n) is the set of keys its evaluation probes. That includes absent keys: every `EXISTS`/`NOT EXISTS`, and every prefix that the longest-prefix scans test (each proper prefix is probed, longest first, until the first hit).
- Rule: after an edit with changed keys K, the names whose result can change are N = {n : R(n) ∩ K ≠ ∅}, closed upward through `link_kid` (parents of changed kids).
- Why this is exact: a deterministic evaluation whose reads are all unchanged returns the same result. The first read that differs is a probe of a key in K, and that key is in the old R(n).

`linked_edges` rows to recompute after an edit of `p`:
- (a) the edges whose source path is `p`;
- (b) the edges whose name is in N′ = {n ∈ N : `link_result(n)` changed};
- (c) the edges whose target path is `p`. `td` re-reads `s_def(p, idx)`: a def whose start moves keeps its `by_name` row, so (c) is not covered by K.

`linker_refusal` is keyed by path or key per arm, and each arm is recomputed for its affected keys.

Fallbacks to full recompute, and why each stays exact:
1. `reference_graph_incomplete` is a global count over open summaries. When it flips, every row of `reference_edges` changes (empty plus a refusal, or restored). The fallback re-joins `linked_edges` entirely. `link_result` is not recomputed.
2. Adding or removing an `__init__.py`: class P/C is recomputed for the directory's subtree (scoped, not global). Every key those files contribute then enters K, so the propagation can be large.
3. Demand (`link_reach`) is only grown, never shrunk:
   - No stage aggregates over the demand set, so a superset of names changes no output.
   - The `d < 19` cut is the SQL's own claim that a name 19 or more hops in cannot yield a definition. Results per demanded name are therefore independent of demand.
   - Shrinking demand exactly needs DRed or a periodic full recompute. That is garbage collection, a memory concern, not a correctness one.

What the rule requires as state: R(n) as an inverted index (key → names), with one entry per probe. The per-worktree sizes (rows out of the views, worktree 1) show the order of magnitude:
- `link_reach` 2.82M names, `link_kid` 2.25M, `prefix_match` 0.82M, `link_plain` 1.16M, `field_candidate` 0.88M;
- so ≈ 10M+ probe entries;
- plus `link_kid` for the upward closure and `link_result` (0.55M).

Against the invariants:
- I8: hand-writing this rule per stage breaks I8.
- I3: generating it needs a generic read-set or demand analysis over `norm::Graph`. That analysis must take its key functions from the plan, never from stage names, or it breaks I3. No such analysis exists.
