# Jeremy's SQL executor at `b3e97cd47`: is "within 2% of native" substantiated?

Checkout: `/tmp/jb-spikes3` (branch `jeremy/sql-capture-demand-spikes`, tip `b3e97cd47`, 2026-10-26). In this report, "JNL" means `docs/sql-matcher-fragment-transition.md`, "PLAN" means `docs/sql-structural-execution-plan.md`, "BI" means `docs/sql-matcher-batch-implementation.md`, and `NS/` means `native/src/code_rule_dsl/`. Line numbers are at the tip. "Measured" means a benchmark JSON or a local run. "Projected" means one of his targets or plans. [INFERENCE] marks my own reasoning.

**Bottom line.** The 2% figure is real, but it measures something else. It comes from one benchmark JSON at commit `c17d2e474` (2026-10-25): cold CPU ratio **1.021** on the shipped **Python** pack (146 per-file AST clauses) over 5,725 files. In that build, SQLite hosted the native matcher in a virtual table, and 95% of matching CPU ran inside native code. That code is no longer at the tip. The tip executor is Jeremy's own **rejected** build at **1.585×** native. I reproduced both locally: c17 at **1.029×** and the tip at **1.75×**, both with exact finding parity.

## 2. Architecture as built

**Selection.** SQL is opt-in. `Engine` defaults to `Native`, and a workspace selects SQL with `engine:"sql"` (`NS/eval/query.rs:467-471`; `NS/workspace/sql.rs:40-55`). There is one SQL path: the older frame compiler remains for historical tests only (`NS/sql/mod.rs:1-4`; JNL:1573).

**Per job.**
1. `run_jobs` splits the files into partitions of about 4 MiB of source: 23 partitions for this corpus. They run on 4 workers (`NS/workspace/evaluate.rs:197-243`; `lib.rs:93`).
2. Per file, native code reads, parses to a `TapeDoc`, and selects anchor roots.
3. Per partition, one prepared statement runs on a pooled **in-memory** SQLite connection (`NS/sql/engine.rs:289`). The SQLite build is bundled **3.53.2** via rusqlite 0.40.2 (`native/Cargo.toml:49`; `Cargo.lock:1888-1890`).

**Per rule.** `Template::compile` splits each clause (`NS/sql/engine/planning.rs:13-50`):
- If the whole matcher lowers to a structural `Predicate`, the clause is SQL-only.
- If the matcher is a top-level `all`, the lowerable terms become a SQL prefilter and the remainder runs natively.
- Otherwise, including every `each` clause, the whole matcher runs natively.

The measured split is **129 native-only, 14 mixed, 3 SQL-only** (`docs/sql-matcher-batch-optimization.md:18`).

**Virtual tables**, registered in `Session::new` (`NS/sql/engine.rs:289-354`):

| vtab or function | Exposes | Cite |
|---|---|---|
| `node` | Every tape node of the batch, read in place: `file,id,last,parent,kind,field,…,prev,next,start,end,…` | `NS/sql/nodes.rs:522` |
| `candidates_i`, `candidate_files_i` | A clause's root domain, filtered by file or node | `NS/sql/fragments/candidates.rs:3-19` |
| `demand_i(...)` and `batch_demands(...)` aggregates | Build immutable demand in Rust; only an `i64` handle crosses SQL | `NS/sql/fragments/demand.rs:47-72` |
| `matcher_batch_k` | Native outputs `(clause,file,node,truth,ordinal,c0..cN)`. `best_index` accepts only `demand = handle`. One `filter` call runs the whole native batch | `NS/sql/fragments/batch.rs:129-169` |

**Generated SQL.** The emitted statement has this shape (`planning.rs:246-263`):

`SELECT … FROM matcher_batch_k WHERE demand=(SELECT batch_demands(clause,handle) FROM (<per-clause candidate arms> UNION ALL …)) AND (truth=1 OR truth<0)`

**Inside that single `filter` call:**
- Files are tiled 16 at a time (`batch.rs:283`).
- `wave.rs` handles admission: numeric `(program, doc, preorder)` lanes, with kind, regex, navigation and closed-utility kernels.
- `cohort::Bank` handles everything else: capture frames, ordered alternatives, utilities, `each`, and semantic and Python-resolution projections (`NS/sql/fragments/cohorts.rs:94,146` → `NS/matcher/cohort.rs:1765`).

SQL receives completed rows only. The doc says no matcher instruction crosses back into SQL (JNL:49-51, 116).

**What c17 ran (the 2% build).** One `matcher_N` vtab per clause, which called the scalar native matcher once per root (BI:10-12; `docs/sql-matcher-batch-optimization.md:12-14`). There were 2 statements of 26 KB (`sql-matcher-fragment-integration.sql`).

**Where matching CPU goes:**
- At c17, 79.50 of 83.56 s of matching CPU was inside native boundaries.
- At the tip it is 154.4 of 159.8 s, or **96.6%** (cohort JSON `nativeBoundaryCpuNs`).

SQLite executes 25.2 M VM instructions per job (same JSON).

**Caches.**
- A compile cache keyed by `(grammar source digest, VERSION=3, each)`, with 1,024 entries (`engine.rs:33-37,61`).
- Statements prepared once per session and re-prepared only if a statistics decision changes (`engine.rs:352-354`).

## 3. Set semantics in practice

**The decision.**
- JNL:186-188 (2026-10-25): "Findings form a set. Budget exhaustion means `Unknown` for the affected rule and file. Exact work charges and witness order remain diagnostic controls, not requirements."
- PLAN §2 (:37-74) formalises it as `finding(rule, code, path, line…)` plus `coverage(rule, doc, Complete|Unknown)`.
- The governing "findings contract" lives in a sibling worktree. PLAN itself says it "remain[s] proposed" (PLAN:23-29).
- PLAN:60-64 warns that "finding-set equality alone does not prove that every legacy choice can become an unordered union".

**What the tip actually does.** Nothing is relaxed in execution. Order-sensitive constructs still run in native code. The set definition is used only by the **gate**: the finding key is `[ruleId, code, path, startLine]` (`fragment_integration.rs:113-120`). The catalog gate is stricter and compares raw matches and captures across 87,162 rule/file pairs.

| Construct | At the tip | Differs from native? |
|---|---|---|
| First match, ordered `any`/`all`, ordered searches | Inside the cohort, ordered. Programs that need fill order are serialised per owner (`cohort.rs:850-852,1855-1860`; JNL:204) | No |
| `each` / enumeration | Whole matcher runs native (`planning.rs:20-48`). Native exclusion plus rematch from the original inputs (`cohorts.rs:~290-352`; JNL:196-198) | No |
| Witness and capture choice | From the native env; catalog compares captures exactly | No (unordered only "by contract") |
| Publication order | Stable sort per file by root (`engine.rs:577-582`) | Order only |
| Logical unknown vs resource failure | Distinct: `truth==2` vs tagged failure rows mapped to `Unknown::{Deadline,Limit}`, file rows cleared (`engine.rs:489-503`) | By design |

**Refusals.** No production compile refusal remains: `ProgramCompiler::clause` always returns `Ok` (`engine.rs:57-85`). Live runtime stops:
- 100 matching executions per job (`workspace/sql.rs`; JNL:293, 323);
- 1 M requests or 128 MiB per demand (`fragments/demand.rs:128`);
- `MAX_UTIL_DEPTH` 256 (`matcher/util.rs:9`).

The legacy lowerer's refusals in `sql/lower*.rs` are test-only.

**Budgets.**
- Allowances are carried as native per-owner limits `(max_visited_nodes, per-node)` (`engine.rs:138-141`; `cohort_host.rs:137-153`).
- The wave prefilter charges proven work. When the work is incomplete or over budget, the file is replayed through the cohort (`batch.rs:~515-528`; JNL:608).
- **None of this is exercised in any headline run.** Every run uses `unbounded-work`, every JSON has `failures: []`, and `waveResourceReplays` is 0.
- Budget parity is covered only by unit tests (`NS/sql/engine/tests.rs:161-215`; `NS/sql/tests/recursion.rs:422-671`).

**Results that can differ from native by design** (his notes):
1. Exhaustion becomes `Unknown` per rule and file, with provisional rows discarded (JNL:187; PLAN:71-72).
2. Work charges and witness order are not requirements (JNL:188; PLAN:46).
3. The attempted-witness metric after exhaustion: native 1, SQL 0 (JNL:362-365).
4. No exact accounting is claimed across separately executed fragments (JNL:59-63).
5. Cache residency is observable: cold-false utility replay can omit incidental captures. This "need[s] a separate semantic review" (JNL:1508-1515).
6. The planned migration may change finding keys, to be recorded in a "semantic-difference ledger". The ledger does not exist yet (PLAN:306, 384).

## 9. Verdict

The claim is literally true of one artefact and misleading as a description of the branch.

**What the 2% is.** "Within 2% of native" is `c17d2e474`'s single-run **1.021×** CPU on the Python pack. I reproduced it at **1.022-1.035×** with exact finding parity. In that build, SQLite only transported demand and published rows around the unchanged native matcher, which consumed 95% of matching CPU. The number measures the **overhead of hosting native matching behind a virtual table**, not the speed of a SQL executor. The "set semantics" are a gate definition and a proposal (PLAN §2), not a change in execution. Budgets were lifted in every run, and 129 of 146 clauses had no SQL component.

**What the tip is.** The executor at the tip ("SQL driving higher-level matches" through `cohort.rs`) is **1.585×** native by his own rejected qualification and **1.67-1.85×** in my reruns.

**What his implementation has that ours lacks.**
1. Complete **execution** (not lowering) of the whole Python DSL with exact raw-match and capture parity on 146/146 clauses, including recursion, ordered capture choices, `each`, parse and resolution. It runs natively inside `cohort.rs`. His earlier pure-SQL lowering reached 146/146 on fixtures only, then was retired.
2. A statistics hook: fts5vocab kind counts choose anchors, though unused in the headline runs.
3. A native budget-replay path in which work charges are preserved within fragments. It is unit-tested only.

**What ours has that his lacks:**
- an independent executor that is **faster** than native (ours: 90 s vs 393 s, 23%, parity 173/173);
- content-addressed memoisation by plan digest (`INVARIANTS.md` I7);
- repository clauses and the linker on an incremental dataflow, exact (ours: 0.5 ms p50 per cross-file edit, 2.1 GB for 40 worktrees);
- any multi-worktree, cross-file or incremental measurement at all.

**Comparability.** The two figures are not comparable. Ours is batch 6: data-layer policies dominated by SQL stages, on 9,010 files at `2b1504adc`. There the engine replaces native's 393 s of mostly SQLite stage work.
