## Decisions

- Phase 1 = the two spikes. Base `e6d2ac73c` (`Moti-Velz/sql-dl60`).
- Executors are `task` subagents; the `task` model role resolves to `anthropic/claude-opus-5-5:high` (cfg `modelRoles`). Mechanical work may go to `sonic` subagents.
- **Spike B: go.** The base + delta dataflow is exact and 50× under the latency target. Memory passes only with a per-path or hierarchical base, so Phase 2's membership model is: base chosen per path (most common content), cluster bases for runs of similar worktrees, worktree deltas relative to their cluster. The tag algebra in B's § 5.2 generalizes to that tree.
- Caveat carried into Phase 2: B's R1–R3 are precisely defined stand-ins over B's extractor, not ports of Jeremy's rules (§ 5.4 of its report). B proves the dataflow machinery and the memory model, not rule fidelity. Phase 2's gate runs the real rule semantics through the compiler against the oracle.
- Open for Phase 3: the 88 MB fixed floor (process + fact store + interner, no eviction; 15,717 contents accumulated by the end of the replay) needs eviction by membership or memory-mapped fact files.
- **Spike A: the A2 gate failed (54%) and the "< 4× win" kill criterion is triggered as written, but not applied as written.** Its fallback, "pattern matching stays native", rests on a premise the data contradicts: the facts-based AST evaluator ran batch 6's 263 matcher inputs in 78 s where native's matcher takes 122.8 s, exact on both corpora. The measured cost is the policies' own tree-rebuilding SQL (107 s of 213 s), which the spike executed as written because substitution was deferred to the compiler by my instruction. Phase 1 therefore has not measured the thesis's central step. Decision: one bounded extension, **Spike A3**, substitutes the (a) units with fact relations and moves repository-partition rows out of the per-file phase, then re-measures A2, A3, A5. Its number sets Phase 2's speed gate: ≤ 25% of native → Phase 2 as designed; ≤ 10% → design confirmed; > 25% → the compiler includes cross-clause sharing from the start.
- The product-level gates are per-edit latency and fleet memory, not cold-corpus CPU. At the spike's current efficiency the 10 heaviest rules cost 23.6 ms per file (212.9 s / 9,010), which already fits the ≤ 100 ms per-edit budget for all rules on one core; cold-corpus CPU is paid once per content. A2's 10% was a proxy; Phase 2's gate is restated in per-file terms once A3 reports.
- Accepted from SpikeA2 beyond its brief, exactness re-verified after each: utility memoisation for `value`-reading utilities (`state-signatures-1` 1,616 s → 15 s) and OR-branch index probes as a fixed rule, not a planner (`parameters` stage 149 s → 3.5 s). Production changes remain visibility-only (`lines.rs`, rlib crate type).
- A5's cause is architectural, not an evaluator bug: repository-partition clauses are cross-file rules in the target design and run on the dataflow over exported facts; the per-file phase must be O(one file). Phase 2's classifier enforces it.
- **Phase 1 verdict: GO for Phase 2, with the speed expectation recalibrated.** Proven: exactness of both backends (per-file evaluator 9 of 10 rules exact on 404 stages; dataflow 0 of 1,576); extraction 0.5 ms per file; cross-file edits 0.4 ms p95; per-file phase O(one file); 40 worktrees in 195 MB with cluster bases; a new worktree for free. Not delivered: 10× on batch-6 cold CPU. Measured 2.6× (152.6 vs 393 s). The residue is the rules' own logic, not tree rebuilding: 82 s of SQL computing Python-derived relations per clause over clause-specific node subsets, 28.5 s of dump-selection predicates, 15 s of row copying in the views. Those are Phase 2's levers, in size order: Python-derived relations as per-file facts over all nodes filtered per clause (≈ −30 s), column views instead of `Box<[V]>` rows and id-range `descendants` (≈ −25 s and most of the per-file peak), compiled selection predicates or per-node facts for them (≈ −15 s), a per-process regex cache and no per-statement drops (≈ −10 s). Floor estimate ≈ 80–90 s ≈ 20–23% of native ≈ 9–10 ms per file for the 10 heaviest rules. The last stretch to 10% is rule shape (per-clause tree dumps under a 22-alternative selection) and belongs to a rule-authoring conversation with Jeremy, not to the engine.
- **G2.3 is set:** batch-6 repository CPU through the compiled path ≤ 90 s (≤ 23% of native), stated per file as ≤ 10 ms p50 for the 10 heaviest rules, with parity unchanged; stretch ≤ 40 s. **G2.5 gains a per-worker clause:** peak ≤ 256 MB per worker on the largest corpus file (764 KB, 148,502 nodes), which column views and id-range `descendants` must deliver.
- Why the go decision stands despite A2: the product targets are per-edit latency and fleet memory. At 16.9 ms per file for the 10 heaviest rules (152.6 s / 9,010) the per-edit budget holds for all rules on one core; the cold corpus is paid once per content; the architecture's decisive wins over native are cross-file incrementality (0.4 ms vs 12–50 s per edit) and fleet memory (195 MB for 40 worktrees vs 2.5 GiB for 47 with light rules and 28.6 GiB for one tree on batch 6), both proven.

- **Re-steer (user direction, 2026-10-22): the goal is SQL's strong suit on native's raw speed through a strong architecture around invariants, not ad-hoc escape hatches and per-operator patching.** Written as `INVARIANTS.md` (I1–I10, binding over PHASE-2): one logical algebra with SQLite semantics; facts as relations with declared structure and derived relations as SQL views; nothing after the parser holds SQL text or stage names; rewrites general and justified with a registry (`REWRITES.md`), a differential test and a mutant each; one columnar physical algebra planned once per rule with `EXPLAIN` and a plan audit; classification as a dependency type; memoization by expression digest; incrementality generated; exact or refuse; admission by gate. Consequences sent to and acknowledged by all five slices: S2 retires A3's `subst.rs` and the OR-probe special case in favour of generic rewrites and a columnar layer (`subst.rs` stays as a benchmark oracle until the generic path holds 152.6 s); S4 defines the Python-derived relations as SQL views over the core and extracts `string_type_definition` from native's existing Ruff classifier; S3 ships a generator, never hand-compiled delta plans; S1 owns the IR metadata, the rewrite registry, `EXPLAIN` and the audit; S5's mutants are registry-driven plus generic ones for the generator, classifier and audit, with an `explain-stable` check.
- S2 finding: compiled rules cost ~320 MB per worker before any file (state-tripwires 160 MB, quality 112 MB) and the largest file peaks at 828 MB per worker. Directed: plans one immutable shared object per process, ≤ 32 MB for batch 6; breakdown requested. Added to G2.5.
