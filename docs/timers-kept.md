# Every timer Rerail keeps, and why

Status: part of a design proposal, discussed in its issue before any code lands. Every file and line is at Rerail
0.1.5 (commit 9cad73564). The report on all timers, with the map, the state maps and the plan, is
[timers-to-facts-design.md](timers-to-facts-design.md).

193 of the 383 timer sites stay. Each was judged against one question: is there a fact (an event, an exit, a lock's release, an answer) that could decide what this clock decides, without a person waiting longer or learning later? For these, no such fact exists, or using it would cost the software or a person more than the clock does. Ids: A hooks and daemon, B commands, set-up and dashboard, C the engine in Rust, D tests (see timers-to-facts-design.md).

Most of them never cost a healthy run anything: they end on the answer they wait for, and the clock only bounds a party that never answers (a hung child, a stalled network, an event loop that never runs again).

## A wait for another process to come up or go away (15)

**Why the values are what they are, unless a row says otherwise:** A kill grace is long enough for a clean shutdown to finish its writes and short beside the person's wait; a start wait is longer than a healthy start on a loaded machine.

**What would let them go later, unless a row says otherwise:** Nothing lets a kill grace go: no system says in advance whether a process will obey SIGTERM. Windows has no SIGTERM, so a stop request with an answer (AG18) is the better fact there.

## A wait for a lock (14)

**Why the values are what they are, unless a row says otherwise:** Longer than the longest transaction another Rerail process holds on the same file (a set-up write, a scrub batch, a checkpoint), so a short overlap waits instead of failing.

**What would let them go later, unless a row says otherwise:** One process owning every write to the file (writes routed through the daemon), so no wait across processes remains; SQLite gives no release event across processes.

## A limit on a request or a child process (79)

**Why the values are what they are, unless a row says otherwise:** Longer than the slowest healthy answer seen, and shorter than the caller's own limit above it (the agent's hook limit, OMP's 30 s tool budget, the CI job's limit), so a hang ends with Rerail's message instead of the caller's kill.

**What would let them go later, unless a row says otherwise:** The party waited on reporting its own failure as an event (a child that exits on its error, a daemon that answers 'busy'), or the wait moving off any path a person waits on.
