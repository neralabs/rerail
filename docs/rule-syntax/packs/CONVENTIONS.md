# Writing a pack rule by hand

How the hand-written pack rules under `packs/<pack>/` are written, reviewed and checked. The five first ones are the
reference: `javascript/eslint-curly.rr`, `eslint-one-var.rr`, `eslint-strict.rr`, `eslint-sort-imports.rr` and
`node/n-no-unsupported-features-node-builtins.rr`. Read two of them before writing one.

## The file

- `packs/<pack>/<rule-id>.rr`: the rule id is the JSON's `id`. The directives (`.policy`, `.description`,
  `.language`, `.mode`, `.scope`) are copied from the JSON; raise the revision by one.
- An opening comment says what the tool's rule does, in a few lines, with its options and a one-line example of each
  behaviour. Then the program, top to bottom in the order a reader needs it.
- A table of data (APIs, versions, names, messages) is facts, not rules. A large one goes in
  `<rule-id>.<part>.rr`, generated by a script beside it (`gen-<rule-id>.py`) that reads the JSON, plus a check
  that the table round-trips (`check-<rule-id>.py`): rebuild what the JSON says from the table, and diff.
- Short: most rules should be 10 to 60 lines. A rule over 120 lines is a sign of missing vocabulary.

## Vocabulary

- Reuse the libraries first: `lib/core.rr`, `lib/python/*.rr`, `lib/tsx/*.rr` (names, jsx, statements, modules,
  values). Read the interface comment at the top of each.
- A concept that a second rule could use goes in a library, not in the rule. New vocabulary for your batch goes in a
  **new** library file you own, `lib/<lang>/<topic>.rr`, in the house style: a header listing the interface, plain
  comments on the language's semantics, a code example per rule. Do not edit an existing library file; write the
  change you need (and why) in your NOTES file. Library changes are integrated between waves.
- A primitive only the engine can provide (a tape fact, a functor) is proposed in NOTES with its `.decl` and a
  comment; never declared in a rule. Keep them few and generic.

## Semantics

- The finding key is (policy, code, path, line). Messages are free text; keep them informative, with columns
  (`"{x} … line {p.line}"`). Codes and message ids: as the JSON.
- Options: `option("name", v)` for a scalar (booleans are `"true"`/`"false"`), `option_item("name", i, v)` for a
  list. Defaults as the tool's.
- Fixes: core's edits (`replace`, `delete`, `insert_before`, `insert_after`) or a library `.edit`. Offer a fix only
  where it is safe; `fix safe` only where the tool marks it safe.
- Follow the tool (ESLint, Ruff, Bandit, Clippy, sqlfluff, …) where the JSON is wrong, and say so in NOTES with a
  counterexample. Where the JSON is right and the tool's documented behaviour differs, follow the tool too, but say so.
- No CPython in any form. No per-node, per-byte text scans: tree facts, tokens, and regexes on a node's text.
  Regexes and globs cost the same; prefer typed text (`value`, `str`) to a regex over source.

## Checking

- `python3 site/check_rr.py`: grounding, strata, duplicate declarations. Must print `ok`.
- `tools/rrlab`: run the rule on the tool's own test fixtures and compare with the tool's recorded findings
  (`rrlab score <pack> <rule-id>`), and on ad-hoc cases (`rrlab run`). Every difference is either fixed or explained
  in NOTES (a known divergence of the JSON, a harness gap).
- Where the tool itself is installed (ESLint, ruff, clippy), run it on counterexamples for ground truth.

## NOTES

One `packs/<pack>/NOTES-<batch>.md` per batch: for each rule, what it follows (tool or JSON) where they differ, with a
counterexample; what is not expressible; the rrlab score; proposed library and core changes. Short.

## Review

Every rule is reviewed by a separate agent that did not write it. It is given the rule, the JSON and the tool, not the
author's notes. It reports confirmed defects with counterexamples, and the author fixes them.
