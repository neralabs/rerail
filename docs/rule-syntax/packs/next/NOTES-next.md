## Deviations

1. **Query strings.** The plugin reads a parameter with `URLSearchParams.get`, which takes the first `display=` or
   `features=` and percent-decodes it. The rules take the first one too, but decode only what the plugin's data
   needs: polyfill.io's `%2C` and `%40`, and nothing for `display`. So `display=%62lock` is `block` to the plugin
   and is not reported here. No fixture has one.
2. **Report position.** The JSON reports at the variable declarator. The plugin reports at the
   `VariableDeclaration`, so the rule does too (`let module = 1` reports at `let`, not at `module`). Counterexample:
   the invalid fixture's recorded column, which the column score matches only at the declaration. A for-in/of
   head declares too: `for (let module of xs)` is reported at `let`.
3. **Paths.** The plugin splits the absolute file name on the substring `pages`, and tests `app/` the same way. The
   engine gives paths relative to the repository, so the result differs only when a directory above the repository
   has `pages` or `app/` in its name. The library header says so.
4. **Recorded paths.** The recording prefixes each path with its fixture directory (for example
   `no-img-element/valid-003/src/app/icon.js`). The plugin's metadata-route test is anchored at the start of the
   path relative to the working directory, so on these prefixed paths it fails and the plugin reports. The rule's
   whole-string `match` fails the same way. The 2 TPs on metadata-route fixtures are this recording artefact. In a
   real repository, `app/icon.js` is exempt in both.
5. **Globals.** The rule keeps its own `browser_global` and `window_name` rows for `window`, `location`,
   `document`, `self` and `globalThis`. It does not use `tsx/names` `es_global`, because rrlab has no `es_global` rows (see the
   request below). The rule follows the plugin's `getStaticStringPrefix`: a variable's value is its last write
   before the read, by position (else its initialiser); any constant counts (`location.href = 5` is "5",
   relative); and `+=` is an assignment too.
6. **Repeated attributes.** `<link rel="preconnect" rel="x" …>`: NodeAttributes keeps the last `rel`, so the
   plugin reports a missing preconnect. `attr` in `lib/tsx/next.rr` gives a row per attribute, so the rule sees
   `preconnect` and does not report. Real code does not repeat attributes; the library header says so.
7. **inline-script-id.** Two rare forms differ, both checked against the plugin:
   - a spread with a method, `{...{ id() {} }}`: the rule does not count the method as an `id`, so it reports; the
     plugin does not report;
   - a `<Script>` used above its import: the plugin remembers imports as it walks and does not report; the rule
     reads the whole file and reports.
8. **Visit order.** no-page-custom-font keeps state as ESLint walks the file: the `next/document` import and the
   `export default` it has seen so far. The rule reads the whole file, so a class exported before the import that
   names its superclass, or a `<link>` above a default export it cannot find by tokens, can differ.

## Library and core change requests

- None for core. `lib/tsx/next.rr` is new. It now has `attr_plain` (x="v" written directly, used by no-css-tags
  and no-before-interactive-script-outside-document), and its private `literal` is renamed `attr_literal`, which
  clashed with eslint-b-control.rr. Its helper is `clause_local` rather than `first_local`, because
  `tsx/modules.rr` already declares `first_local`.
- `lib/tsx/names.rr`: when rrlab supplies `es_global` facts, rule 5 can drop its own rows and use
  `es_global("window")`.

## Harness gaps (rrlab)

- The own-fixture subset uses the whole rule name. Proposal: also match the last `/` segment of the recorded rule
  name, so `@next/next/no-css-tags` finds `no-css-tags/…`.
