Syntax

Datalog in one minute

Datalog is a query language over tables. The data is a set of facts, rows in named tables called relations. A rule defines a new relation from existing ones, and its rows can feed further rules. There are no loops or functions: you say which rows a relation has, and the engine works out all of them.

In Rerail the facts describe the syntax tree of your code. A rule file defines relations over them, and the rows of the relation declared as a .violation are the findings. The four steps below build the rule shown in the next section, which reports calls to Python's exec.

The language is Soufflé Datalog, with a few additions for code: patterns, regex captures, findings and fixes, and relations that may be unknown. "Soufflé, and what is added" below lists them.

1. Facts

The parser turns each file into facts. Every node of the tree gets an id, written here as #1, #2, …. kind gives a node's type, field links a node to a named child, and text gives a node's source text.

These are ordinary rows: kind(#3, "call") is one row of the kind table.

Python
from builtins import exec as run # the import binds the name `run` to exec exec(src) # #3 a call; its function is #4, the name `exec` run(src) # #5 a call; its function is #6, the name `run`
Some of its facts
kind(#3, "call"). field(#3, "function", #4). kind(#4, "identifier"). text(#4, "exec"). kind(#5, "call"). field(#5, "function", #6). kind(#6, "identifier"). text(#6, "run"). // … and rows for the import, the arguments, and the module itself.

2. A rule

head :- body. reads: the head holds wherever every atom of the body holds. Commas mean and. A bare name inside an atom, like c or f, is a variable: the engine tries every value that fits. Strings and numbers are constants.

For c = #3, all three atoms hold, so B102(#3) is derived. For #5 the last atom fails: the name is run. This rule misses the alias.

Rule, first try
B102(c) :- kind(c, "call"), // c is a call node field(c, "function", f), // f is the expression being called text(f, "exec"). // and its source text is exactly "exec" // Rows derived: B102(#3). Not derived: B102(#5), because text(#6, "run").

3. Use a library relation

sym_of(n, q) says expression n refers to qualified name q. It is not a parser fact: rules in the python/names and python/imports libraries derive it from the facts, following scopes, imports and re-exports. Rules use it like any other relation.

Swap text for sym_of and both calls are found. Click sym_of to see its definition.

Rule, second try
#include "python/names.rr" // load the library that defines sym_of // Rows the library derives for the code above: // sym_of(#4, "builtins.exec") `exec` is not bound in this file, so it is the builtin // sym_of(#6, "builtins.exec") `run` is bound by the import to builtins.exec B102(c) :- kind(c, "call"), field(c, "function", f), sym_of(f, "builtins.exec"). // Rows derived: B102(#3), B102(#5).

4. Or: several rules, one head

Write a second rule with the same head; the relation has the rows of both. (Inside one body, ( a ; b ) is also an or, as in Soufflé.)

Here the second rule covers (exec)(src), where the called expression is wrapped in parentheses. Negation (!), counting and sets are in "Bodies" below.

Rule, final
B102(c) :- kind(c, "call"), field(c, "function", f), sym_of(f, "builtins.exec"). B102(c) :- kind(c, "call"), field(c, "function", f), kind(f, "parenthesized_expression"), // the call is (…)(src) child(f, g, 0), // g is what the parentheses wrap sym_of(g, "builtins.exec").

Soufflé, and what is added

Everything a rule body can say comes from Soufflé, so its documentation and its intuitions apply. The additions are for code: they match syntax, carry findings to people and agents, and keep unknown facts apart from false ones.

From Soufflé, unchangedAdded for Rerail
Rules h :- b. and facts r("a").; variables are bare names, _ is any value n ~ `exec($ARG)`: n matches a code pattern of the policy's language; each $X in it binds the variable X
!, ( a ; b ), =, !=, <, arithmetic Captures: a named group in match("…(?<X>…)…", s) binds X; match_all gives one row per match
count, min, max, sum : { … } .decl r(…) must, may: a relation that may be unknown, and must / may rules (see "Unknown is not false")
match, cat, strlen, substr, to_number; @functor(…) with .functor .violation, fix, => edits and .edit: findings and fixes

Stratified negation: a relation is complete before anything negates it Policy directives: .policy, .description, .language, .mode, .scope, .budget, …; #include loads each file once

Patterns and captures

Two additions bind variables from code. A pattern atom, n ~ `…`, matches node n against a code pattern in the policy's language, ast-grep's pattern syntax. Each $X in the pattern binds the variable X; by convention, variables bound by patterns are written in capitals and no others are.

A named group in a regex binds a variable too: (?<D>…) binds D. Matched against a node, the capture is a span, a piece of that node's text. A span has text and line, can be a finding's at, and can be the target of an edit, so a finding and its fix can point at four characters of a comment. Matched against a string, the capture is a string.

A group that takes no part in the match gives no row. Inside ! or count : { … } a group binds only there, like any variable.

Python
getattr(user, "email") # ← B009: fix writes user.email x = 1 # todo: retry # ← TD006 at "todo": fix writes TODO
Rules
// The pattern binds FUNC, OBJ and NAME to the call's parts; the rest of the body tests // them. B009(n) :- n ~ `$FUNC($OBJ, $NAME)`, getattr_ref(FUNC), plain_arg(OBJ), attr_name(NAME, _). // In the fix template, $OBJ is OBJ's source text and $a is a's value. to_attr(n) :- n ~ `$FUNC($OBJ, $NAME)`, attr_name(NAME, a) => replace(n, `$OBJ.$a`). // The group D is a span of the comment: the finding is at those four characters. .violation TD006(at: span) "Write `{at.text}` as `TODO`." fix safe upper "Write TODO" TD006(D) :- kind(c, "comment"), match("#\s*(?<D>(?i:todo))\b.*", c), text(D, t), t != "TODO". upper(D) => replace(D, `TODO`). // Matched against a string, a capture is a string: "use_foo" gives x = "foo". hook_name(f, x) :- def_name(f, n), match("use_(?<x>.*)", n).

From JSON to .rr

Every JSON construct has a fixed lowering. The tree axes become native tree relations: within is "below", and within_stop is "below, with no stop node in between". Utilities become relations. ast-grep shares metavariables between a rule and its utilities; a Datalog variable belongs to one rule, so a utility that reads or binds a metavariable its caller uses gets it as an extra column. Anything without a lowering stays as a matcher atom, ast(n, {…}), and runs as it does today.

Fixes

A fix is a set of edits, and rules derive edits like any other rows. A rule that ends in => e1, e2 adds those edits to the fix named in its head. A fix relation has its violation's columns; Rerail fills them from each finding, so a fix's rules run once per finding.

The binary applies four edits: replace, delete, insert_before, insert_after. Edits declared with .edit, such as hoist and remove_stmt, are Datalog in the libraries and expand to those four, so they change without a new binary.

The example is from function-level-imports. One file has two imports inside functions:

  1. FUNCTION_IMPORT finds both and gives each a code: "deferred-no-cycle" and "unread".
  2. For the first, Rerail asks hoist_import(<import>, "deferred-no-cycle"). Its body checks that the move is harmless and derives the edit hoist(<import>).
  3. hoist expands: remove_stmt becomes delete (the function has another statement), and add_top becomes insert_after(import os, …).
  4. The native applier turns those into byte edits, reindents the moved line, applies both and reparses. The fix is safe, so Rerail may apply it on its own.
  5. The second finding gets remove_import. It is a suggestion: the module may be imported for a side effect, so the agent or a person decides.
Python before
import os def load(path): from app.storage import read_blob # ← "deferred-no-cycle": app.storage return read_blob(path) # does not import this module def debug(): import app.plugins.audit # ← "unread": nothing reads `app`

Native or Datalog

The binary provides the parse tape, tree arithmetic, value builtins, file readers and the edit applier. Name resolution, imports, call targets, JSX structure, typing and most edits are Datalog libraries over those. A library update ships without a new binary.

  • core: native. Tape relations, within, nearest, functors, config readers, the four edits.
  • python/names, python/imports, python/calls: adapted from an earlier Datalog prototype of Python call resolution.
  • tsx/names, tsx/jsx: drafted for this page.

Unknown is not false

Some facts cannot be known. Below, Shell comes from a package Rerail has no source for, so whether it renders its children is unknown. A two-valued rule must pick: treat unknown as false and miss real bugs, or as true and report things that may be fine.

A relation declared must, may is computed twice. must holds what is proven; may holds what is proven or unknown. A rule prefixed must or may adds rows to that side only. A rule with no prefix adds to both.

Negation swaps sides. must stuck(e) :- …, !passes(e) reads the may side: the element is surely stuck only if it surely does not pass. So a definite finding never rests on an unknown.

A finding that holds only on the may side keeps its code, is tagged possible, and uses the .possible mode, here log instead of block.

TSX being checked
import { BrowserRouter } from "react-router-dom"; import { Card } from "./Card"; // ours: returns <div>{children}</div> import { Shell } from "@acme/ui"; // a package: no source, so unknown <BrowserRouter> <Card><BrowserRouter/></Card> // ← definite: Card renders its children <Shell><BrowserRouter/></Shell> // ← possible: only if Shell does </BrowserRouter>
