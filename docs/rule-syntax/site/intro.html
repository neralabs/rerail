Rerail logic: rules as Datalog

A proposal for how Rerail rules are written. It replaces today's rerail.policy/v1 JSON with one text format, .rr, and moves name, import and call resolution out of the binary into libraries written in the same format.

The format is Soufflé Datalog with four additions for code: syntax patterns, regex captures that bind variables, findings with fixes, and relations that may be unknown.

Why change

The JSON is hard to read and write

A rule is a nested matcher tree. Every and, or and helper is another level of objects, and the logic is spread across them.

This is Bandit B102, "no exec()", as it ships today, next to the same check in .rr.

It cannot say what the data-layer checks need

The data layer is a Python codebase of about 9,000 files whose architecture is enforced by custom checks: which layer may import which, sync and async methods in pairs, no import cycles. They follow imports across files and reason over the module graph, so today they are Python scripts, not Rerail rules. The 49 on this page are {{dl_py_lines}} lines of Python. Resolution logic ships in the binary

What a name refers to, what an import loads and what a call targets are computed in Rust. A JSON rule can only ask through fixed keys such as resolves. Changing how Python scoping or re-exports are handled means changing the binary.

In .rr, the same logic is rules in a library. This is the core of Python name lookup.

Today: the rule asks; native/src/code_rule_dsl/{scope,calls,import_target,module_graph} answers (≈28k lines of Rust)
"resolves": { "binding": { "form": "import", "site": { "matches": "alias-to-exec" } } }
.rr: lib/python/names.rr ({{lib_py_lines}} lines for all Python libraries)
// walk: start at the name's own scope and move outward, skipping class bodies, until a // scope binds it. walk(n, x, s) :- nameref(n, x), nearest(n, s, scope). walk(n, x, p) :- walk(n, x, s), !bound_in(s, x), nearest(s, p, fscope). look(n, x, s) :- walk(n, x, s), bound_in(s, x). // the scope that binds it // sym_of: an imported name gives the module path; a local def its qualified name; else // a builtin. sym_of(n, q) :- qn(n, q0), resolve_export(q0, q). sym_of(n, q) :- look(n, x, s), defn(s, x, f), qualname(f, q). sym_of(n, q) :- builtin_ref(n, x), q = @dot("builtins", x).

What changes

Settings become directives

Identity, mode and scope are one line each at the top of the file. Approving a rule or moving a ratchet changes one line.

Today
{ "format": "rerail.policy/v1", "id": "bandit-b102-exec-used", "revision": 3, "mode": "steer", "scope": { "include": ["**/*.py"] }, "clauses": [ … ] }
.rr
.policy "bandit-b102-exec-used" revision 3 .mode steer .scope include "**/*.py"

Libraries are Datalog; the binary keeps the basics

The binary provides facts about the tree and a few operations on it. Everything that interprets the language, such as scopes, imports, calls and JSX, is Datalog that ships as data. A library change is a text change to a .rr file, with no new release.

lib/core.rr: native, in the binary
.decl kind(n: node, k: symbol) // a node's grammar kind .decl field(p: node, f: symbol, c: node) // c is p's child in field f .decl within(n: node, a: node) // n is somewhere below a .input kind, field, within // rows come from the binary .edit replace(n: loc, text: symbol) // an edit, for fixes
lib/python/names.rr: Datalog, shipped as data
// python/names: `len(xs)` with no local `len` refers to the builtin. sym_of(n, q) :- builtin_ref(n, x), q = @dot("builtins", x).

Unknown is not false

Some facts cannot be known, such as what a component from a package renders. Today's rules must guess. A .rr relation can be declared must, may: a finding proven from known facts is definite, and one that needs an unknown fact is reported as possible, with its own mode.

TSX
<BrowserRouter> <Card><BrowserRouter/></Card> // Card is workspace code and renders its children <Shell><BrowserRouter/></Shell> // Shell comes from a package with no source </BrowserRouter>
Findings
today (JSON) no findings: the rule stops at any component .rr line 2 nested router definite → .mode line 3 nested router possible → .possible

Fixes are rules

Today a fix is one text template that replaces the match. In .rr a fix is a set of edits derived from facts, so it can touch several places, and a rule can mark it safe only where its evidence shows the edit changes nothing else.

Today: one template
"fix": "$E"
.rr
// Hoist a function-level import, but only if it closes no cycle and is a plain // statement. hoist_import(i, "deferred-no-cycle") :- plain_stmt(i), !clash(i) => hoist(i).
The edit it makes
import os + from app.storage import read_blob def load(path): - from app.storage import read_blob return read_blob(path)

Example: no explicitly nested routers

What the rule is for

In React, a react-router router (<BrowserRouter>, <MemoryRouter>, …) owns the app's location. It keeps the current URL and the navigation history, and hands them to everything rendered below it through React context. <Link>, useNavigate() and <Route> read that context to know where the app is and to move it.

So there must be exactly one router above any piece of the tree. A second router inside the first would start its own history: links below it would change the inner router's location, not the URL bar or the rest of the app. react-router refuses this at render time with “You cannot render a <Router> inside another <Router>. You should never have more than one in your app.”

That error appears only when that screen renders, so tests and review can miss it. It usually comes from code moved between contexts: a page copied from a standalone app, or a component that wraps itself in <MemoryRouter> for a demo or test and is then used inside the app. A static rule catches it before it runs.

This version reports a router inside another router in the same file, with only HTML elements or fragments between them. It stops at anything it cannot see through: a function boundary, an attribute, or a component, whose source it does not read. That makes it precise but incomplete; the two misses below are what the accurate version, on the Data-layer rules tab, adds.

What it reports
import { BrowserRouter, MemoryRouter } from "react-router-dom"; export function App() { return ( <BrowserRouter> <main> <MemoryRouter>…</MemoryRouter> // ← reported: only <main> in between </main> <Layout> <MemoryRouter>…</MemoryRouter> // missed: the climb stops at <Layout>; // the accurate version reads Layout's source </Layout> <Route element={<MemoryRouter/>} /> // missed: inside an attribute; // the accurate version follows `element` </BrowserRouter> ); }

How it works

  1. router_el(e): the tag of element e is a name imported from a react-router package, and the imported name is one of the router exports (BrowserRouter, MemoryRouter, …). It follows the import, so import { BrowserRouter as R } counts.
  2. stop(n): where the climb up the tree ends. A function or attribute (the relation barrier), any router element, or a component element, meaning a tag that is not a lowercase HTML tag.
  3. NESTED_ROUTER_JSX(inner): inner is a router, and the nearest stop above it is also a router. <main> and <>…</> are not stops, so the climb passes through them.

For the first <MemoryRouter>: climbing up, <main> is not a stop and <BrowserRouter> is, and it is a router, so the rule reports it. For the second, the nearest stop is <Layout>, which is not a router, so it reports nothing.

The three relations, from nested-routers.b1.rr
// 1. router_el(e): e's tag refers to a router export of a react-router package. router_el(e) :- tag(e, t), kind(t, "identifier"), ref_site(t, s), imported(s, m, x), router_module(m), router_export(x). // 2. stop(n): the climb ends at functions and attributes, at routers, and at // components. stop(n) :- kind(n, k), barrier(k). stop(n) :- router_el(n). stop(e) :- kind(e, "jsx_element"), !router_el(e), tag(e, t), // not <div>, <main>, … count : { kind(t, "identifier"), text(t, s), glob("[a-z]*", s) } = 0. // 3. The finding: the nearest stop above a router is a router. NESTED_ROUTER_JSX(inner) :- router_el(inner), nearest(inner, outer, stop), router_el(outer).

Where it stands

{{hand_rules}} / {{rules}}pack rules written by hand in .rr, each reviewed against its tool
{{json_mb}} → {{hand_mb}}pretty JSON → hand-written .rr, comments excluded
{{dl_py_lines}} → {{dl_rr_code}}data-layer lines: Python → .rr logic
  • Every pack rule is written by hand on the shared libraries. A second person reviewed each batch against the tool it ports (Ruff, Bandit, ESLint and its plugins, Clippy, sqlfluff, PHPStan, …), and the defects found were fixed. Each rule's NOTES file lists where it still differs from the tool, and why.
  • The rules run in tools/rrlab, a lab harness on Soufflé, and are scored against the tool's own findings on its test fixtures.
  • The engine reads .rr as its only rule format. With the reader work on its branch final-rerail-shape-rr-align (not merged yet), 3,890 of the libraries' 3,906 clauses and 5,220 of the packs' 5,264 clauses lower. The rest are constructs it still refuses by name, such as ordered by, a place used as a value, and recursion whose bound it cannot yet prove. docs/rule-syntax/ALIGN-FINAL-SHAPE.md lists every difference and who changes what.
  • The machine translation of the JSON is kept as a second tab, for comparison.
  • 49 data-layer checks, function-level-imports and the router rule are also written in their final form, beside the Python they replace. Each data-layer check follows its Python linter and is scored with rrlab dl against the linter calls recorded from that linter's own test suite.
