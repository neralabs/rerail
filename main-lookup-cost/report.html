5. The changes

Each line opens its card.

AOne read for a session's checkoutsMedium riskOne tool call at 120 worktrees: 1,542 to 2,125 ms of daemon CPU on main, 42 to 186 ms here.
Problem
At every hook event the daemon re-read every checkout the session knows, each with every recorded checkout of its repository, so one event cost the worktrees known times the checkouts recorded.
Who meets it
Everyone with many worktrees, at every hook event of every session there, on main with the 0.2.0 engine as before it.
What it does
recordedCheckoutsReader reads every checkout a session asks about, with its parents and start state, in one prepared statement. refreshCodeRules has each checkout's auditor read its rules when its inputs moved: the session checkout's at each event, every auditor's when a signature or setting changed, an auditor's at its opening and at the session's end.
Risk
Medium: a version that misses a change would leave an auditor on old rules until its next input moves.
Check
Whether any write to checkouts or repositories leaves the recorded checkouts' version as it was, and whether an auditor can audit before it read its rules after an input moved.
BHEAD read from Git's filesMedium riskThree walks of the other worktrees: 10 Git starts for their HEAD through gitHead, 0 through this reader.
Problem
With the lookups gone, the walks' git rev-parse HEAD, one per watched worktree per walk, held the daemon's thread: each a fork of a process of several gigabytes.
Who meets it
Everyone with many worktrees: 17.8% of the daemon's thread at 190 worktrees in a CPU profile, Linux x64.
What it does
gitHeadReader reads HEAD, the branch's ref and packed-refs from Git's files. Git is asked at a checkout's first read and whenever its .git entry, a configuration file Git reads, an owner Git checks or the object and ref folders changed; between, the files' answer stands where Git's last answer named the same commit.
Risk
Medium: an answer from the files where Git names another commit would attribute a change to the wrong commit.
Check
Whether a file Git reads for HEAD is missing from the key, and whether any path makes the reader answer without Git having vouched.
CLine endings from Git's filesMedium riskA pass that finds a change: 3 line-ending Git starts through gitCrlfPaths, 0 through this reader.
Problem
Each pass that found a change asked Git for the line-ending settings and attributes again: git config twice and git check-attr, though no file they come from changed.
Who meets it
Everyone with many worktrees and busy sessions: about 15% of the daemon's thread once HEAD came from files, Linux x64.
What it does
gitCrlfReader keeps the settings by the configuration files' stamps and each path's attributes by every attributes file Git reads, asking check-attr only for paths whose key moved, and none where no attributes file exists.
Risk
Medium: a kept answer that misses an attributes file would compare a change under the wrong line endings.
Check
Whether every file Git reads attributes from is in a path's key, attr.tree and GIT_ATTR_SOURCE included.
DTool call's edit checked firstLow riskAfter a nested checkout moved, beside another session: on time 4 or 5 in 5 on the engine; main always.
Problem
A walk of the other worktrees queues what it found as log edits, which steer no session. A nested checkout moved inside a worktree is about 46 of them, and the agent's next Write was answered after all.
Who meets it
A session whose agent writes in a worktree just after a folder of files changed there, now that walks reach a change about a second sooner.
What it does
Where no rule of the checkout reads other files, the edit that may steer is checked first. Where one does, it is checked with the log edits ahead of it in one engine call. Each revision publishes once its edits are checked, and a tool call's result waits for the edits that may steer.
Risk
Low: every edit is checked and recorded, and the Log lists audits in the order edits came; where a rule reads other files, a log edit is checked with the batch's texts held.
Check
Whether a rule the cross-file flag misses reads another file the workspace holds.
EWorktree made again watched at onceLow riskA file written in a worktree deleted and added again: recorded 1 of 5 on main, 5 of 5 now.
Problem
A worktree deleted and added again lost its watch with the old folder, and main waited 5 s to watch it again. A file written after the walk read the new folder waited for some later tool call's walk.
Who meets it
A session whose repository has a worktree removed and added again at the same place while the daemon runs.
What it does
Each watch keeps the identity of the folder it watches; when it ended and another folder stands at the path, the next walk watches the worktree before it reads it.
Risk
Low: one awaited lstat as a watch opens, and one per walk while an ended watch waits its 5 s; the same folder, or none, still waits 5 s.
Check
Whether a folder being moved back and forth could now have its watch end on every walk.

6. The decisions

When does a checkout's auditor read its rules again?

We chose when an input moved: the recorded checkouts' version, a signature row, or its own rules folder at each event.

Would change our mind: a change Rerail records that moves neither the recorded checkouts' version nor a signature row.

When may a reader answer from Git's files?

We chose only where Git's last answer named the same commit under the same inputs, all at least 2 s old.

Would change our mind: a file Git reads for a checkout's HEAD or attributes that the key leaves out.

8. What is not covered

  • A worktree's files changed at once beside another session, a Write there was on time 19 of 20 times on the 0.2.0 engine, main 20 of 20; the late one a call later.
  • One session, a worktree removed late on main too: its walk's first sight of the worktree, a defect we report separately. One probe: 1 of 152 late here, 3 of 152 on main.
  • A worktree walked while gone, then added again a file written there waits for an unrelated walk, here as on main.
  • The 10-minute load at this head did not run. At 0.1.5's code against this change's code then: CPU 43% against 96 to 98% of a core.
  • macOS never ran.
Four limits that stay

Limits that stay.

  • A rule file written into a worktree's own .rerail/rules, then a Write there, beside another session: on time 19 of 20 here, 20 of 20 on main; the late one a call later, its finding logged at once.
  • A rule that another worktree's rules file leaves unrunnable is recorded as skipped at that worktree's next walk or tool call, or at the session's end, where main records it at the next event. Every check runs with current rules.
  • Each catalog build still serializes every rule with its mode, as on main: each checkout's rule set hands it a copy of its own.
  • After a failed git var, the HEAD reader asks Git for 60 s before it tries Git's file list again.
