5. The changes

Each line opens its card.

AHooks beside a silent daemonHigh riskHooks beside a silent daemon: 12.2 s each on main, 0.15 to 0.34 s after the first here.
Problem
While the daemon's process lives but reads nothing, every hook waits its whole bound, then drops its event: the agent waits at each tool call, and nothing it does is recorded or checked.
Who meets it
Every session whose daemon stops reading for a while, at each tool call of that silence. Shown through the product on Linux x64 and Windows 11.
What it does
leaveUntaken writes a hook's event, after its bounded wait, into a folder of the Rerail home; while an event waits there, untakenFor lets each later hook leave its own at once. The daemon takes the folder in arrival order when it reads again, before any later event, and what it finds reaches the agent with the next answer.
Risk
High: it decides which hook waits and when an event is checked; a wrong mark would skip a daemon that reads, or check events out of order.
Check
Whether a hook can skip its wait for a daemon that reads (the taken mark, the folder's identity in the state file), whether every left event is checked before any later one, and whether a late check of an edit tells only lines the edit made.
BRecords off the hook threadHigh riskA hook while another process holds the database: 5.2 s on main, 0.2 to 0.3 s here, steered.
Problem
While another Rerail process holds the database's write lock (rerail reset, a scrub), each record waits SQLite's 5 s on the thread that answers hooks: hooks wait, no steer comes, and a record that outlasts it is lost.
Who meets it
Every session while another Rerail process holds the database, at each hook. Shown through the product on Linux x64 and Windows 11.
What it does
openRecordWriter keeps a record write in memory while the lock is held and makes it once a worker thread finds the lock free, trying at SQLite's own times and when the write-ahead log changes. Reads of this process's records see waiting writes. A steered hook hands its receipt to the daemon, which keeps it until the lock is free.
Risk
High: it changes when every record is written; a lost or reordered waiting write would leave the Log without an audit.
Check
Whether a read of what this process recorded can miss a waiting write, whether a waiting write keeps its 5 s bound, whether the worker can try later than SQLite's own busy wait would, and whether a receipt the daemon keeps is recorded once, after the release or at the next start.
CA turn's end that gave upMedium riskThe next prompt after a turn's end gave up: 30.2 s, then failing, on main; 0.2 to 0.5 s here.
Problem
A turn's end whose hook gave up at its 30 s went on waiting for every check; the next prompt and tool calls queued behind it, each giving up, and its steers went into an answer no one read.
Who meets it
A session whose turn ends while many checks still run, as after a formatter rewrites thousands of files. Shown through the product on Linux x64 and Windows 11.
What it does

Risk
Medium: a steer kept for the next event could reach the agent twice or never; it reached it once in every run.
Check
Whether a turn's end can mark a steer delivered into an answer no hook reads, and whether a kept steer reaches the agent once, with the next event.

Problem

Who meets it

SessionNotices keeps the paths the folder's watch reported since the last pass, and #finishSessionWalk reads only those at a command's result. 6. The decisions

After the daemon left an event untaken, does each later hook wait?

We chose the first hook of a silence waits; later ones leave their events in order and answer at once.

Would change our mind: a case where an event's check at its own hook matters more than 12 s a hook.

8. What is not covered

  • A write no notice tells of is checked at the turn's end or the next whole walk, not at its own result, as the release note says.
  • A record behind a quiet holder lands at main's time: a holder that changed nothing leaves no sign of its release.
  • Codex and Cursor ran their answers' new fields in unit cases only; every product run drove Claude Code's hooks.
  • The dashboard under one write a second was measured before its last fix only: 3.0 s against main's 2.6 s at the median.
  • The change stream's last reads stay in the daemon's memory for its life: one short entry per part for each checkout Rerail recorded that a stream named.
  • macOS ran in none of our runs; CI runs the tree watch's tests there.
Six limits that stay

Limits that stay.

  • On Windows the file system reports an open file's growth only once it is flushed, so a record waiting for another process's lock keeps SQLite's own times there, as on main.
  • The first edit of a session's first start can be steered at the next hook while the rules still compile, on main as here: 5 of 19 and 4 of 19.
  • Left out, a check's turn on the engine in arrival order: on the 0.2.0 engine main's check beside a large scan no longer waits (153 to 200 ms, against 1.4 to 3.1 s before).
  • Each change was measured through the product on Windows 11 when it was built, at older main commits; today's figures are Linux x64.
  • Behind a proxy other than nginx that holds a streamed response, the page reads every 5 s from when it opens, as main does: a change shows at the next read.
  • On Unix a lock wait given up keeps its thread and the lock file open until the holder lets go or ends; only a command, a hook or a daemon's start waits for a held lock.
