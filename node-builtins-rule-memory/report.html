5. The changes

Each line opens its card.

AOne regex per patternMedium riskThe rule: 500 MiB at main, 153 MiB with shared regexes.
Problem
With the Node.js pack on, the engine holds 500 MiB for one rule once compiled, and takes 2.6 s to compile it. Most of it is the same few hundred regexes, built again for every term in every table.
Who meets it
Every process that compiles the Node.js pack, each time, for as long as its rules stay loaded. The five packs' 109 on-by-default rules hold 760 MiB at main and 149 MiB here (release builds, the median of three runs).
What it does
Regex::new in regexes returns a pattern's one compiled regex, from a process-wide table behind a read-write lock. Five files import that type, not the regex crate's; anchors/semantic.rs, outside the diff, takes it through use super::*. sweep drops each regex nothing outside the table holds: CodeRuleDslRuntime::compile calls it as a compilation ends, and Drop for CompiledCodeRule as a rule drops.
Risk
Medium. Engine code that every rule's regex terms go through, with new process-wide state behind a lock. The table is read at compile time, never at match time, and a regex is immutable.
Check
Only Regex::new hands a regex out of the table, under its lock; a clone of a held Regex (matcher/anchors.rs line 378) takes no lock: its holder already counts. Can sweep drop one in flight? CompiledCodeRule derives Clone, and a workspace copies a rule it places (Arc::make_mut in workspace/api.rs), so each copy sweeps as it drops. Does anything but a rule's clauses hold a Regex and drop after the rule? violations.rs compares witness regexes by address: through Deref, the shared regex's.
BLean utility tablesMedium riskThe rule: 153 MiB before, 87 MiB after.
Problem
Each shared table of a define makes room for every utility of the define and copies every name, though its queries reach a few dozen to a few hundred utilities.
Who meets it
The same processes as A. The cost grows with a define's utilities times its tables: this rule has 3,053 utilities in 108 tables.
What it does
UtilTable keeps one slot per utility and makes the utility's state when a query first compiles or reads it. A language's tables share one copy of the names, parameter flags and origins through UtilTable::sharing. AddedByIndex records only the utilities a table compiled.
Risk
Medium. Every utility lookup of every rule goes through a slot, behind one more pointer. A wrong answer for a utility not yet filled would change what a rule matches.
Check
Do rule, with_target and summary_key answer for a utility with no slot as main does for an empty cell? scope and memo_term make the slot on first read. fill and draft still panic past the table's utilities. names and framed come from utils in key order, the order defs has. AddedByIndex gives None for a utility not compiled, and its mutable index inserts an entry.

6. The decisions

One regex per pattern: per process, or per document? ask 1

We chose the process: sharing per document hung on a hidden thread-local scope.

Would change our mind: a profile of matching threads waiting on a shared regex's cache pool.

8. What is not covered

  • The automated reviewer has not read the eight commits since its review. Its change request stands.
  • The sweep alone is not timed: it scans about 1,700 entries under the write lock.
  • Matching time is not measured at this head, only at 1e3c8127.
  • Windows: only the five touched modules' lib tests ran. macOS never ran.
Six smaller gaps, seven limits that stay
  • What the review has not read. The process-wide table, the sweep as a rule drops, the Regex type, AddedByIndex and the UtilTable::new and sharing pair all came after the automated review of 2ea7b4b4.
  • The follow-up thread. Our reply to the review's one inline finding is posted, and the thread is still open. Nobody has asked for a second review since the push: we ask for it with this update.
  • A running daemon. Every figure comes from fresh Node 24 processes that load the engine and compile the rules, not from a daemon's own memory.
  • Backreference patterns. They run on another regex engine and are not shared. What they hold was not measured.
  • Our own whole-suite runs. They date from bd4e7cfa for the Rust workspace and from 2ea7b4b4 for the vitest suite, both without the pack test data. CI ran both with the data at this head, and they passed.
  • The trial merge with #508. It is a draft that still moves: the count is that of its head 29de931d, read on 13 November 2026.

Limits that stay.

  • Regexes built elsewhere keep the regex crate's type and are not shared: a clause's regex query over file content or path, transforms, suppression comments, the module graph.
  • A rule dropped on another thread while a document compiles can sweep a regex that document validated. Its terms compile it again: a second compile, not a wrong regex.
  • The table's key is the pattern alone. A term that needs its own regex options cannot use it.
  • Threads that match one pattern share its cache pool. The engine matches on 4 worker threads, as at main.
  • A table that fills every utility, as a query's own table does, reads each utility's state behind one more pointer.
  • The define check's validation tables keep copies of their own, as at main, and drop them when the check ends.
  • The 1.4 s of compile time left is work per clause.

9. What we ask of you

  1. Is a process-wide regex table, swept at each compilation's end and each rule drop, an owner you accept? We recommend yes: calls::names is such a table.
  2. May the shared type keep the name Regex? We recommend yes: another name edits six long functions.
  3. Should the long compile functions come under the ceiling in their own pull request? We recommend yes; we can open it.
