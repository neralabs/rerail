Incremental Duplicate Detection

After a small edit, the duplicated-block findings, and what changed in them, should cost about as much as the edit, not as much as the tree. This spike keeps the suffix-array index up to date over edits and checks every result against a full rebuild.

The answer

  1. A suffix array to depth w is enough, and it is local. A finding only depends on which w-unit windows are equal, so the index needs the windows sorted, and nothing past depth w. An edit then changes only the windows that overlap it.
  2. Two levels: an immutable base plus an overlay. Base windows that the edit overlaps get tombstones. The new windows the edit makes are looked up in the base and added to their class. The rest of the edited file stays in the base and only moves. Compaction merges the overlay into a new base in one linear pass.
  3. About 1,000× fewer instructions than a rebuild. On Jeff's native/src as node symbols (5.6 M windows), an edit costs a median 5.7 M instructions (0.6 ms) with the index in memory, against 6.4 G for a run that rebuilds. A fresh process that maps the saved index and applies the edit costs 0.15 G instructions, 0.02 s. All 100 replayed steps (50 per method) gave the rebuild's exact findings.

Why it can be incremental

Jeff's rule, and report.rs after it, decide two things per position:

  • whether its window of w units (30 lines, or 150 nodes) is duplicated, meaning some neighbouring suffix shares at least w units with it;
  • for a block, its other copies: the suffixes that share its first window.

Neither looks past depth w, so a suffix array truncated to depth w gives the same findings. In a full suffix array, a suffix's place depends on everything after it, up to the end of its document, so one edit can move suffixes anywhere in the order. In the truncated one, a window's class depends only on its own w units.

The index

The base holds every full window of a snapshot, in window order:

  • a bit per window for "same as the window before", which replaces the LCP array;
  • each window's class (a run of equal windows);
  • each position's rank.

That is 16 bytes per window: 91 MB for the node windows of native/src. The base is never edited.

The overlay has an entry per document changed since the base. The entry is computed from the base version and the current version only, so editing a document again replaces its entry. A run that starts from a saved base only needs the documents changed since that base. An entry holds:

  • Tombstones: a bit per base window, with each class's count of live members.
  • Added windows: each new window is found by a binary search over the base windows, skipping the units already matched at both bounds. It joins the base class it equals, or a fresh class, keyed by a hash of its units and compared in full, when no base window is the same.
  • A position map for the rest of the document.

The blocks are kept per document, each holding its first window's class. After a batch of changes, blocks are recomputed only in documents with a member in a class that gained or lost one, since those classes' counts may have crossed 2. A block's other copies are read from its class when reported, so they never go stale. In the replays that was at most 6 documents a step.

Compaction merges the overlay into a new base. It is one pass in window order:

  • tombstoned windows are dropped;
  • added windows go at the end of their class;
  • fresh classes go at the rank their binary search stopped at.

No window is compared or sorted again, and the "same as before" bits follow from the classes.

Finding changes: each step, the last findings are moved through each document's change and compared with the new ones. A finding is then unchanged, moved, has changed copies, is added, or is removed.

What was tried, and what it costs

The edits are 50 steps on Jeff's tree, from make_steps.py:

  • 40 one-line renames;
  • a 60-line paste that creates a new duplicate, and a later step that removes it;
  • one file deleted;
  • three steps that each change 5 files.

Each bar is one design, in two colours on one log scale of instructions retired:

  • cold is the first run from nothing: a whole process that reads the base, builds the index and computes its findings, and for the saved index also writes it;
  • warm is one later edit. For the in-memory designs, that is the median per-edit cost inside a running process (rebuilds over steps 1–10, updates over all 50). For the saved index, it is a whole new process that maps the index, applies the edit and reports the changes, median over six steps.

Instructions are the process's own count. Unlike CPU time, the machine's load doesn't change them (its load average reached 145 during these runs). Hover a bar for both figures.

Checked against a full rebuild

same on every step, for both methods. With --check, every step rebuilds SA-IS and blocks over the current versions and compares the findings, with all their other copies, one for one:

  • lines: 50 of 50 steps (562 findings, rising to 564 when the paste lands);
  • node symbols: 50 of 50 steps (600 to 602);
  • a cold run that loads the saved index: 6 of 6 steps, skipping steps 3–40.

The unit test edits_give_the_rebuilds_findings runs random documents through random batches of edits, new and deleted documents, edits to the same document again, and random compactions. It covers both kinds of base, with and without --whole-doc: 19,320 findings compared across 1,560 compactions, all equal to the rebuild. A second test checks that doubling gives SA-IS's classes, in SA-IS's order.

Why the node rebuild took 7 s, and the fix

The algorithm wasn't the problem; the symbol reads were. The profile:

  • The same symbols, read three ways. SA-IS and LCP reading the tape took 5.5 s. Over per-document arrays they took 1.3 s, and over one flat array 0.37 s, which is 63 ns per symbol, in line with lines.
  • The tape reads cost about 4.2 s. SA-IS and Kasai's LCP read each symbol 11.9 times, mostly in random order. Each read derived the node's symbol again: two start reads (start_stated topped the profile), a scan of the source for a newline, and a SipHash lookup in the dictionary.
  • Joined::locate cost about 0.9 s. It was a binary search over the document starts, done on every read.

Faster tape reads in the tree. None of the worktrees has a bulk decoder for format 16. The fastest read there is reads::f16::start_next: each start is the previous one plus the node's gap, with a checkpoint every K nodes. start_stated is the random-access form, which sums up to K − 1 gaps from the checkpoint. The reads crate on uglykl-CPU-SIMD-parallelization decodes 16z blocks into a shared cache; it is for compressed tapes and doesn't apply here.

The fix: derive each symbol once. A node's symbol is not a column of the tape. It is derived from the code, the leaf bit, the gap and its line break, and the leaf's length, then numbered by the dictionary. NodeDocs now derives every symbol once, in tape order:

  • starts by start_next;
  • line breaks by one forward scan of the source;
  • dictionary lookups by an Fx hash instead of SipHash;
  • the results go into a u32 relation laid out as the joined text the sort reads, one separator after each document.

The tape is not read again for these symbols. SA-IS and LCP read the relation directly (Docs::joined), with no locate. On 5.9 M nodes:

  • deriving the symbols takes 0.15 s;
  • the SA-IS base takes 0.47 s, down from 7 s;
  • a whole cold process takes 6.4 G instructions, down from 65.6 G.

The relation is 24 MB. It is a derived fact written once where it is computed, which decision 0353 counts as not a copy. A run on a saved index skips it: it reads about 150 symbols per lookup and derives each one where it reads it.

The path after a small edit

A process that stays up (a watch mode or a language server) keeps the index in memory. After each save it reads the changed files' new versions, which for node symbols means parsing them. Reading a step's new tapes took 0.1–2.4 ms here; the engine's parse of the changed files is a separate cost, not measured here. It sets them in the overlay and recomputes the affected documents. That is milliseconds, and then it reports the changes in the findings.

A CLI run maps the saved index and the base's tapes, applies every document changed since the base, and reports what changed since the last run: 0.02 s wall, 0.15 G instructions. The steps:

  • The index file is mapped. Its arrays are slices of the mapping, aligned to 8 bytes, and nothing is read until used.
  • The lines method's base ids and its line dictionary are in the index, so the base files are not read again.
  • The last findings are in the index, by document. Only the affected documents' findings are recomputed; the others' are moved through the change.
  • Tombstone counts are held only for the classes an edit touched, so a loaded index starts without a pass over its 5.5 M classes.
  • Still open: each language (tape tag) needs its own base, and the spike runs one.
