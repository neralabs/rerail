Decision report · Rerail pull request #657

A Rerail home runs one daemon, however many processes start it

1. The one question

Does one Rerail home end up with exactly one daemon, named in daemon.json, whatever starts, stops or dies, with nothing on main slower or broken?

  1. Every build's daemon locks its home, in locks/; a second exits. Changes the intent.
  2. A lock holder that never writes daemon.json fails every start after 15 s.

We recommend: rule first on the two design questions open on #626, since this pull request builds the lock per home, then review it as built.

5. The changes

Each line opens its card.

AThe home's lock and record checkHigh riskReal-daemon tests at f8240d5ba: 7 of 15 fail at main on Linux x64, none here.
Problem
A running daemon that daemon.json no longer names blocks every start, and rerail daemon stop says none runs. Nothing is recorded or steered until someone ends it by hand. On Windows a checkout's busy daemon gets a second beside it.
Who meets it
Every home whose daemon.json goes while its daemon runs: #626's four steps fail every time at main. How often the file goes is not known. Seen once, on a busy Windows 11 machine: 52 start processes, no daemon.
What it does
runHomeDaemon takes an OS lock on locks/daemon.lock before the daemon opens a store or binds anything, and holds it until the process ends. #record and #restoreRecord read daemon.json every second and write it again when it differs. lookupHomeDaemon makes a start or a stop wait for that record while homeDaemonRuns says the lock is held.
Risk
High. It decides which daemon a home runs and whether a start waits, uses it or launches one. A fault leaves a home where nothing is recorded. Where the lock cannot be asked or taken, main's behaviour stays.
Check
Can homeDaemonRuns answer yes where no daemon of this home runs? On Windows homeHolderMayRun asks the lock only while this home's engine pipe is listed. holdHomeDaemonLock returns no lease on any failure of its first try. A restart at the heap ceiling launches the next daemon before the old process exits: does the old one always let go within the second the next one waits? #restoreRecord writes the capabilities to daemon.json alone, mode 0600, and logs only a process id.
BThe shared start claimMedium risk20 hooks, no daemon: 20 starts at main, 1 at 2cb75efa0.
Problem
Every process that finds the daemon down launches its own rerail daemon start. After a daemon stops, every hook in flight does so at the same moment: 52 start processes were seen once on a Windows 11 machine.
Who meets it
Every machine with several sessions when the daemon goes down. At main, on Linux x64 and Windows 11, 2, 5 and 20 hooks launch 2, 5 and 20 starts. A comment on #626 names it as that issue's second cause.
What it does
claimAutostart creates autostart.claim in the Rerail home exclusively: the process that made it launches, and handOverClaim writes the launcher's process id into it. claimHolds lets the others leave the start to that launcher while it runs, 30 s at most. startUnderLock ends the claim through endOwnClaim when the start ends, only if the claim names this process.
Risk
Medium. A claim that held too long would keep every session from starting the daemon. It holds only while its launcher runs, and 30 s at most. A start still takes the start lock, and the daemon the home's lock.
Check
Its code is in daemon-control.ts, which the map counts under A. Can a claim outlive its launcher? claimHolds needs a live process id and a file time within 30 s of now, either way. Two processes that replace a stale claim at the same moment can both launch: the start lock still lets one start a daemon. A launcher that hands its start to the active version's CLI leaves the claim to end at its own exit.

8. What is not covered

  • macOS never ran.
  • No test ran at a merge with main.
  • Left as main intends: a daemon.json naming a live process that is no daemon refuses every start.
  • Windows, as on main: beside a busy daemon, a program holding the lock file open lets a second daemon start. A retry, not built, would close it.
  • In no known setup: a start that cannot ask the lock fails beside a busy daemon after about 1.5 s. Main fails it on Linux and starts a second on Windows.
Six smaller gaps, eight limits that stay
  • That Windows case, in full. The busy daemon's daemon.json is gone, and the program holds the lock file open twice: when a start asks the lock, and when the new daemon first tries it. A failed first try means no lock, as on main. Read from the code, not run.
  • That last case, in full. The start cannot ask the lock, the daemon can, and the busy daemon's daemon.json is gone. Linux x64, d100d92f8, the start's question made to fail: it fails after 1,513 ms. With 6a2140fa8's line reverted, as at 50705c972, it waited 8,059 ms and used it.
  • A restart at the heap ceiling. The next daemon is launched before the old process exits, and tries for the lock for one second. No test of this branch restarts a real daemon that way.
  • One fix has no test of its own: d100d92f8 stops removing the holder record before it is replaced. The gap it closes is microseconds wide, and the tests of the atomic replace it relies on are main's.
  • The folder watch was measured in idle Node processes: restored 200 of 200 times within 1 s on both systems. It was not measured inside a real daemon, and not on macOS.
  • One timing test on Linux. Of the 78 files at 2cb75efa0 on Linux x64, 1,703 tests passed, 5 were skipped and 1 failed: a code-rule-runtime-lifecycle timing test outside this change, beside another job at load 15. Alone it failed 0 of 10 runs.

Limits that stay.

  • The Rerail home gains locks/daemon.lock, locks/daemon.json and autostart.claim. Against 0.1.4 it gains locks/, which main already makes. Rerail 0.1.4 sharing the home is not locked out and leaves the lock intact (measured at f8240d5ba).
  • Where the engine does not load or the lock file does not open there is no lock: a start or a stop goes on at once, and the engine socket or pipe keeps the daemon to one, as on main.
  • An older build's daemon takes no lock. On Windows it can still run beside a busy daemon of this build, on the fallback pipe. The holder keeps daemon.json naming itself, so hooks reach it.
  • A hook that finds no daemon.json in the second before it is written back drops its event. A hook still looks once and never waits: ask 2 is about that.
  • On Windows a holder that hangs before it binds its engine pipe is not waited for: a start launches a daemon that exits after about a second, naming it.
  • A daemon started in-process, as RerailDaemon.start and the tests do, takes no lock and writes daemon.json once: only the entry point takes the lock.
  • Two processes that replace a stale claim at the same moment can both launch a start. The start lock still lets one of them start a daemon.
  • The record check costs an idle daemon one read of daemon.json a second: the calls of one check take 46 µs on Linux x64 and 75 µs on Windows 11, the median of 2,000, three times.

9. What we ask of you

Ask 1 rules on answer 1.

  1. On #626: a lock per home, taken by every build, or the socket alone? We recommend the lock.
  2. On #626: should a hook wait a second for daemon.json while the lock is held? We recommend yes, as its own change.

Answer 2 asks no ruling. By design: main starts another (the description's "Decision 3").
