# Changelog

## 0.1.0 (unreleased)

First release of Rerail as `@neralabs/rerail`, licensed under Apache-2.0.

### Rules

- Two rule kinds: `file` rules, `rerail.policy/v1` documents whose clauses each report a violation, and `conversation` rules, which match the live conversation semantically or structurally.
- One required `mode` on every rule: `log` records only, `steer` delivers guidance, and `block` is stored, shown, and carried on violations but delivered exactly like `steer` until block enforcement lands; no shipped rule uses `block`. The rules and diagnostics filters take `mode=log|steer|block`.

### Semantic monitor

- Native Model2Vec embeddings and cosine matching against resident compiled rule references, using the bundled, pinned INT8 `minishlab/potion-base-8M` model; runtime matching makes no network requests.
- Conversation rules over `assistant-text`, `user-input`, and `tool:<name>` sources at sentence, message, turn, and tool-call boundaries, with `once`, `always`, and `after-gap` repeat policies.
- Structural tool-call rules: a conversation rule's `match` may instead be a condition in the code-rule DSL's vocabulary (`regex`, `eq`, `contains` combined with `all`/`any`/`not`) over `text`, `tool.name`, `input`, or one string argument such as `input.command`. Structural rules never embed, and the engine validates their regexes when a rule is written.
- Generic `mark`, `select`, `project`, and `relate` primitives for custom semantic workflows, exposed in OMP and Pi as the `rerail_mark`, `rerail_select`, `rerail_project`, and `rerail_relate` tools.

### File rules

- The `rerail.policy/v1` code-rule DSL evaluated by a resident native engine over Python, JavaScript, TypeScript, PHP, and Blade sources: regex, AST (ast-grep), and relational clauses with ordered violations, witnesses, optional fixes, and bounded source, node, and witness budgets.
- Python identifiers are NFKC-normalized wherever the engine resolves or compares them, as CPython and Ruff read them; string contents, spans, and `regex` keep the source text.
- AST candidate selection through predicate-aware positional indexes that preserve matcher semantics and incremental reuse. Relations read only the nodes they relate to the roots already selected, remember value tests per node, and narrow `precedes`/`follows` comparisons to the siblings that can match, so nested relations and duplicate-key checks cost linear rather than quadratic work.
- Three audit scopes (`repository`, `touched-files`, `ai-output`) and two run modes (`steer`, `log`). AI-output scope reports only changed post-image ranges, using pre-edit source captured at the host's tool-call boundary; there are no violation baselines or acknowledgements.
- Every audit returns violations, concrete execution failures, and per-clause `coverage` (`complete`, `partial`, or `failed` with reasons).
- One automatic log-only full-repository audit per repository, explicit `repository` and `git-diff` scans, and bounded full-repository budgets (five minutes, 100,000 files or 512 MiB of source, 20 reported failures).
- Repository scans of Git checkouts use the native repository index and a machine-wide content-addressed store (`~/.cache/rerail/`) to restore clean files from previous results; checkout builds keep a private store under `<checkout>/.rerail/`. At most one main instance — the managed installation's daemon — opens the machine-wide store, guarded by an OS lock. Edits after evicting inactive files update the call graph in place instead of linking it again.
- An opt-in rule pack of TSLint rule ports (`code-rule-dsl/rules/opt-in/tslint/`) with the conformance harness in `conformance/tslint/` that scores each port against TSLint's own test fixtures.
- Opt-in cyclomatic complexity rules (`code-rule-dsl/rules/opt-in/complexity/`), mode `steer`: `complexity:cyclomatic-python`, `complexity:cyclomatic-typescript` and `complexity:cyclomatic-javascript` flag a function whose cyclomatic complexity is above 6, with lizard 1.24.0's decision points and without its tokenizer defects; test files are not scored. A corpus lizard scored proves the counting and each deviation, and a function-by-function comparison on jinja, click and marshmallow matched lizard on every function it reads correctly. The violation names the number: `Cyclomatic complexity 8 (limit 6). …`. With the `ai-output` scope they reproduce the Metrics-in-the-Loop study's complexity feedback; `docs/rule-packs.md` says how and where they differ.
- A `count` can bind its value for the violation message: `as` names a metavariable and `offset` adds a constant, so `count: { has: …, min: 6, as: "CCN", offset: 1 }` with the message `Cyclomatic complexity $CCN (limit 6)` reports one plus the number of matching nodes. A count with `as` walks to the end instead of stopping at `min`; when its value is unknown (a source-partial subtree), the clause reports nothing.
- A language-pack conformance harness in `conformance/languages/` (`npm run conformance:languages -- --pack <pack>`): ported upstream linter rules are scored TP/FP/FN through the production workspace against the upstream rule fixtures and the linter's output on pinned corpora, with reports under the common `rerail.language-conformance/v1` header.

### Rule packs

- A rule pack (`policies/rule-packs/<id>.json`) groups rules that already ship, with a title and a group for each rule and a match definition (file globs or `package.json` dependencies) that explains which repositories it fits; it adds no rules of its own. The match definition is optional, and a pack without one is never recommended, so set-up never adds it: complexity runs only in repositories that add it. Two packs ship: TSLint, the 74 golden TSLint ports, and complexity, the three cyclomatic complexity rules, chosen by hand.
- `recommendRulePacks` matches a repository's files and manifests against each pack locally, with no model and no network, and returns each fitting pack with its rule count, the folder it fits (a language pack in the folder where it matched, a repository pack for the whole repository) and the reason it matched. Read-only daemon operations and MCP tools `rule_packs_list` and `rule_packs_recommend` (which takes a target); listed rules carry `packId`. See `docs/rule-packs.md`.

### Rule catalog and database

- One SQLite database per Rerail home (`$RERAIL_HOME/rerail.sqlite`) holds repositories and their checkouts, rule attachments and settings, your rule library, and every repository's sessions, events, work links, audits, and audit requests; the schema is defined as Drizzle tables.
- Rules belong to repositories. A repository is keyed by its normalised `origin` (or sole) remote address, `remote:<host>/<path>`, else `clone:<clone id>`, with aliases for renames and mirrors, so every clone and worktree of one remote shares its rules; checkouts are recorded under their real Git top level. A repository is Not set up until its first configuration, and a repository that is not set up records sessions but runs no rules.
- By Rerail rules are read from the package and run only where a repository adds them or their pack; rules created by you live in a library, once per machine, and run only where added. Either can be added for the whole repository or one folder. Editing a By Rerail rule stores a copy in the library, added where the original was, with the original switched off there.
- Rule settings turn a rule or pack on or off or change its mode for the repository or one checkout, per folder. Per field, this checkout wins, then the checkouts containing it, then the repository, then the deepest folder, the rule before its pack, the pack's starting value and the rule's default. Edits made through the daemon, the UI, or MCP apply to the next sample or tool call in every open session.
- Each file is judged by the checkout that owns it: a declared submodule or a started, set-up recorded checkout judges its own files, and any other nested `.git` is judged with the checkout around it. Conversation rules come from the session's starting folder.
- `rerail rules export` / `rerail rules import` move the library and each repository's configuration by hand; `rerail reset` deletes the current repository's history and keeps rules; `rerail seed` writes mock data. See `docs/rule-scoping.md`.
- JSON `.<harness>/conversation-rules.json` files remain a secondary source, applied only where Rerail is started and the repository is set up; a rule the repository's configuration holds with the same id, on or off, wins.

### Daemon, API, and UI

- `rerail daemon start`, `rerail daemon stop`, `status`, `ui`, and `session`: one background daemon that owns the resident engine, serves the rules UI, an HTTP API under `/api`, its OpenAPI 3.1 document, and a stateless MCP Streamable HTTP endpoint at `/mcp`, all generated from one operation registry.
- Audits, violations, repository audits, audit settings, and audit requests are exposed as `audits_list`, `violations_list`, `repository_audits_list`, `repository_audit_entries_list`, `audit_settings_get`/`audit_settings_update`, and `audit_requests_create`/`audit_requests_list`.
- The daemon serves every repository on the machine, and its operations name their target: a `repository`, `checkout` and `folder`. Repository operations and MCP tools: `repositories_list`, `repository_context_get`, `repository_rules_get`, `repository_settings_set`, `repository_attachments_set`, `repository_start`, `repository_stop`, `repository_link` (people only), `rerail_rules_list` and `library_rules_list`/`get`/`upsert`/`remove`. `rules_activity`, `sessions_list`, `violations_list`, `audits_list` and `repository_audits_list` take an optional `repository` and are machine-wide without it.
- The MCP bridge sends `x-rerail-caller-cwd`, so a coding agent's calls default to its checkout. A coding agent may change its own worktree's settings, set a repository up, and add a rule it created or its copy of a By Rerail rule; anything else answers `403 agent-not-permitted` with the dashboard URL.
- Loopback-only by default; DNS-rebinding protection through `Host` and `Origin` checks, `--allow-remote` for any other bind address, and framing protection on the served page.
- A static rules UI (plain HTML, CSS, and ES modules, no toolchain) with Rules, Sessions, Settings, and Diagnostics pages, conditional GETs, and paginated, server-filtered diagnostics. It opens scoped to a repository (`?repository=<key>&checkout=<path>`), with a repository picker, Not set up, and "This worktree | Repository" changes.

### Harness integration

- OMP and Pi extensions, and Claude Code, Codex, and Cursor lifecycle hooks, all sharing one transport-neutral event runtime; command hooks reach the daemon's resident engine over an owner-only Unix socket or Windows named pipe, and the daemon autostarts on first use (`RERAIL_AUTOSTART=0` opts out).
- Rerail is off in every repository until it is started there. `/rerail-start` and `/rerail-stop` (OMP, Pi, Claude Code, Cursor) or `rerail start` / `rerail stop` (terminal and Codex) turn it on or off in the current checkout and the checkouts inside it, or with `--repository` in every checkout of the repository. Set-up and rules belong to the repository; on and off belong to each checkout. Starting a repository that is not set up sets it up: it adds the recommended rule packs (`--no-packs` adds none; in OMP and Pi, `/rerail-start` asks). `rerail state` prints `started`, `stopped` or `not-set-up`.
- Per-session event lanes, tool-call correlation by native call ID, preimages and pending calls that survive daemon restarts, and shell-write discovery at turn checkpoints.
- The persistent `RERAIL-EVENTS/1` stream (`rerail events`) for out-of-process harnesses.
- One command set for every coding agent: `/rerail` (what Rerail is doing here, then every command), `/rerail-ui`, `/rerail-create`, `/rerail-stop`, `/rerail-start`, `/rerail-update` and `/rerail-rage-quit`. Claude Code and Cursor get command files, Codex gets `$rerail-*` skills, and OMP and Pi register them natively; `/cosine-rules` and the `conversation_rules` tool remain in OMP and Pi. Settings, scans, status, update checks, rollback and reset are CLI commands (`rerail settings`, `scan`, `status`, `update check`, `update rollback`, `reset`). In Claude Code, `/rerail-rage-quit` never runs the removal without Claude Code's own confirmation.
- `/rerail-create` creates a rule in your own words. The coding agent drafts it, tests it with `rerail rules test <draft.json> [--json]` (it validates the rule, runs its caught and passed cases and counts matches across the repo, without storing anything), reads it back, and adds it with `rerail rules add <draft.json>` only after you confirm. `rules add` stores the rule in your library and adds it, on, to this repository (at the whole repository, or the draft's `folder`), setting a repository that is not set up up with just that rule; it refuses to replace a rule by Rerail.
- Steers read as one line and a link: `▲ Rerail · <rule>  Steered.`, then the guidance with its location, then `Why? → <dashboard>/#rule/<id>`, scoped to the repository and checkout when the daemon knows them. Claude Code and Codex also show you that one line; Codex delivers a steer with the tool result; Cursor asks the coding agent to pass the line on.
- In a started repo the coding agent is told at session start that Rerail is there, how many rules are on, what a steer looks like, and the session's dashboard link; in a started repo that is not set up it is told that no rules are checked and that you can set it up with `/rerail-start`.
- In-session presence: an OMP, Pi and Claude Code status line that reads `Rerail ● 26 rules`, adds `steered 3×` only once Rerail has steered, and says `Rerail ○ not on here` where Rerail is stopped, `Rerail ○ not set up  ·  rerail start` in a started repository that is not set up, and `Rerail ✕ not running` when no daemon answers. The rule count links the rules page scoped to this repository and checkout.

### Installation and distribution

- `npx @neralabs/rerail setup` installs a managed version under `~/.rerail/versions`, writes the `rerail` launcher, registers every detected harness with backed-up, idempotent edits, and starts the daemon; `rerail install --remove` takes the registrations out again, stops the daemon, and moves `rerail.sqlite` into a dated backup.
- Explicit updates only: `rerail update` resolves an npm dist-tag (`latest`, `beta`, `next`), validates the native engine and a real event-stream round-trip before activating, copies the database to `rerail.sqlite.pre-update` first, and keeps the previous version for `rerail update rollback`.
- Signed customer activation profiles (`rerail activate`, online or offline) with device keys in macOS Keychain, Linux Secret Service, or Windows Credential Manager.
- Prebuilt native engines for macOS, Linux glibc, and Windows MSVC on arm64 and x64; the Windows engines link the C runtime statically.
