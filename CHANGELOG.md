# Changelog

## 0.1.0 (unreleased)

First release of Rerail as `@neralabs/rerail`, licensed under Apache-2.0.

### Internal testing

- The release is code rules in `log` or `steer` mode, the dashboard, and the `/rerail` commands. Full-repository scanning (`rerail scan`, explicit audit requests, the automatic first repository audit, repository audit baselines), conversation rules (cosine and command), `/cosine-rules` and the `conversation_rules` tool, the `rerail_mark`/`select`/`project`/`relate` tools, `block` mode, activation profiles and `rerail events` stay in the code for internal testing: each is tagged `Internal testing:` where it is defined, and its CLI usage, MCP tool, and OMP and Pi tool and command descriptions start with `[Internal testing]`. README.md's Internal testing section lists them.

### Rules

- Two rule kinds: `code` rules, `rerail.policy/v1` documents whose clauses each report a violation, and `conversation` rules, which match the live conversation semantically or structurally.
- One required `mode` on every rule: `log` records only, `steer` delivers guidance, and `block` is stored, shown, and carried on violations but delivered exactly like `steer` until block enforcement lands; no shipped rule uses `block`. The rules and diagnostics filters take `mode=log|steer|block`.
- Vue single-file components (`.vue`) are a supported code-rule language: rules name tree-sitter-vue's kinds, and with `ast.embedded: "script-block"` the ECMAScript kinds of the program a component's `<script>` blocks and template expressions make, and read scope, values and arguments with ECMAScript's semantics; `calls` and `formatArgs` are refused, as for ECMAScript; `suppress.eslint` honours ESLint directives in scripts and eslint-plugin-vue's template comment directives.

### Semantic monitor

- Native Model2Vec embeddings and cosine matching against resident compiled rule references, using the bundled, pinned INT8 `minishlab/potion-base-8M` model; runtime matching makes no network requests.
- Conversation rules over `assistant-text`, `user-input`, and `tool:<name>` sources at sentence, message, turn, and tool-call boundaries, with `once`, `always`, and `after-gap` repeat policies.
- Structural tool-call rules: a conversation rule's `match` may instead be a condition in the code-rule DSL's vocabulary (`regex`, `eq`, `contains` combined with `all`/`any`/`not`) over `text`, `tool.name`, `input`, or one string argument such as `input.command`. Structural rules never embed, and the engine validates their regexes when a rule is written.
- Generic `mark`, `select`, `project`, and `relate` primitives for custom semantic workflows, exposed in OMP and Pi as the `rerail_mark`, `rerail_select`, `rerail_project`, and `rerail_relate` tools.

### Code rules

- The `rerail.policy/v1` code-rule DSL evaluated by a resident native engine over Python, JavaScript, TypeScript, PHP, Blade, SQL, and Rust sources: regex, AST (ast-grep), and relational clauses with ordered violations, witnesses, optional fixes, and bounded source, node, and witness budgets.
- Blade templates are parsed by a Rust port of Forte 1.1.0 (MIT, [docs/blade-parser.md](docs/blade-parser.md)), which reads every template of the BookStack, Filament and laravel/framework corpora without an error, where tree-sitter-blade failed on 218 of BookStack's 325. A Blade rule names Forte's kinds (`directive`, `directive_name`, `directive_block`, `echo`, `raw_echo`, `component`, `attribute`, ...); every `@name` is a `directive`, an application's included. The embedded PHP a rule with `ast.embedded: "compiled-view"` reads, with PHP's kinds and semantic predicates, is the program Blade compiles the template to, byte for byte on those corpora.
- A file whose language embeds another (a Blade template's PHP, a Vue component's script program) is its own tree plus one program per registry `via`, a document of its own in the embedded language's grammar. A query reaches the program with `ast.embedded: "<via>"` (`compiled-view` for `blade`, `script-block` for `vue`; another via is refused), where its kinds, patterns and utilities are the embedded language's and its witnesses, captures and fixes map to the file's bytes. The rule key `embedded` reaches the program from a node of the file's own tree (some program node within the node's range matches), running its rule in a fresh environment, as `parse` does, and exporting what it binds to the host rule with the file spans the program nodes stand for. Outside a `parse`, `host` leads from a program node back to the innermost node of the file's own tree covering it and, like `host` inside a `parse`, binds nothing: it runs in the host environment as the enclosing `embedded` began (fresh under `ast.embedded`) plus the program rule's captures, so `host: { compare: … }` compares a host capture with a program capture. The schema refuses `embedded` in a rule over the program, on a language that embeds none and inside `parse`, and `host` outside `parse` on the file's own tree.
- Python identifiers are NFKC-normalized wherever the engine resolves or compares them, as CPython and Ruff read them; string contents, spans, and `regex` keep the source text.
- AST candidate selection through predicate-aware positional indexes that preserve matcher semantics and incremental reuse. Relations read only the nodes they relate to the roots already selected, remember value tests per node, and narrow `precedes`/`follows` comparisons to the siblings that can match, so nested relations and duplicate-key checks cost linear rather than quadratic work.
- Three audit scopes (`repository`, `touched-files`, `ai-output`) and two run modes (`steer`, `log`). AI-output scope reports only changed post-image ranges, using pre-edit source captured at the host's tool-call boundary; there are no violation baselines or acknowledgements. Automatic audits default to `ai-output`: an edit to one function of a file that already breaks rules elsewhere is told only about what its own lines break. An edit made without a captured preimage (a shell write, a Codex `apply_patch`) takes the text the session last changed the file to (the most recently changed 64 MB are kept), else its Git index or `HEAD` blob (never fetched from a partial clone's remote), whichever has the file's digest from before the change; without one, that edit reports its whole file, and the file's later edits report only their own lines. When a newer edit of a file overtakes an earlier one before its steer reaches the agent (it supersedes the queued evaluation, or its revision drops the queued steer, as happens on Claude Code, Codex and Cursor when an evaluation outlasts the tool result), the newer edit reports both edits' lines, so the violation still reaches the agent once unless the newer edit removed it.
- A steer never becomes the person's message when the coding agent compacts its context. In OMP and Pi a steer from an edit's own check rides that edit's tool result instead of a `rerail.rule` custom message, which both hosts count as the start of a turn and Pi shows its summarizer as the user; Rerail's `session_before_compact` handler folds a split turn that a Rerail message (a later steer, the session-start note) leads back into the history and labels every Rerail message as an automated rule check, not the user (OMP registers it only once Rerail attaches in a started repository, since any such handler turns off OMP's speculative compaction). Claude Code no longer gets a held steer at `UserPromptSubmit`, where it rode the person's own turn, but at the next tool call; Codex no longer holds `Stop` open with the steer as a user-role `<hook_prompt>`: `Stop` shows the person's line and the steer reaches the agent as developer context with the next hook, led as a late steer.
- Experimental, off by default (`RERAIL_EXPERIMENTAL_STEER_STRATEGIES=1` in the environment of the daemon, or of Pi when it runs Rerail in process; otherwise every steer is a `message`): three code-rule steer strategies, set per checkout in the audit settings as `steerStrategy` (stored only when it is not `message`, so a release that reads `{ scope, mode }` strictly still reads every other row) (`rerail settings --steer-strategy`, `PATCH /api/sessions/{id}/audit-settings`; default and what earlier settings read as: `message`), so their effect on agents can be measured: `message` sends the steer as its own message, as before; `rewind` rolls back an edit whose own check steers while its tool result is still being answered (every captured file back to its preimage, a file the edit created deleted, all or none) and puts the steer, saying what was put back and to redo the edit following the rule, into that tool call's result; `subagent` sends the steer ending with an instruction to hand the fix to a subagent (`rerail_fix` in Pi, which Rerail registers and which runs a child `pi -p`; `task` in OMP; `Task` in Claude Code and Cursor; `spawn_agent` in Codex) and keep to the agent's own task. In Pi and OMP a steer sent as a message is a custom message, which their compaction takes for the start of a turn: a split-turn summary then reads the steer as the person's "Original Request" and the agent loses its task; a rewound steer is part of the tool result and starts no turn. `benchmark/steer-strategy.ts` (`just rerail-steer-strategy`) runs every strategy on a real harness and reports task completion, steers, rollbacks, violations left, subagent calls, time, tokens and, for Pi and OMP, how often a split-turn compaction would start at a steer.
- Every audit returns violations, concrete execution failures, and per-clause `coverage` (`complete`, `partial`, or `failed` with reasons).
- A file whose syntax-error regions cover half of its bytes or more is not read: no AST clause runs there, sound or not, and each reports `source-incomplete` with `file did not parse: error regions cover N% of it, first at line L, column C` instead of a `source-partial` that looked like a clean file (a Flow-annotated `.js` file tree-sitter reads as one ERROR, prose saved as `.js`). Every evaluation path reports that message with the file's path: the workspace and stateless runtimes, local clauses and cross-file `select_when` queries; `isUnreadFailure` recognizes it. `rerail rules test` reports a case whose file a clause could not check as `not checked (<reason>)`, never as passed, also where the failure names no file, and lists the repository files the rule could not check; the conformance runner counts unread files under `syntaxErrorFiles`.
- A `.php` file's inline text (HTML, `<script>` blocks) is no PHP code to a rule: tree-sitter-php parses a same-length view of the file where text outside `<?php … ?>`, `<?= … ?>` and short `<? … ?>` tags, and the data after `__halt_compiler();`, is blanked, PHP's lexer deciding where PHP ends (strings and the strings their interpolations nest, heredocs and nowdocs, comments that a `?>` ends), a `<?= ` before `$`, `(` or a literal reads as `echo` (before a name the tag is blanked, its expression a statement), and a mid-file `?>` keeps its implicit `;` where a statement needs it (after a closure or `match` too); spans, text and lines read the file. A template such as `<?php if ($a): ?><p>…</p><?php endif; ?>` reads without syntax errors instead of skipping most PHP rules, and JavaScript's `eval` after `?>` is no `Squiz.PHP.Eval` finding. Stored PHP tapes are parsed again once.
- TypeScript and TSX read three more constructs without syntax errors (`native/grammars/tree-sitter-typescript/PATCHES.md`, Patches 4-6): variance annotations on type parameters (`interface I<out T>`, `class C<in out T>`, `<const in T>`), a function type's parameter named by a type keyword (`(any) => void`, `Record<number, (string) => void>`, `(unknown, x) => void`), and a member named `in`, `instanceof` or `in_point` on the line after another in an object type, interface or class (`a: typeof b⏎ instanceof: typeof c`). Each failed before and took its declaration out of every AST clause's reach. Node kinds and fields are unchanged; stored tapes are parsed again once, as the grammar build id changes.
- TSX reads a bare `&` in JSX text as text, as TypeScript does (`<span>Help & Support</span>`, `{a} & {b}`, `<p>&nbsp</p>`; `native/grammars/tree-sitter-typescript/PATCHES.md`, Patch 7); only a complete character reference such as `&amp;` is an `html_character_reference`. Such a file failed to parse before and lost the element around the `&` to every AST clause: 101 TSX files of the Next.js examples, shadcn-ui and vscode corpora parse now. TypeScript and TSX also take the JavaScript fixes (Patches 8-14, 20 and 21): import attributes on re-exports (`export * from 'y' with { type: 'json' }`), `yield` as a label or a name where no yield expression parses (`yield = 2`, `yield.x`; in a generator `yield++⏎x` still yields `++x`), parenthesized destructuring targets (`({a: (/**/b)} = c)`), a line starting with `*`, `+`, `-` or a member named `instanceof` after a declarator, a type or a class field (`var a⏎+b`, `a: string⏎*gen() {}`), Unicode whitespace such as U+3000 and every line terminator (a lone CR, U+2028) where a semicolon may be inserted, and a comment in a TSX closing tag (`<></* c *//>`, which Babel reads and `tsc` rejects) parse without syntax errors; a U+00A0 on a TSX line of its own is text whatever the locale; a `{` at the start of a statement or arrow body is a block with a label, not an object (`if (a) { b: 1 }`), and a line break after an arrow function's block body ends the statement (`f = () => {}⏎[1, 2].map(f)`). TypeScript syntax that failed to parse now does (Patches 15-19 and 22): an import type followed by `[]`, an indexed access or type arguments (`import('x').T[]`, `import('x').I<T>`, `import('x')<T>`), a tuple member named by a type keyword (`[spoken: string, symbol: string]`, `[void: number]`), an anonymous default function signature (`export default function (x: string): string;`), `accessor` after `static`, `abstract` or `override`, `export type * from 'x'`, and a member named `abstract` (`{ abstract: Set<string> }`); 32 more files of the vscode and Next.js corpora and the packs' TypeScript fixtures parse, and no file gains an error. A call or construct signature with type parameters may follow another member on the next line of an interface or object type (`): Promise<T>⏎<T extends B>(r: R): Promise<T>`, as hono writes it; Patch 23), `return` and `yield` take no operand after a line break (`yield⏎(a)` yields nothing), and a block comment holding a line break counts as one (`a = 1 /*⏎*/ b = 2`; Patch 24). Node kinds and fields are unchanged; stored tapes are parsed again once, as the grammar build id changes.
- TypeScript and TSX read two more constructs TypeScript accepts (`native/grammars/tree-sitter-typescript/PATCHES.md`, Patches 25 and 26): a static index signature in a class (`static [k: string]: number;`, an `index_signature` with an anonymous `static`; an interface still rejects it), and `global { … }` without `declare`, as inside `declare module 'x' { … }`, which is an `internal_module` named `global`, as TypeScript's `ModuleDeclaration` is (`declare global { … }` stays an `ambient_declaration`, and `global` stays a name elsewhere). Like `declare global`, the augmentation binds no name in the scope model, nor do its declarations, and `typescript-eslint-no-namespace` does not report it, as typescript-eslint does not. Both were parse errors that took the file from every AST clause. Node kinds and fields are unchanged; stored tapes are parsed again once, as the grammar build id changes.
- JavaScript and JSX (`.js`, `.jsx`, `.mjs`, `.cjs`) are parsed with a vendored, patched tree-sitter-javascript 0.25.0 instead of ast-grep's bundled copy (`native/grammars/tree-sitter-javascript/PATCHES.md`, Patches 1-15). Unpatched it builds the same trees. It now parses these without syntax errors: a bare `&` in a JSX attribute string or JSX text, import attributes on re-exports (`export * from 'y' with { type: 'json' }`), `for (await using r = f(); ;)`, parenthesized destructuring targets (`({a: (/**/b)} = c)`), `yield` as a label or a name where no yield expression parses (`yield = 2`, `[yield] = a`, `yield.x`), and a line starting with `[`, `*`, `+` or a member named `instanceof` after a declarator or class field (`var a⏎+b`, `#x⏎[y]`), Unicode whitespace such as U+3000 or a lone CR line break before an automatic semicolon, a reserved word or `this` in a JSX name (`<a class="x" />`, `<this.props.tag />`), a comment in a closing tag (`<></* c *//>`), and a block comment holding a line break, which ends the line (`a = 1 /*⏎*/ b = 2`). Three kinds of silently wrong tree are fixed: a `{` at the start of a statement or arrow body is a block with a label, not an object (`if (a) { b: 1 }`), a line break after an arrow function's block body ends the statement (`f = () => {}⏎[1, 2].map(f)`), and a line break right after `return` or `yield` ends the statement before its operand (`return⏎[a]` is `return; [a];`). Over the Next.js, React and TypeScript corpora and the packs' fixtures, 56 `.js`/`.jsx` files that had syntax errors now parse, including all 13 failing Next.js plugin fixtures. No file gains an error. Node kinds and fields are unchanged. Stored tapes are parsed again once, because the grammar build id changes.
- A JavaScript `using` or `await using` declaration binds its names in its block, as `const` does, for every clause that reads scopes (`no-undef` no longer reports `r` in `for (await using r = open(); ;) { r.close(); }`).
- One automatic log-only full-repository audit per repository, explicit `repository` and `git-diff` scans, and bounded full-repository budgets (five minutes, 100,000 files or 512 MiB of source), whose stop is always listed; failures to read a file never stop a scan. At most 20 failures that fail the audit and 20 gaps are listed; the audit record and session summary keep the total (`failureCount`, `unlistedFailureCount`), and the session footer says `audit failed (N failures)`. Files Rerail reads only in part or not at all, because of syntax errors (`source-partial`, a rule that needs the whole file skipped, `file did not parse`, or a file every rule failed on for its syntax) or because they are binary, are listed but never fail a repository audit, so a large checkout with a few such files completes its baseline; the list no longer claims a scan stopped when it read every file. A touched-files or `git-diff` scan still fails on any of them. An interrupted repository audit is run again by the next session in that checkout; a failed one only when it could now come out differently (it failed only for files read in part, or the rules changed since), so a budget or engine failure does not rerun at every session start; a completed one never.
- No per-file limit is a fixed cut-off for a large file: each file's shared work (parsing, its tape, the anchor index) and each clause's own work allowance grow with its size, and a clause may visit `maxVisitedNodes` nodes or `maxVisitsPerNode` (16) per node of the file, whichever is more. Each clause runs under an allowance of its own: a costly clause fails alone instead of failing every rule on the file and dropping the findings of those that finished. In one evaluation of a file its clauses together may spend eight allowances, which bounds its total work. A rule running out of its own allowance in an evaluation of all of a file's rules is stored as the content's result and read back by later scans instead of re-run; a failure that depends on what else ran (the file's shared work, the ceiling, or an evaluation of some of its rules) is evaluated again by the next scan, as is an evaluation the workspace closing or the inline deadline cut short. Anchor selection spends one unit per 256 steps across all its loops, and a lookup of a binding's node in a taped tree searches by position instead of reading wide child lists.
- A rule that runs out of work on a file is a coverage gap, not a failed audit: its failure says what would let it finish (simplify the rule, or exclude generated or vendored files from its scope), the failure list keeps one failure of every such rule past its cap, and the session footer counts such rules ("2 rules ran out of work"). A rule the file's work stopped (`file-budget-exceeded`: its shared work, or the ceiling the rules before it spent) is a gap advised to exclude or split the file, not counted as a rule that ran out. A file every clause failed on is a blind file: reported once (one failure marked `blind`, never cut from the list; `blindFiles` and `blindFileCount` on the audit record; "N files not checked" in the footer); blind for its work it is a gap, blind for its syntax it is a file read in part (it fails a touched-files scan, not a repository audit). A clause that finds more than `maxWitnesses` fails with its own code, `witness-limit`: it read the file, so it is neither a gap nor a blind file, and it fails the audit.
- Repository scans of Git checkouts use the native repository index and a machine-wide content-addressed store (`~/.cache/rerail/`) to restore clean files from previous results; checkout builds keep a private store under `<checkout>/.rerail/`. At most one main instance — the managed installation's daemon — opens the machine-wide store, guarded by an OS lock. Edits after evicting inactive files update the call graph in place instead of linking it again.
- Concurrent Rerail processes share the content store without failing scans. Publishing a checkout's Git trees resolves entry names through an index, so a 14,000-file checkout attaches into a fresh store in under half a second instead of 20 and no longer holds the store's writer for seconds; foreground writers wait out a busy store with jittered backoff for up to 10 seconds, which one apply, one attach and one scan completion each share across all their writes, while background maintenance tries once and again on its next pass; opening an up-to-date store takes no write lock; and a store still busy after that costs repository reuse (`repository reuse is disabled: content store busy …`), never the scan: an apply keeps its results, and the files it could not publish or remove from the store are published or removed by the next apply or scan completion that finds the store free, or, for removals, when the workspace closes. At most 64 MiB of those files' sources stays in memory; past that a file keeps only its results and is not reused (`storageReleasedFiles`), and a file whose source is then needed but gone is reported `source-incomplete` instead of failing the scan. A workspace whose write waited out the deadline leaves the store alone for 30 seconds and says so once per busy period (`repository reuse is paused: content store busy …`), so a scan pays that wait once, not once per batch, and its apply metrics count the retries and the files left unpublished (`storageUnpublishedFiles`). The native workspace's unused `maintainStorage` is removed.
- One language registry, `languages/<id>.json` (`rerail.language/v1`, [language packs](docs/language-packs.md)): each language's family, dialects (file suffixes, parser, grammar, tape tag), per-capability support, suppressions, embedded languages and status. The engine generates its language tables from it at build time and the host reads a module generated from it.
- SQL is supported (`languages/sql.json`, family `sql`): `.sql` files parse with DerekStride's tree-sitter-sql 0.3.11 and Rerail's patches (`native/grammars/tree-sitter-sql/PATCHES.md`), one generic dialect for PostgreSQL, SQLite, MySQL and ANSI files, read as SQLFluff 4.4.0 reads them and as PostgreSQL where the dialects differ. Its adapter (`adapter/sql.rs`) folds names as PostgreSQL does and reads scope (query blocks: `binds` forms `relation`, `cte` and `target`, scope `query`; `resolves.unresolved` as RF01 and `binds: { used: false }` as AL05 report), values where PostgreSQL and SQLite agree, call arguments as PostgreSQL 18.6 binds them, and SQLFluff's `-- noqa` comments (`suppress.sqlfluff`, matching a rule's code, name, aliases and groups, globs included). `calls` and `formatArgs` are `refused`: SQLFluff reads neither, a routine's body is another language's string, and ISO SQL has no format function. Outside their declared divergences, the SQL pack's 22 SQLFluff ports (`packs/sql/`) report every finding of SQLFluff's fixtures and nothing else, and on the four pinned corpora they report nothing SQLFluff does not (a result of those recordings, not a guarantee for other SQL), where they miss findings mostly in the files the grammar cannot parse cleanly (`packs/sql/README.md`). All 22 are candidates (`packs/sql/candidates/rules/`) until they pass the V1 rule validation gates: they are scored and reported but never gate a check or ship, and the pack lists no rules, so it is never recommended. If PG01, PG02 and AM02 ever ship they should start off: they depend on SQLFluff's dialect, which Rerail does not detect (every `.sql` file is read as one dialect), PG01 and PG02 are PostgreSQL-only and AM02 is skipped by SQLFluff for PostgreSQL.
- One engine adapter per language family (`native/src/code_rule_dsl/language/adapter.rs`): each family's scope, values, call arguments, call graph, format strings, suppressions and refusals sit behind it, dispatched by a macro generated from the registry, so adding a family is a registry entry and one adapter. The engine alone refuses what a rule's language lacks; the host schema checks shapes only, and every rule write compiles the rule in the engine, refusing a rule that breaks only a language restriction as `invalid-rule` with the engine's reason.
- Cyclomatic complexity rules (the `complexity` pack, `@neralabs/rerail-pack-complexity`), mode `steer`: `complexity-cyclomatic-python`, `complexity-cyclomatic-typescript` and `complexity-cyclomatic-javascript` (`complexity:cyclomatic-<language>` in 0.1.0-next.0 and 0.1.0-next.1, so a setting saved for the old id no longer applies) flag a function whose cyclomatic complexity is above 6, with lizard 1.24.0's decision points and without its tokenizer defects; test files are not scored. A corpus lizard scored proves the counting and each deviation, and a function-by-function comparison on jinja, click and marshmallow matched lizard on every function it reads correctly. The violation names the number: `Cyclomatic complexity 8 (limit 6). …`. With the `ai-output` scope they reproduce the Metrics-in-the-Loop study's complexity feedback; `docs/rule-packs.md` says how and where they differ.
- A `count` can bind its value for the violation message: `as` names a metavariable and `offset` adds a constant, so `count: { has: …, min: 6, as: "CCN", offset: 1 }` with the message `Cyclomatic complexity $CCN (limit 6)` reports one plus the number of matching nodes. A count with `as` walks to the end instead of stopping at `min`; when its value is unknown (a source-partial subtree), the clause reports nothing.
- Rules read comments in every supported language: `kind: "comment"` and `regex` over the comment's text, with its position read through `follows`/`precedes` (a leading comment is the declaration's preceding sibling) and `layout` (attached and trailing comments). In Blade, `kind: "comment"` matches `{{-- --}}` and `<!-- -->`, and under `ast.embedded: "compiled-view"` the embedded PHP's comments, where it also stands beside `parse: { grammar: "phpDoc" }`. The reference's Comments section lists each language's line, block and doc comment openings and how to compare a comment's text with code.
- A language-pack conformance harness in `conformance/languages/` (`npm run conformance:languages -- --pack <pack>`): ported upstream linter rules are scored TP/FP/FN through the production workspace against the upstream rule fixtures and the linter's output on pinned corpora, with reports under the common `rerail.language-conformance/v1` header. A port may be scored on part of the fixtures only (`fixtures` globs: one document per option set of a rule), and ports under `candidates/` are scored and reported but never fail the gate.
- Language support foundation: `Family` and `GrammarDialect` are generated from the language registry, so a supported language adds no hand-written enum arm. Rust takes tape tag 9, SQL tag 10 and Vue tag 12. Embedding goes through one seam (`Embedder`): a file holds at most one embedded program per `via`, a guest document beside the file's own tree with its own grammar's kinds, its own text and the segments mapping that text to the file's bytes, so every tape, the file's and each program's, keeps tree-sitter's invariants (siblings in order, children within their parent). Every position a rule reports or carries across documents (witnesses, captures, fixes, captures exported out of a parsed literal or a program, syntax errors, suppression covers, `layout`'s lines and a transform's `line`) is placed in the file through one seam (`origin`): each document is an `Origin` into the one it was read from, so a rule over a program counts the file's lines, not the program's. A program node written out of file order stands for each file range apart (`FileRanges`): syntax errors, suppression covers, `host` and `embedded` read every one, and a witness or capture reports the range the node starts in, never a range widened over bytes it does not stand for; zero-width positions are owned half-open (a boundary belongs to the range starting there, the file's end to the last). A Blade template's tape holds its syntax errors as Blade reads them as `ERROR` leaves where they lie, as tree-sitter's tapes do, instead of byte ranges beside the records; Forte stopping at its nesting or step limit leaves the template with no tape (`file-budget-exceeded`, `budget-exceeded` in the stateless runtime), not a whole-file syntax error. Each document has its own syntax errors: a clause over a clean program is complete whatever the template's errors, unless the program reads through them (a Blade view does). The tape format moves to v7: every tape holds one source, one grammar and one tree, and a derived document (Blade's compiled view, a Vue component's script program) is a tape row of its own, related to the file's tape by the store's new `file_documents` table, so existing tape caches are rebuilt on upgrade. Suppression kinds sit in one table on each side (`suppression_kinds!` in the engine, `codeRuleSuppressSchema` in the schema). Call names carry their family, and value semantics are owned by `ValueRules`.
- Rust is a supported language: `.rs` files parse with tree-sitter-rust (tape tag 9), and the `rust` family's adapter (`native/src/code_rule_dsl/language/adapter/rust.rs`) answers every capability from syntax alone, each proven against a Rust 1.99.0 recording under `fixtures/rust/`: `scope` (rustc's lexical name resolution and namespaces, `extern` blocks, associated types and `for<'a>` lifetimes included; a name a macro invoked where an item may stand could define, such as `thread_local!`'s, is not unresolved; `resolves.import` lists Rust paths such as `std::env::var`, read through `use` and `extern crate`), `value` (literals and constant expressions as rustc evaluates them, `follow` through a file's `const` items, `type` names such as `u8` and `&str`; an expression nested past 256 levels is unknown), `arguments`, `calls` (a crate's functions by path, `Self::f`, `Type::f` and `self.m()`; what needs types is open, and so is a macro whose expansion may call a crate function: a call in a macro is left open, never absent) and `formatArgs` (style `rust` and the `rustFormat` grammar: the `format_args!` family as rustc binds it, a `<` after a cast's type a comparison as rustc reads it). `suppress.clippy` honours rustc's and Clippy's `#[allow]`/`#[expect]` (with `warn`, `deny`, `forbid`, inner attributes and active `cfg_attr`), and with `msrv` a `#[clippy::msrv]` naming an older Rust. Names in macro token trees and what needs types or macro expansion are not read.
- A violation's `suppress` may name `oxlint` beside `eslint` for TypeScript and JavaScript queries: `oxlint-disable`, `oxlint-enable`, `oxlint-disable-line` and `oxlint-disable-next-line` (and the `eslint-*` forms, which oxlint also reads) silence it as oxlint 1.88.0 reads them, with oxlint's own name matching (a directive name's part after its last `/`, so `react-hooks/rules-of-hooks` silences `rules-of-hooks`) and block directives covering a problem that overlaps them. It may name `biome` too, with Biome's lint rules (`lint/correctness/useHookAtTopLevel`): `biome-ignore`, `biome-ignore-all` and `biome-ignore-start`/`biome-ignore-end` silence it as Biome 2.5.15 reads them, naming `lint`, the rule's group or the rule, with a reason; `biome-ignore` covers the line after it, `biome-ignore-all` the file from its top, and a comment Biome refuses (an unknown category, no reason) silences nothing. Compiling refuses `oxlint` and `biome` outside the ECMAScript languages, and a `biome` name that is no lint rule of Biome's JavaScript analyzer.
- Rerail's own suppression comment, `rerail-ignore`: `// rerail-ignore complexity-cyclomatic-typescript -- generated` (`#`, `/* */`, `{{-- --}}` and `<!-- -->` alike) silences the code rules it names by id, in every supported language, with no opt-in in the rule document and whatever the repository's `suppressions` setting, which governs only linters' comments. It covers a node: the whole file before the file's first code, the next node on its own line, and the code it trails otherwise (after a list element's `,` or a class field's `;`, that element or field, not the list or class body around it). It silences a violation where it is reported and never removes a fact another violation reads: a `require_each`'s evidence and the rows a `budget` counts stay whatever the comments, and a `budget` group's violation is silenced only at the row it is reported at. Regex queries are not silenced by it.
- `suppress.eslint` and `suppress.oxlint` read directives in JavaScript's HTML-like comments (`<!-- eslint-disable-next-line no-debugger`, and a `-->` first on its line) as ESLint 9.39.1 and oxlint 1.88.0 do in a script; `suppress.biome` does not, as Biome 2.5.15 has none.
- A JavaScript or TypeScript query that does not pin `languageOptions.sourceType` reads each file's own module system: `.cjs` and `.cts` files are CommonJS, `.mjs`, `.mts`, `.tsx` and declaration files (`.d.cts` aside, which is CommonJS) are modules, and a `.js`, `.jsx` or `.ts` file follows its nearest `package.json` `type` (Node runs `.ts` files like `.js` ones), else Node's syntax detection (a static `import`/`export` that type stripping keeps, `import.meta`, a top-level `await`, or a top-level `const`/`let`/`class` named `require`, `module`, `exports`, `__dirname` or `__filename` makes a module). A file without any `package.json` stays a module, as in ESLint's default config.
- A JavaScript or TypeScript query's `file` condition reads the file's nearest `package.json`: `file.package` takes `bin` (the file is one of its `bin` targets), `nodeVersion: { subsetOf }` (its configured Node range, from `engines.node`, else `devEngines.runtime`, else `>=16.0.0` as eslint-plugin-n reads it, is a subset of an npm range), `dependsOn` and `path` (relative to the manifest's folder). `file.jsxRuntime` matches the file's JSX runtime: `react`, `other` or `unknown`, from a `@jsxImportSource` (read, as Babel reads it, without the comment's delimiters, so `/*@jsx React*/` counts) naming React, a React wrapper such as Emotion, or another JSX library, a `@jsx React…` pragma, an import of another library's `h` or `createElement`, else the `jsxImportSource` of the package's `tsconfig.json` or `jsconfig.json`, else the manifest's dependencies. No manifest is read in a folder that resolves outside the workspace through a symlink. Hosts send each file's manifest as its `package` (a `nodeVersion` that is not a valid npm range makes it malformed) (none for a file whose folder resolves through a symlink to outside the checkout) and, where a code rule has a JavaScript or TypeScript AST clause, refresh it when a `package.json` or `tsconfig.json`-style project configuration changes; without such a rule those edits start no audit. A touched-files audit of that edit reports the sources it refreshes, and an AI-output audit, which reports the manifest's own changed lines, reports again only a refreshed source whose findings in its own changed lines changed, dropping its stale queued steer, and leaves the others' findings and steers to their own edits. A queued steer such a refresh drops, an edit's or a touched-files audit's, is steered again for the other sources it spoke for, with what each last reported, and a refresh leaves a source whose own edit is still queued to that edit, which reads the facts then on disk. Snapshots, file sets and editors derive it from the `package.json` files they hold. The native binding's `packageFacts(label, absolute, root)` derives that `package` for a file of any dialect (null where its family reads no manifest), `readsPackageManifests(label)` says whether the dialect's family reads one, a workspace's `readsPackageManifests()` whether any of its code rules has an AST clause in such a family, and `nearestPackage(absolute, root)` names the package around any file, whatever family reads it.
- `file.package.serverGraph` matches a file of a package that depends on `next` by whether it is in the Next App Router server module graph: reached from a server page, layout, route or metadata file (with Next's default page extensions, `.tsx`, `.ts`, `.jsx` or `.js`) under `app/` or `src/app/` by static imports, `export … from`, `import()` and `require()` of a string, without passing a `"use client"` module. Imports resolve relative to the importer and through the package's `tsconfig.json` or `jsconfig.json` `paths` (its first 64 patterns, the first 16 targets of each) and `baseUrl`. Hosts send each file's membership, walking each package's graph off the JS thread (the native binding's `serverGraphAsync`) once per edit, and once for all applied sources when new code rules replace the workspace; snapshots, editors and workspaces without host facts derive it from their own files (an editor's edit summarizing again only the source it edits and deriving again only the packages whose graph that, a manifest or a project configuration changes), and an edit that moves a source in or out of the graph (a source's imports or directive, a nested `package.json`, a project configuration) resends the sources already applied whose membership it changes, reading back only those; such a source is routed even outside the code rules' scope. The graph reads what a disk walk reads (no hidden folders or folders hosts ignore, such as `node_modules`, `dist` or `build`, no nested checkout on disk, sources of at most 1 MiB, decoded lossily, at most 20,000 of them and 512 MiB in all), and Next's rule that a root `app/` hides `src/app/`; on disk the walk lists at most 100,000 entries (files and folders of any kind, the folders it skips included), and a project configuration that is a symlink is read where its real path stays inside the workspace; a project configuration that does not parse sets nothing, its `extends` included, is not replaced by the `jsconfig.json` beside it and reports no failure; a package whose source or folder cannot be read on disk, or past those bounds, has no graph, so neither `serverGraph` value holds for its files, until it reads again.

### Rule packs

- A rule pack (`packs/<id>/pack.json`) lists its rule documents, with a title and a group for each rule and a required match definition that says which repositories it fits: file globs, or dependencies in `package.json`, `requirements*.txt`, `pyproject.toml` or `composer.json` (`{ "dependencies": { "ecosystem": "npm" | "pypi" | "composer", "names" } }`). A match is data: a pack holds no code.
- Core ships no rule packs. Each pack is its own npm package (`@neralabs/rerail-pack-<id>`), installed into `$RERAIL_HOME/packs` and read from there, and core lists them by name only (`pack-list.generated.ts`). Each installed pack is checked on its own (package name, `pack.json`, listed documents, core range against the active Rerail, every code rule compiling, no rule another pack holds); one that fails is left out and reported (`rerail packs list`, `rule_packs_list` `skipped`, and the daemon's log when it starts) while the others load. A running daemon follows installs, removals and a change of the active core (`rerail update`) without a restart.
- **Upgrading, if a repository adds `complexity`:** core no longer ships it, so after upgrading run `rerail packs add complexity` (a version with a match, 0.1.2 or later). Until it is installed, repositories that add it report it as unavailable (`missing`) and its rules do not run; their settings for it stay.
- Set-up fetches every Rerail pack from npm under the update channel's dist-tag (`latest` by default, where each new pack version is published; `next` for a pack with no `latest` version) into a staging folder of its own, which it removes, and matches each against the repository only after the person allows it to read it. It lists the fitting packs with their rule counts and why each fits, and says when one replaces an installed version every repository uses; a newer installed version is offered rather than replaced, and an answer naming an older one is refused. Nothing is installed before an answer that installs, and an answer installs only what it carries. "Change rule packs…" (`--answer choose`) picks from every pack it fetched; a coding agent's answer carries the versions shown (`--packs typescript@0.1.1,…`), installed from npm's cache where discovery left them. "Skip, I'll pick packs" reads nothing in the repository: it lists every fetched pack, installs the ones the person picks and adds each for the whole repository without its lint config, or none ("None for now", `--packs none`; `--json` reports the question as `pick-packs`). When npm fails, or a pack installs but is left out or pushes another out, what changed is put back (a pack added from a folder from that folder) and set-up asks again, saying why (no read access, not logged in, registry unreachable, why the pack was left out). `rerail packs list|add|remove|recommend` manage installed packs; `add` takes a pack id or package name at a version, range or tag, or a tarball or folder, and refuses npm options and other specs; npm runs no install scripts.
- Installing packs is one checked change at a time. Set-up's install and `rerail packs add` and `remove` hold a lock on `$RERAIL_HOME/packs` (`.lock`), so two set-ups, or a set-up and `rerail packs add`, never install together. `rerail packs add` now checks what it installed as set-up does: a pack left out (its core range, a rule another pack holds), or one that stops another loading, is put back and the command exits non-zero with why. When npm fails partway, the packs are put back as they were before "Nothing was changed." is said. Set-up names a newer installed pack whose core range excludes the active core instead of offering npm's older one, offers no "Choose rule packs…" when it could fetch no pack, and refuses an answer's version semver cannot read. `rerail update` and `update rollback` name each installed pack the newly active core leaves out by its range. The dashboard's activity view follows an install or removal at once. Poetry's `[tool.poetry.dev-dependencies]` table counts as dependencies for a pack's match.
- Ported rules honour their linter's suppression comments for the upstream rule they reproduce: every ESLint, typescript-eslint and plugin port in the javascript and typescript packs now carries `suppress.eslint`, every ECMAScript port of a rule oxlint 1.88.0 implements carries `suppress.oxlint`, and every one whose ESLint rule Biome 2.5.15 has a rule the same as (`.same()` in its sources) carries `suppress.biome` naming that rule. Pack validation (check 4) fails a port whose linter honours inline directives but whose violations do not name its upstream rule, unless `conformance.json` exempts it with a reason (`suppressionExemptions`; a stale exemption fails too), and a violation whose `suppress.eslint` lacks the Biome rules the same as its ESLint rule.
- Set-up reads the repository's own lint config as data (ESLint's flat `eslint.config.{js,mjs,cjs,ts,mts,cts}`, parsed with `@babel/parser`, never run, and read only when the whole file is data, else `.eslintrc.json`, `.eslintrc` as JSON or `package.json` `eslintConfig` with their `overrides`; `.oxlintrc.json`; Ruff's `select`, `extend-select`, `ignore`, `extend-ignore` and `per-file-ignores` in `.ruff.toml`, `ruff.toml` or `pyproject.toml` and the configs its `extend` names inside the repository) and, on the confirm screen, proposes starting the ported rules those configs turn off as off, for the whole repository or in the folder a config turns them off for, and setting a port's options where the config sets the same upstream rule's options; starting writes them as repository settings. A file Rerail cannot read statically (one that runs code: a function, a statement that changes something, a loop; or one that takes more than 100,000 steps or builds more than 100,000 values to read, as a `const` named twice at each of many levels does) is named, and every rule Rerail ports from ESLint starts off with no options, since Rerail cannot tell which it turns off. Options for every file are not proposed where an entry for some files sets others. A flat config's literal rule entries are read through its exported array, same-file `const`s, spreads, `defineConfig`, typescript-eslint's `config` and `extends`, in ESLint's order; an entry whose value Rerail cannot read without running the config turns the port off, and the shared configs it does not read are named. An `.eslintrc` or `eslintConfig` severity is read in any case (`"OFF"`, `"Warn"`), as ESLint's eslintrc loader reads it; a flat config's only in lower case, as ESLint 9 takes it. Ruff's selectors are applied by specificity and config by config as Ruff applies them, so a rule a more specific or later `select` re-enables stays on; a TOML file whose arrays or inline tables nest more than 64 deep is named as not read. Nothing narrower than a folder turns a rule off. oxlint keys resolve to oxlint's own rules as its config does, so another plugin's rule of the same name never turns a ported rule off. `.eslintrc.js` and YAML configs are named but never run or read.
- `recommendRulePacks` matches a repository's files and manifests against each installed pack locally, with no model, and returns each fitting pack with its rule count (the rules that start on; a pack whose rules all start off is not recommended), the folder it fits (a language pack in the folder where it matched, a repository pack for the whole repository) and the reason it matched. Read-only daemon operations and MCP tools `rule_packs_list` (each pack with its `version`, and `skipped`) and `rule_packs_recommend` (which takes a target); listed rules carry `packId`. See `docs/rule-packs.md`.
- Packs in their own packages under `packs/<id>/` ([pack format](docs/pack-format.md)): `pack.json` names each rule's `document`, and `package.json` declares core as a peer. `test/packs.test.ts` holds every pack to the validation contract: its rules are listed, match their documents and compile; each is proven by examples or a port; examples are caught or pass through the engine; ports agree with the tools' recordings outside declared divergences; the package publishes no validation material and its licence agrees with `licenses/`; every copied file is recorded. Every rule's description meets the description criteria a machine can check (one sentence ending in a period, 200 characters at most, no tool names); its messages are left to review.  Every pack uses one rule id style, lowercase letters, digits and dashes (`eslint-no-empty`): a rule's id is its document's file name and its port's id in `conformance.json`, candidates included, and no two packs share one. A rule for a language core does not read yet is reported `not supported yet` and does not fail. The Python pack (22 Ruff and Bandit ports) is the first to move there; it is not published yet.
- The Rust pack, `@neralabs/rerail-pack-rust` (`packs/rust/`): no rules yet: its 34 code rules ported from Clippy 0.1.99 are candidates until they pass the V1 rule validation gates, scored against Clippy's findings on its UI tests and on pinned ripgrep and tokio checkouts with no unexplained false positive or negative (each disagreement is declared with its evidence in `divergences.json`, [README](packs/rust/README.md)); the pack is never recommended while it ships no rules.
- The Vue pack ships no rules yet: its 24 eslint-plugin-vue ports are candidates (`packs/vue/candidates/rules/`), scored and reported but never gating a check and never shipped, until they pass the V1 rule validation gates. A pack with no rules is never recommended, so setting a repository up adds none of it.
- The PHP and Blade packs ship no rules yet: their 18 PHP_CodeSniffer, PHPStan and Psalm ports and 17 Bladestan, tlint and stillat/blade-parser ports move to `candidates/rules/`, scored and reported but never gating a check, until they pass the V1 rule validation gates. A pack with no rules is never recommended, so setting up a PHP or Blade repository adds neither. The 11 example pairs the ports carried while they shipped stay in each pack's README, and `test/engine/catalog/candidate-examples.test.ts` still checks each one through the engine.
- A pack with no rule that starts on (React and Node.js today) is no longer missing without a word: set-up's confirm question names those that would fit the repository as having no rules yet, "Skip, I'll pick packs" names every such pack, and `rerail packs recommend` lists them under "No rules yet, so not offered".
- Why a pack is left out is said in plain words wherever it is shown (set-up's "Rule packs set-up could not use", `rerail packs list`, `rerail update`, the daemon's log): a core older than the pack's range says the pack needs a newer Rerail and that `rerail update` installs it, a core newer than it says which Rerail the pack is for, and a rule the engine refuses says this Rerail cannot run it and may be older than the pack, before the engine's own words. The reason no longer repeats the pack's name and version, which every place that shows it already prints.

### Rule catalog and database

- One SQLite database per Rerail home (`$RERAIL_HOME/rerail.sqlite`) holds repositories and their checkouts, rule attachments and settings, your rule library, and every repository's sessions, events, work links, audits, and audit requests; the schema is defined as Drizzle tables.
- The file records its compatibility floor in `PRAGMA user_version` (3 in this release) and the migration steps it has run in `schema_migrations`. A writer runs the steps a file has not run in one transaction, so a schema change after this release reaches existing databases instead of asking you to move them aside; a step that adds a column or table keeps the floor, so older versions still open the file, and a read-only open (a hook, the status line) runs such steps first so its readers see the new shape, and is refused with the reason when it cannot write the file. `rerail update` keeps its pre-update copy only for an update that changes the version, recorded with that change, and `rerail update rollback` puts it back when undoing that change after its migrations raised the floor above what the version rolled back to opens; while it does (`rerail.sqlite.restoring`), Rerail refuses to open the database. The copy is put back once and then removed with its record, and the replaced database is kept as `rerail.sqlite.before-rollback` (`.2`, `.3`, … for later rollbacks, never over an earlier one). A database 0.1.0-next.1 wrote (stamped 1, before the migration path) is adopted at the baseline with everything in it. A file written by a newer Rerail, by other software, by 0.1.0-next.0 (stamped 1, in an older shape) or stamped 2 by a development build is refused and left untouched (see `docs/installation.md`).
- Rules belong to repositories. A repository is keyed by its normalised `origin` (or sole) remote address, `remote:<host>/<path>`, else `clone:<clone id>`, with aliases for renames and mirrors, so every clone and worktree of one remote shares its rules; checkouts are recorded under their real Git top level. A repository is Not set up until its first configuration, and a repository that is not set up records sessions but runs no rules.
- By Rerail rules are read from the installed rule packs and run only where a repository adds them or their pack; rules created by you live in a library, once per machine, and run only where added. Either can be added for the whole repository or one folder. Editing a By Rerail rule stores a copy in the library, added where the original was, with the original switched off there.
- Rule settings turn a rule or pack on or off or change its mode for the repository or one checkout, per folder. Per field, this checkout wins, then the checkouts containing it, then the repository, then the deepest folder, the rule before its pack, the pack's starting value and the rule's default. Edits made through the daemon, the UI, or MCP apply to the next sample or tool call in every open session.
- Rule settings take two more fields. `suppressions` (`honour` | `ignore`, on a rule or a pack) decides whether linters' suppression comments (`eslint-disable`, `noqa`, `nosec`, ...) silence a ported rule; a pack's `honourSuppressionComments` is the value its rules start with (`honour` by default). `config` sets a code rule by Rerail's option values for the whole repository, merged per option, checkout before repository; an unknown option or a disallowed value is refused with `400 invalid-setting`, and a stored config that no longer applies quarantines the rule. Both are available through `repository_settings_set`, `repository_attachments_set` and `repository_rules_get` (which adds `suppressionsSource`, `configSource` and `configError`), and the dashboard rule and pack panels can switch suppression comments. Existing databases gain `rule_settings.suppressions` and `config_json` through the migration step `rule-settings-suppressions-config` (a rebuild of the table). Older versions still open the file, by choice, so agent hosts on different installed versions keep sharing it; they read only a setting's on/off and mode: they ignore its `suppressions` and `config` (the rule runs with its default options and honours suppression comments), and when one resets that rule's or pack's on/off and mode, it deletes the row with both. Rules dumps stay version 1 and carry the new fields only when they are set.
- Each file is judged by the checkout that owns it: a declared submodule or a recorded checkout owns its own files (and runs nothing while stopped or not set up), and only a nested `.git` Rerail never recorded is judged with the checkout around it. Conversation rules come from the session's starting folder.
- `rerail rules export` / `rerail rules import` move the library and each repository's configuration by hand; `rerail reset` deletes the current repository's history and keeps rules; `rerail seed` writes mock data. See `docs/rule-scoping.md`.
- Rules come only from the repository's configuration (rule packs, By Rerail rules and your library). `.<harness>/conversation-rules.json` files and host-supplied `rules`/`ruleFiles` options are no longer read, and `rerail install` no longer takes `--project`.

### Daemon, API, and UI

- `rerail daemon start`, `rerail daemon stop`, `status`, `manage`, and `session`: one background daemon that owns the resident engine, serves the rules UI, an HTTP API under `/api`, its OpenAPI 3.1 document, and a stateless MCP Streamable HTTP endpoint at `/mcp`, all generated from one operation registry.
- Audits, violations, repository audits, audit settings, and audit requests are exposed as `audits_list`, `violations_list`, `repository_audits_list`, `repository_audit_entries_list`, `audit_settings_get`/`audit_settings_update`, and `audit_requests_create`/`audit_requests_list`.
- The daemon serves every repository on the machine, and its operations name their target: a `repository`, `checkout` and `folder`. Repository operations and MCP tools: `repositories_list`, `repository_context_get`, `repository_rules_get`, `repository_settings_set`, `repository_attachments_set`, `repository_start`, `repository_stop`, `repository_link` (people only), `rerail_rules_list` and `library_rules_list`/`get`/`upsert`/`remove`. `rules_activity`, `sessions_list`, `violations_list`, `audits_list` and `repository_audits_list` take an optional `repository` and are machine-wide without it. `coding_agents_list` (`GET /api/coding-agents`) reports each coding agent Rerail works with: whether it is on this computer, whether Rerail is connected to it, and any problem; it changes nothing.
- The MCP bridge sends `x-rerail-caller-cwd`, so a coding agent's calls default to its checkout. A coding agent may change its own worktree's settings, set a repository up, and add a rule it created or its copy of a By Rerail rule; anything else answers `403 agent-not-permitted` with the dashboard URL.
- Loopback-only by default; DNS-rebinding protection through `Host` and `Origin` checks, `--allow-remote` for any other bind address, and framing protection on the served page.
- The dashboard (v8): a static UI (plain HTML, CSS, and ES modules, no toolchain, conditional GETs) with a sidebar navigator under a top bar that spans the page, so the status never moves when a rule's sheet opens. The sidebar lists Overview, one item per added rule pack with how many of its rules are on, Created by you, Add rule packs, Create a rule, History by rule and by session, and Settings. Overview (`#overview`, the default) shows the Violations steered and sessions tiles, Most violations logged and Recent sessions (with how many of each session's violations were steered), or, where nothing is added yet, Add rule packs and Create a rule. A rule pack's page (`#pack/<id>`, and `#created` for rules created by you) lists its rules with search, Filter, Sort and one switch for the whole pack; rule packs are added and removed whole from the catalog (`#packs`, and `#packs?review=1` for set-up's review of the recommended packs). Create a rule (`#create`) shows the `/rerail-create` command to type in a session. History by rule (`#history`, `?rule=<id>` for one rule) and by session (`#sessions`, `?sessionId=` for one session) replace Activity. A rule's sheet (`#rule/<id>`, the link a steer carries) hands edits to the coding agent as a copyable prompt and deletes a rule created by you from the repository, with Undo. Settings shows the theme, the status line, when Rerail was installed, where history is stored with a two-step Clear history for the repository, Follow .gitignore, each repository's rule count with an On/Off switch where it has rules, each coding agent with the command that connects or disconnects it (`rerail install --agents <id>`, `rerail install --remove --agents <id>`), and uninstall. Every change applies to the repository: the "This worktree | Repository" choice and the Rule detail width setting are gone, and dates show the year. Links from before v8 still resolve (`#rules` to Overview, `#activity` to History by rule, `#rule-packs` to the catalog), always scoped to a repository (`?repository=<key>&checkout=<path>`); without a scope it lists the repositories to pick from. The API adds what it reads: `repository_reset` (`POST /api/repository/reset`, people only) clears a repository's history across its checkouts as `rerail reset` does; `/healthz` reports `installedAt`; `repository_rules_get` adds each rule's `addedAt` and, for a rule created by you, `updatedAt`; `sessions_list` adds each session's `steeredViolations` and `lastEventAt`.
- The dashboard stays fast as history grows, and no longer holds up the daemon. Activity, violation and session-count reads come from history tables that triggers on `audits` keep current, whichever Rerail version writes the audit, instead of expanding every audit's JSON on each read; an upgrade fills them once from the audits a database already holds. On 4,000 audits one poll went from 3.7 s to under 50 ms, and a status-line request made while two dashboard tabs poll from 11 s to under 0.1 s (`just rerail-dashboard-history`). An unchanged history read is answered from the last result until the database changes. Each view loads only what it shows, and nothing is polled while the tab is hidden.
- History is paged with a cursor: `violations_list` and `sessions_list` take `limit` and `cursor` and answer `nextCursor` (`offset` is gone); `sessions_list` lists newest first with each session's `violationCount` and a `total`; `violations_list` takes `sessionId` and adds each violation's `host`; `rules_activity` adds `sessions: { started, withViolations }`; `session_events` takes `before` to page back from the newest events; `sessions_get` adds `gaps` (events never delivered and boundaries answered before checks ran, over the whole transcript). The dashboard's sessions list, History by rule and a session's violations load a page at a time with Load more, and a session opens on its newest events with one Load earlier that pages back through its events and violations together; what it says the session missed covers the whole session, however much of it is loaded.
- The dashboard keeps its address across restarts: the daemon remembers the port it last listened on (or the one `rerail daemon start --port` named) in `daemon-port.json` in the Rerail home and comes back on it, taking 4737 and then a free port only when another process holds it. Before, with 4737 taken, every restart chose a new random port and dashboard links and bookmarks broke.
- `rerail daemon stop` returns in a container without an init process: a daemon that has exited but that nothing reaps (a zombie, Linux) counts as stopped, and a process that outlives SIGKILL is reported after five seconds instead of being waited on forever.
- A `rerail daemon start` that fails shows only what that launch wrote to `daemon.log`, not lines from earlier runs.
- `rerail status` says Rerail is not installed, and to install it with `npx @neralabs/rerail setup`, on a computer it was never set up on, instead of "stopped"; outside a repository it says no repo was found there and names the folder, instead of `Rerail is stopped in .`.

### Harness integration

- OMP and Pi extensions, and Claude Code, Codex, and Cursor lifecycle hooks, all sharing one transport-neutral event runtime; command hooks reach the daemon's resident engine over an owner-only Unix socket or Windows named pipe, and the daemon autostarts when a session starts (`RERAIL_AUTOSTART=0` opts out). After an edit a hook waits up to one second for that edit's rule check, so a steer lands under the edit rather than at the end of the turn. A later hook that finds no daemon answers at once with nothing, and every hook exits 0, so a daemon that is down never stalls a tool call or shows as a hook error; a Codex session that starts without one says `Rerail ✕ not running · start it with: rerail daemon start`, since Codex has no footer.
- The daemon log (`$RERAIL_HOME/daemon.log`) times each session's initialize and code-rule evaluator open, each repository storage attach (discovery and publication), each repository audit (index and result pages, with its files, violations, failures and status), and any turn end that waited more than a second, and on what; Rerail running inside a host process (Pi) writes none of these lines.
- Rerail is off in every repository until it is started there. `/rerail-start` and `/rerail-stop` (OMP, Pi, Claude Code, Cursor) or `rerail start` / `rerail stop` (terminal and Codex) turn it on or off in the current checkout and the checkouts inside it, or with `--repository` in every checkout of the repository. Set-up and rules belong to the repository; on and off belong to each checkout. Starting a repository that is not set up runs set-up's questions there first: it asks before reading the repository, recommends rule packs, and starts once you confirm ("Skip, I’ll pick packs" lists every rule pack to pick from, or none). `rerail state` prints `started`, `stopped` or `not-set-up`.
- `/rerail-start` in OMP and Pi asks set-up's questions through the coding agent's own picker, driven by `rerail start --json`: each question's text shows as a notice, then the question as a select (a text box for a folder or coding agent ids), until set-up is done, stopped or fails. In a repository that is set up it just starts Rerail and says so. Closing a picker stops set-up and turns nothing on. Claude Code and Cursor relay the questions as text.
- Session ledgers stay out of Git. `<repository>/.rerail/sessions/` holds a `.gitignore` of `*`, written whenever a session opens and it is missing, never overwritten, so a session's prompts and file preimages never show in `git status` or get committed by `git add -A`. The repository's own `.gitignore` is not touched, and neither is a custom storage root outside a `.rerail` folder (`RERAIL_STORAGE_ROOT`).
- Per-session event lanes, tool-call correlation by native call ID, preimages and pending calls that survive daemon restarts, and shell-write discovery at turn checkpoints.
- Sessions keep their events under load. The OMP and Pi attach answers as soon as the session is recorded, and its code-rule evaluator opens behind it (indexing the repository). A tool call, result or turn end reached while it is still opening does not wait for it: it answers at once without code rules, the session's history records a `code-rules-pending` event (shown on the dashboard timeline), and the edit is not checked later at its result either; the evaluator's first walk still checks a file changed while it ran, as it does any change it did not see made. An evaluator that cannot open is recorded as a failed audit while the session goes on without code rules. Closing or re-initializing a session never waits for an evaluator still opening; that evaluator closes itself once it opens, without touching the audits of a session reopened under the same id. A turn end waits only for its own edits, never the session-start repository audit. A turn end or command result waits at most 10 seconds for the checkout-wide shell-write walk; what the walk finds later reaches a later boundary, and the session's history records a `source-discovery-pending` event for each boundary that answered without it, shown on the dashboard timeline.
- Events the OMP or Pi extension cannot hand to the daemon are recorded, never lost silently: a `rerail.events-dropped` session entry with the count, the event kinds and the first and last event id, which gets the final count when the gap ends or the session closes or is left (in that session, never the one the host switched to); an `events-dropped` session event on the dashboard timeline (the daemon's `record-gap` operation), retried with backoff (1 to 60 seconds) and tried once more as the session closes, while a gap the daemon refuses outright is dropped from the queue so later gaps still record; and a footer line, `Rerail: N session event(s) dropped — daemon not answering`, while it lasts (none when the presentation is `silent`). In OMP, events that arrive while an attach is failing and retrying, that were waiting on the attach that failed, or that waited on a daemon restart or reload that failed, are counted too; and an assistant message whose streamed parts were dropped still reaches the daemon whole at its end.
- A busy daemon is no longer taken for a lost one, and the agent no longer stalls on its audits. In OMP and Pi, a tool result or turn end waits at most 10 seconds for the audits of the session's edits; audits still running then (a shell command that wrote thousands of sources) carry on, and while they drain no later boundary waits for them again. The extension's request asks for a deferred reply: the daemon answers within 10 seconds, with the reply or a ticket for an operation it is still running, and the extension asks again with the ticket (`await-reply`), so the events behind it wait in order and their replies, steers included, are delivered. An operation still running after 2 minutes (a poll after 30 seconds), or a request the daemon does not answer within 30 seconds, starts an outage and drops events as before, so a stuck daemon never queues events without end.
- Experimental, off by default (`RERAIL_EXPERIMENTAL_MISSED_STEER_DIGEST=1` in the environment of the daemon, of Pi when it runs Rerail in process, and of Cursor's hook for its follow-up; its behaviour may change or go away): a missed-steer digest. A code-rule steer whose check finishes after its step has moved on (past 1 second for Claude Code, Codex and Cursor, past 10 seconds for OMP and Pi) is no longer handed to some unrelated later step: its findings are held and reach the agent once, when it finishes its run, as one steer led by `Rerail finished checking your earlier edits after you moved on:` that lists every finding once; a file edited again meanwhile drops out of it. OMP sends it from the `session_stop` hold (the daemon's `yield` operation, which otherwise returns the steers still pending) and Pi from `agent_before_settle`, and both continue the run with it; Codex carries it in its `Stop` block; Cursor's `stop` answers with a `followup_message` (while `loop_count` is under 3); Claude Code shows one line per rule at `Stop` and gives the agent the block with the next message. The digest has no size limit yet.
- Per-repository setting **Follow .gitignore**, on by default, in the dashboard's Settings (`PUT /api/repository/follow-gitignore`, `repository_follow_gitignore_set`; `followGitignore` in the repository summary). Files Git ignores (`.gitignore` files at any depth, `.git/info/exclude`, the global excludes file) are not audited: shell writes there are not picked up, direct edits to them are not checked, and repository audits and the repository index skip them; tracked files are always audited, and a checkout outside Git is unaffected. It applies to sessions started after the change.
- OMP says when the daemon is still indexing the repository: the footer appends ` · indexing` (when that takes over half a second) until the session's code rules are open, and nothing waits for it. The daemon's `await-code-rules` operation answers once the session's code rules are open.
- The persistent `RERAIL-EVENTS/1` stream (`rerail events`) for out-of-process harnesses.
- One command set for every coding agent: `/rerail` (what Rerail is doing here, then every command), `/rerail-manage` (open the dashboard), `/rerail-create`, `/rerail-stop`, `/rerail-start`, `/rerail-update`, `/rerail-uninstall` and `/rerail-help` (the same as `/rerail`). Claude Code and Cursor get command files, Codex gets `$rerail-*` skills, and OMP and Pi register them natively; `/cosine-rules` and the `conversation_rules` tool remain in OMP and Pi. Settings, scans, status, update checks, rollback and reset are CLI commands (`rerail settings`, `scan`, `status`, `update check`, `update rollback`, `reset`). In Claude Code, `/rerail-uninstall` never runs the removal without Claude Code's own confirmation.
- `/rerail-ui` is now `/rerail-manage` and `rerail ui` is `rerail manage`; `/rerail-rage-quit` is now `/rerail-uninstall`. Registration removes the `rerail-ui` and `rerail-rage-quit` command files and Codex skills an earlier build wrote, when they are Rerail's own, and `rerail update` runs it for every coding agent already connected.
- `/rerail-create` creates a rule in your own words. The coding agent drafts it, tests it with `rerail rules test <draft.json> [--json]` (it validates the rule, runs its caught and passed cases and counts matches across the repo, without storing anything), reads it back, and adds it with `rerail rules add <draft.json>` only after you confirm. `rules add` stores the rule in your library and adds it, on, to this repository (at the whole repository, or the draft's `folder`), setting a repository that is not set up up with just that rule; it refuses to replace a rule by Rerail.
- `/rerail-create` without words suggests rules, and with a complaint about a rule tunes it. The coding agent follows the `rerail-create` skill the package ships (`skills/rerail-create/`), which gathers evidence with the new `rerail rules evidence [--repo <dir>] [--days <n>] [--limit <n>] [--json]`. That command reads the Rerail database without writing it, over every coding agent's sessions in every checkout of the repository: the person's correction prompts with the agent's calls just before each, risky commands (force pushes, skipped hooks, hard resets, recursive deletes, publishes), how often each rule steered, and the files where the repository writes its standards. The skill ranks candidates by the rule-witness study's findings (the repository's own conventions pay, while generic rules that fight it lose quality and cost more), keeps at most five, and checks every draft against harmful-steering gates before the read-back. Its example drafts are run through the engine by the test suite. The skill writes descriptions and messages to the same criteria as the shipped packs: a description is one imperative sentence of at most 200 characters saying what the rule wants, and a message is advice of at most 200 characters saying what to change in the flagged code and when to leave it. [docs/writing-rules.md](docs/writing-rules.md) is the guide.
- `/rerail-show-me` shows Rerail working on your own repo in under a minute. `rerail show-me` adds a demo rule, `local:rerail-show-me`, that checks one file, `rerail-show-me.js`; the coding agent writes that file breaking the rule on purpose, is steered, and fixes it; `rerail show-me --cleanup` then deletes the file and takes the rule out of this repository (out of your library once no repository has it), and the next run in the same checkout clears a demo file an interrupted one left. It runs only where Rerail is on and the repository set up, and never touches a file or rule of that name it did not write, a symlink included. Set-up's summary and tips suggest it.
- A steer is one line and a link for you, and a block for the coding agent. The block, one per delivery, is written for the agent alone and carries none of Rerail's own vocabulary: a lead that says what Rerail did (`Rerail found 2 problems in your last edit:`; `Rerail re-checked; still open:`; `Rerail finished checking your earlier edits after you moved on:`; `Rerail checked the repository and found 1 problem:`; `Rerail has guidance for this Bash call:`), then one line per finding in the order found, `- <path>:<line>:<col> — <message> [<rule id>]`, with any suggested fix under it (a deletion, a one-line replacement as inline code, or a longer one in a `~~~` fence), then the latitude: `Fix it, or tell the user in one line why you won't.` (`Fix these`; `Follow it` for a tool call's guidance). Block-mode rules steer until blocking ships. Your line is built from the rules the delivery carries (`rules`: each rule's id, state and where it comes from, kept wherever a steer is held), never read out of the block, and a tool-call or conversation rule's steer now names its rule too. You see one line per rule, `◆ Rerail · <rule>  steered  ·  why?`, with Rerail drawn as the footer's coloured `R E R A I L` where the coding agent draws colour (Claude Code, OMP): Claude Code puts the link on `why?` in a terminal known to draw links, Orca included even inside tmux (else prints it after the word), and a steer found as a turn ends shows its line then and reaches the coding agent with your next message, led as a late steer; Codex prints the link after the word, and holds a turn open at `Stop` with the block; Cursor asks the coding agent to begin its reply with the line, the link in markdown; OMP draws the line from the message's rules, with where each rule comes from and the block on Ctrl+O, and holds the end of a run until that turn's check has answered, so its steer continues the run. Pi shows the block in its default card. In OMP and Pi a tool call never waits on Rerail longer than 25 seconds, and a failure inside Rerail never blocks it.
- In a started repo the coding agent is told at session start that Rerail is there, how many rules are on, what a steer looks like (a message starting `Rerail found` that lists each problem with its location, what to do, and the rule id in brackets), that a steer is advice it may decline in one line, to answer "why?" from the steer's rule id and what it matched (you open the rule from your line's why? link), to ask you before turning a rule off or changing its mode, never to turn a rule off or stop Rerail to get past one, and the session's dashboard link; in a started repo that is not set up it is told that no rules are checked and that you can set it up with `/rerail-start`.
- In-session presence: an OMP, Pi and Claude Code status line that reads `R E R A I L ● 26 rules`, the letters each in their own colour (24-bit, else 256 colours, none under `NO_COLOR`), adds ` · steered 3×` once Rerail has steered (one per rule line you saw, so two rules in one edit count 2), and says `R E R A I L ○ not on here` where Rerail is stopped, `R E R A I L ○ not set up · rerail start` in a started repository that is not set up, and `R E R A I L ✕ not running` when no daemon answers. The rule count links the dashboard's Overview scoped to this repository and checkout.

### Installation and distribution

- `npx @neralabs/rerail setup` is first-run set-up, the same in a terminal and from a coding agent: check Node 24+; install a managed version under `~/.rerail/versions` and the `rerail` launcher, turning nothing on; ask before reading the repository; recommend rule packs with the reason for each; confirm in three numbered steps (may Rerail see sessions, scan this repo or another, then start, change the rule packs, or not now); start in this repository only (every checkout of it not stopped on its own); and a summary that ends on the dashboard link (opened unless `BROWSER=none`, over SSH, or on Linux without a display). Set-up no longer offers the dashboard's review, so `--answer review` and `--answer other` are removed (name coding agents with `--agents`, which works with any answer); "Not now" is `--answer not-now` and installs nothing. A repository an earlier set-up's review set up counts as set up: `rerail start` starts it with the packs kept on there, asking nothing. Outside a repository set-up asks which project (type the folder, or skip for now), and that question counts as the scan step, so the count never changes mid-run; a relayed `--answer pick-myself` there asks it again rather than skipping. Every ending uses the same summary layout: "Skip, I’ll pick packs" then "None for now" ends on the started summary with no rule packs on, and "Skip for now" on "Rerail is installed · not on in any repo yet" with how to start it in a session. "Skip, I’ll pick packs" lists the packs once in a terminal, numbered after "Choose rule packs…"; a `--json` step's `screen` keeps the blank line between what leads up to the question and what follows it. In a terminal each question is a menu: ↑/↓ (or k/j) move the cursor, wrapping around, a digit moves it to that answer, and Enter takes it; Ctrl-C puts the terminal back and stops set-up, Ctrl-D cancels it. Where answers are typed as lines, a line that names no answer gets "Type a number from 1 to N." before the question is asked again. Without a terminal on stdin and stdout, or with `--relay`, it prints each question with one command per answer (`--answer`, `--repo`, `--agents`); `/rerail-start` and every answer pass `--relay`, so a coding agent that runs commands in a terminal never gets a prompt waiting on input. `--json` prints one `SetupStep` object per run for coding agents that ask through their own UI. Registrations are idempotent, and a configuration file they change is backed up first; command files and skills Rerail generated are replaced without a `.bak` copy. `rerail install --agents <list>` connects coding agents on its own, and `rerail install --remove` takes the registrations out again, stops the daemon, and moves `rerail.sqlite` into a dated backup; removing Rerail from a Cursor it never registered with no longer writes `~/.cursor/hooks.json`.
- Set-up checks the computer before it installs anything, and stops with what to do instead of failing the install: on Alpine and other musl Linux, on a glibc older than the Linux engines need (2.28), or on a system or processor with no engine, it names what Rerail runs on; without Git it says Rerail needs Git, lists where it looked, and gives this system's install command. An older Node's message names the upgrade that fits how Node was installed (`brew upgrade node`, `nvm install 24`, `fnm`, `volta`), else nodejs.org. Inside WSL, for a repo on the Windows drive (`/mnt/c/…`), it notes that Rerail and the coding agent belong on the same side and that such repos are slow. An install that fails anyway removes the empty `~/.rerail` folders it made.
- Rerail also finds Git where one user installed it: Git for Windows under `%LOCALAPPDATA%\Programs\Git`, scoop's, Linuxbrew's and a Nix profile's. It still never runs a `git` from `PATH`.
- Set-up puts the launcher's directory (`~/.rerail/bin`) on `PATH` itself, so `rerail` runs from a new terminal: a marked block in the startup file `$SHELL` reads (`.zshrc`, `.bashrc` plus bash's login file, fish's `conf.d/rerail.fish`, otherwise `.profile`), or the user `Path` on Windows. It writes nothing when `PATH` has the directory already or `RERAIL_MODIFY_PATH=0`, re-running changes nothing, and the full uninstall (`rerail install --remove`) takes the entry out again. An install whose set-up predates this step (0.1.0-next.2 or earlier) gets the entry from its next `rerail update`: the `rerail install --refresh` it ends with puts the launcher's directory on `PATH` where it is missing, and says so, once: set-up records in the Rerail home (`launcher-path.json`) that it handled `PATH`, and from then on `PATH` is yours, so a block you take out stays out of later updates (`rerail setup` run again adds it back). Where `SHELL` is unset, as inside a coding agent's host it may be, the startup file is the account's login shell's rather than `.profile`, which zsh never reads.
- A shell startup file the `PATH` step changes keeps one backup, `<file>.rerail.bak`, which each change replaces and `rerail install --remove` deletes, instead of a new `<file>.<timestamp>.bak` every time. On Windows set-up also writes `~/.rerail/bin/rerail`, an sh launcher Git Bash runs as `rerail` (it never runs `rerail.cmd` by that name); `rerail.cmd` spells a non-ASCII path, such as a profile folder named José, through `%~dp0` or `%LOCALAPPDATA%`, `%APPDATA%` and `%USERPROFILE%`, since cmd.exe reads it in the console's code page, not UTF-8; and coding agents are connected in the profile folder (`USERPROFILE`) they read, even where `HOME` names another folder, as Git Bash's may.
- On Windows, Codex's hooks run from a profile folder whose name has a space, such as `C:\Users\José García`. Codex hands a hook's command to PowerShell, which split the earlier `cmd /d /c "if exist …"` command at the space; the hook is now a PowerShell command, `if (Test-Path -LiteralPath '<node>') { & '<node>' '<hook>' } else { node '<hook>' }`, its paths in single quotes, that still falls back to `node` on `PATH` and exits with the hook's own exit code. Registering replaces the earlier command, so Codex asks to trust the hook once more with `/hooks`.
- `rerail version` (also `--version` and `-v`) prints the installed version, with no daemon to ask, and `/rerail` ends by naming the terminal commands: `rerail status`, `rerail version`, `rerail update`, `rerail daemon stop`.
- Rerail keeps working through a Node upgrade: set-up records Homebrew's Node by the link `brew upgrade` keeps (`/opt/homebrew/bin/node`) rather than its versioned `Cellar` folder, the Claude Code status line falls back to `node` on `PATH` like the hooks once the recorded Node is gone (on macOS and Linux), and `rerail install --refresh` (which `rerail update` ends with) records the Node it runs on in the launcher too. When that fallback lands on a Node older than 24, the CLI and the daemon stop with set-up's message, the hooks do nothing and say so in one line on stderr, and the status line shows `needs Node 24 or newer`.
- Set-up opens with the `R E R A I L` mark in a terminal, and asks once per computer, before it reads a repository or connects a coding agent, whether Rerail may read your coding agent sessions to check them and show their events in the dashboard. Yes is kept in `~/.rerail/consent.json`; no stops set-up with nothing new connected or started, and takes back an earlier yes. Set-up has installed Rerail and put `rerail` on `PATH` before it asks, so after no it says Rerail stays installed and off, and that `rerail install --remove` takes it off the computer. `--json` reports the question as the `sessions` step, with the answers `allow` and `decline`.
- Set-up connects each coding agent on its own: one whose config is not plain JSON (a comment, a trailing comma) is left untouched and named in the summary with the file, the reason and what to do, while the others are connected and the repository starts. Run again in a repository that is set up, set-up connects the coding agents installed since, never one left out with `--agents` or removed with `rerail install --remove --agents <id>` (recorded in `~/.rerail/coding-agents.json`). The summary writes Rerail's commands as `$rerail-show-me` when Codex is the only coding agent connected (with Codex's form beside the others' when it is one of several), says to trust Codex's hooks once with `/hooks`, and, with no coding agent found, says so and how to connect one. `rerail install --remove` also removes the `~/.codex/skills/rerail*` folders it emptied (and `~/.codex/skills` when nothing else was in it) and an empty `~/.omp/agent/extensions`.
- The full uninstall, `rerail install --remove` (and `/rerail-uninstall`), deletes the installation once the coding agents are disconnected, the daemon has stopped and the database is in the backup: `~/.rerail/current`, the launcher's `~/.rerail/bin`, every version under `~/.rerail/versions` with `update-state.json`, the rule packs in `~/.rerail/packs`, and the cache `~/.cache/rerail` (kept, and said so, while another Rerail home's daemon holds it). It names each path it removed, what it kept in the Rerail home, and the backup; a file it cannot remove (one Windows keeps locked) is named with the command that finishes the job. The Windows launcher `rerail.cmd` ends its batch before it runs node, keeping node's exit code, so removing it from under the running command does not end with "The batch file cannot be found."
- Explicit updates only: `rerail update` resolves an npm dist-tag (`latest`, `beta`, `next`), validates the native engine and a real event-stream round-trip before activating, copies the database to `rerail.sqlite.pre-update` first, and keeps the previous version for `rerail update rollback`. The check passes both ways between this release and 0.1.0-next.0, from before set-up. Rolling back starts 0.1.0-next.0 without `--answer`, which it does not take. Updating from it works because its check's own start (`rerail start --repo` with no terminal, at an empty folder outside Git, under `RERAIL_AUTOSTART=0` with its own `RERAIL_HOME` and `RERAIL_STORAGE_ROOT`) starts Rerail there without setting it up; every other start runs set-up.
- `rerail update` (and `/rerail-update`) installs the commands and skills a new version adds, such as `/rerail-show-me`: newer version or not, the active version runs `rerail install --refresh`, which registers it again with every coding agent already connected, writing its commands, skills and hooks and removing the ones it retired. A coding agent never connected is left alone, and so is one whose configuration cannot be read to tell, named with the reason. A connected one that cannot be registered again is named while the others are refreshed, and the update exits 1 with the new version active. The Codex note to trust the hook appears only when Codex's hooks changed. Updating from 0.1.0-next.2 or earlier runs that version's update, which does not refresh: run `rerail install --refresh` once afterwards.
- When npm cannot reach the registry, set-up and `rerail update` stop in seconds and name it: `could not reach the npm registry (<url>, ECONNREFUSED): check your network, proxy, or registry in ~/.npmrc`. Installing a version first says what it downloads, then asks the registry once with an empty cache: npm otherwise answers a registry that is down from its stale cache only after waiting out its retries on every package in turn, which left set-up silent for 15 minutes and more. Every npm call Rerail makes retries once after 2 s, not after npm's 10 s and 60 s. A failed install leaves no staging folder or update lock behind.
- When npm gives set-up none of the rule packs (no network, no access), set-up says it could not download them, with why, and offers to try again or stop, instead of saying that none fit and offering to start with none.
- Output piped to a reader that closes early (`rerail setup | head -2`) no longer ends in an `EPIPE` stack trace: the command finishes what it started without the lines no one reads.
- Signed customer activation profiles (`rerail activate`, online or offline) with device keys in macOS Keychain, Linux Secret Service, or Windows Credential Manager.
- Prebuilt native engines for macOS, Linux glibc, and Windows MSVC on arm64 and x64; the Linux engines are built against glibc 2.17 and stripped, so they load on every distribution Node 24 runs on (Debian 12, Ubuntu 22.04, RHEL 9 and Amazon Linux 2023 included), and the Windows engines link the C runtime statically.
- The package's built entry points mirror the source layers: `rerail` runs `dist/cli/cli.js`, the hooks `dist/hosts/<harness>/<harness>-hook.js`, the OMP and Pi extensions `dist/hosts/{omp,pi}/`, and `@neralabs/rerail/schemas` exports the rule-document schemas without the Node runtime.
- `@neralabs/rerail/rules` validates a code rule exactly as Rerail's own writes do, for servers and tools that store rules: `validateCodeRule(input)` returns `{ ok: true, rule }`, `{ ok: true, rule, inactive }` for a language not supported yet, or `{ ok: false, code: "invalid-rule", reason, issues? }`, and throws `EngineUnavailableError` only when the native engine cannot load. It loads the schema and the native engine, not the daemon. The native binding's `pythonModulePath(absolute)` is now `modulePath(label, absolute)`, which answers for every dialect.
