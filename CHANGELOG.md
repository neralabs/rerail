# Changelog

## Unreleased

- One database again: `$RERAIL_HOME/rerail.sqlite` holds the rule catalog and every repository's sessions, events, work links, and policy runs; sessions carry their repository identity and the daemon's listings cover the repository it was started in. The first open copies an existing `~/.rerail/rules.sqlite` into it (the old file is left in place, unread); checkout `.rerail/transcripts.sqlite` files are left untouched and their history is not imported. Rule scoping is unchanged. `--database` is gone from `rerail start`, `seed`, `reset`, `rules`, `scan`, and `settings`, and `RERAIL_TRANSCRIPT_DATABASE_PATH` is no longer read. `rerail reset` now deletes only the current repository's history and never touches rules; `rerail update` copies the database to `rerail.sqlite.pre-update` instead of exporting rules. Schema revision 13 adds `sessions.repository_id`; the compatibility floor stays v10.
- Link the MSVC C runtime statically into the Windows kernels. 0.1.1 `rerail setup` failed on a clean Windows install with `The specified module could not be found` for `native\omp_cosine_rules.win32-*-msvc.node`, because the kernel imported `VCRUNTIME140.dll`; release runners ship that runtime, so CI never saw it. The release workflow now rejects a Windows kernel that imports the Visual C++ redistributable.
- Register Claude Code hooks on Windows in exec form, which Claude Code spawns without a shell; requires Claude Code 2.1.139 or newer. Claude Code runs shell-form hooks through Git Bash, which rewrote the old `cmd /d /c` wrapper's switches into drive paths: cmd started interactively, read each event's JSON from stdin as commands, and the hook never ran. The entry runs `node` from `PATH` on `dist/hook-launcher.js`, which hands the hook to the `node.exe` recorded at setup while it exists and runs it under the `PATH` node once a version-manager upgrade removes that binary, the same order the shell launchers use. `rerail setup` and `rerail install` replace the old entries.
- Start the daemon on Windows through the native kernel with an explicit inherited-handle list (NUL stdin and `daemon.log`). Node's spawn passed every inheritable handle in the launching process to the daemon, including an output pipe a Rust launcher such as `just` left inheritable, so `just rerail` with captured output (CI, `| tee`, an agent's shell tool) did not finish until `rerail stop`.
- Check a staged install's native kernel in a child process. Loading it into the installing process kept the kernel mapped, and on Windows x64 renaming the staging directory into place then failed with `EPERM`, so `rerail setup` and `rerail update` could not install there.
- `just rerail` runs on stock Windows: the Landing `Justfile` sets `windows-shell` to `cmd.exe`, so recipes no longer need `sh`, which Git for Windows leaves off `PATH` (`could not find the shell sh`).

## 0.1.1

- Keep globally installed Rerail inert beneath repository-operations workspaces with `NERA_RERAIL_ENABLED=false`, including ad hoc nested worktrees; explicit workspace opt-out no longer falls through to the shared host daemon.
- Repository-scope scans of a Git checkout run the native repository index on the scan workspace, one bounded chunk per call (at most 32 files or about 1 MiB of source resident, released after each chunk's publication; interactive edits go first between chunks, and listing and restoring the checkout never hold the evaluation slot they wait on), restore completed clean directories from the store and record them for reuse; JavaScript no longer reads the corpus. Such scans evaluate exactly the files the JavaScript walk selects (the host's ignored directories, source languages and policy scopes): `.gitignore`, `.rerailignore` and Rerail's built-in ignores such as `tmp/` decide only which clean files are restored, so tracked files under `tmp/`, gitignored files and workspace roots inside ignored directories are scanned too. A file is restored only when Git status compared it with the worktree: assume-unchanged and skip-worktree entries are read on every scan, and the ignore rules fold case as `core.ignoreCase` does, so an edit under `Tmp/` is never answered from the committed blob's results. Recording the reuse cache runs off the JavaScript thread and is best effort: a busy or failing store write is logged and the scan keeps its results. Scans report paths relative to the workspace root even when it is a subdirectory of the worktree; outside Git, and in a checkout Git cannot describe (one holding an unreadable untracked directory, say), the JavaScript walk remains: it reports what it cannot read, and interactive edits evaluate without reuse instead of failing. A workspace root reached through a symlink is scanned as its target, with or without Git. Host-supplied files whose bytes equal their committed blob are stored under the Git alias and promoted into the snapshot again. `applyPathsAsync`, `retireStorage` and the synchronous `completeStorageRevision` are removed from the native workspace (`completeStorageRevisionAsync` replaces the last).
- Repository reuse is no longer lost silently or wholesale. When Git cannot describe a checkout, Rerail logs the cause once (`rerail: repository reuse is disabled: …`) unless the root is simply outside Git. A nested repository Git cannot describe, such as an untracked `git init` without commits, is read as untracked content instead of disabling reuse for the whole checkout. A commit that lands while discovery runs leaves the files it changed unrestored. A workspace's store lease starts when the workspace registers, so a slow snapshot publication can no longer register an already-expired lease that another process's collection would retire.
- Match tool calls structurally, not only by cosine similarity (NER-1644). A cosine-kind rule's `match` may now be a condition in the policy DSL's vocabulary — `{ "field", "regex" | "eq" | "contains" }` combined with `all`/`any`/`not` — over `text`, `tool.name`, `input` (the arguments as stable JSON), or one string argument such as `input.command`. `tool:*` selects every tool. Structural rules take no `reference`, never tokenize or embed (32 corpus rules match in ~5 µs against ~80 µs for one cosine rule), see only tool calls when they read tool fields (tool results carry no `input`), and use the Rust regex dialect and `maxRegexPatternBytes` limit, validated by the kernel when a rule is written. Existing cosine rules are unchanged. Schema v11 rebuilds the checkout `rules` table so a structural row may omit its reference.
- Install from the private Azure Artifacts feed through the guided `just rerail`: it signs you in with the Azure CLI, mints a personal read-only token into `~/.npmrc`, and runs setup. Re-running it refreshes expired credentials.
- Stop publishing to GitHub Packages; Azure Artifacts is the registry of record.
- npm 401 failures from `rerail update` and other npm-backed commands say the registry credentials are missing or expired and tell you to re-run `just rerail`. Redact `_password` values from npm error output alongside `_authToken`.
- `rerail setup` starts the daemon from the resolved install root. 0.1.0 failed on clean installs with `better-sqlite3 is not installed below ~/.rerail/current`.
- Stamp the Claude, Codex, and Cursor plugin manifest versions from `package.json` at pack time; releases bump `package.json` only.
- The native content store moves to `~/.cache/nera/rerail/content-v3.sqlite` (override: `RERAIL_CONTENT_STORE_PATH`). Its compatibility floor rose, so older Rerail builds keep their own `content-v2.sqlite`, which is left in place; the first workspace attach after upgrading starts from an empty cache. Rerail never deletes the previous store and does not count it against the store's capacity limits: once no Rerail 0.1.0 or older binary runs on the machine (every install and harness session upgraded), delete `~/.cache/nera/rerail/content-v2.sqlite`, `content-v2.sqlite-wal` and `content-v2.sqlite-shm` to reclaim up to 10 GiB; it is only a cache. Snapshot publication no longer fails when a concurrent collection deletes a just-written root, and records the snapshot and registers its workspace in one transaction, so a collection can no longer delete the snapshot before the workspace attaches. A Git tree with duplicate entry names (`git fsck` duplicateEntries) is complete once stored, instead of failing the attach when it is the root and being rewritten on every publication otherwise. Publication repairs Git trees whose entries another writer partly deleted, and one collection pass deletes at most 512 Git tree entries unless a single tree is larger.
- Keep development builds out of the managed installation's content store. Only the managed install (`~/.rerail/versions/<version>`, usually loaded through `~/.rerail/current`) opens the machine-wide `~/.cache/nera/rerail/content-v3.sqlite`; a build running from a Git checkout (source, `dist/`, tests, benchmarks, every worktree, `just rerail-dev`) uses `<checkout>/.rerail/content-v3.sqlite` (gitignored), so a checkout can no longer migrate or fill the store the installed version reads. The build is classified by where the running package lives; a package that is neither has no store and its first scan fails saying so. Both stores take the native binary's store file name, which follows the store's compatibility floor. `RERAIL_CONTENT_STORE_PATH` still overrides the location, but only on the host side: the native `PolicyDslWorkspace.enableStorageAsync(root, storePath)` now requires the store path, refuses an empty one, and no longer reads `HOME` or the environment.
- Run at most one main Rerail instance per machine. The managed daemon holds an OS advisory lock (`flock` / `LockFileEx`, released by the OS however the process ends, and unlocked explicitly on shutdown) on `~/.cache/nera/rerail/main-instance.lock` and records its pid, version, package root and start time in `main-instance.json` beside it; a second main daemon exits at startup with `Another main Rerail instance is running: pid …, version …`, and no other process may open the machine-wide content store. In the managed installation `rerail events` and Pi sessions now send their events to the daemon (started on demand, like the hooks and OMP) instead of evaluating in-process; checkout builds keep their in-process runtime and never take the lock.
- Every policy evaluation response and the first page of a paged result carry a `coverage` list beside `findings` and `failures`: one entry per evaluated check (`checkId`, `policyId`, `status` and `reasons`). `status` is `complete` without failures, `partial` when every failure is `source-partial` or `source-incomplete`, and `failed` otherwise; each reason gives a failure code, its count and at most three example paths. A failure that names no check (the `runtime` budget) counts against every check of its policy.
- Policy option numbers must be exactly representable as JavaScript numbers. An integer outside JavaScript's safe range (beyond ±2^53−1, which JSON parsing may silently round) or a non-finite number is rejected in option declarations, enums, defaults and configured values, by both the native resolver and the TypeScript options check, instead of selecting a different value than the one written.
