Every request to the daemon for your data, its API, `/mcp`, `/healthz` and `/openapi.json` included, now needs its access capability in the `x-rerail-access` header and answers `401 access-required` without it; `Host` and `Origin` are what a client claims, and loopback is no boundary against another user of the machine or a sandboxed process allowed localhost. Only the page's own static files load without it. Rerail's own processes read the capability from `daemon.json`. On loopback it is kept in `access-token` in the Rerail home across restarts; a daemon started with `--allow-remote` or `--public-host` mints a fresh one on every start. A browser gets it from the dashboard link (`rerail manage` prints and opens it at a terminal, `rerail daemon start` prints it, set-up and `/rerail-manage` attach it), keeps it in that origin's storage rather than a cookie, which every server on `localhost` would receive, and takes it out of the address at once; a browser without it is told to run `rerail manage`. A piped `rerail daemon start` or `rerail manage` prints no capability. When the daemon refuses the capability `daemon.json` records, `rerail status`, `rerail daemon start` and the MCP bridge say so instead of calling the daemon unresponsive.
