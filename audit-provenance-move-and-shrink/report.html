Decision report · Rerail pull request #648

Audits: recorded audits move to the shared rule provenance after a week

1. The one question

Should recorded audits move to the shared rule provenance, when an older Rerail started again afterwards, or silent for 7 days, then reads [] for each?

  1. An older Rerail, restarted after the move or silent 7 days, reads [] for moved audits. Changes the intent.
  2. An audit without rules names a stored []: about 4 bytes more.
  3. While the move waits, the daemon reads the file hourly.

We recommend: yes, with the 7-day wait, once a maintainer answers #646's question 1 and the three places marked read first hold; main's rerail scrub gives back 1 MB of 1,438.

5. The changes

Each line opens its card.

AThe move, after a week's waitHigh riskAfter rerail scrub: 1,437 MB at main, 158 MB here once moved.
Problem
A database that grew before #530 keeps its size, and each recorded audit keeps its own copy of the rule provenance. At main rerail scrub gives nothing back while each audit keeps its copy.
Who meets it
Everyone whose database grew under 0.1.3 or 0.1.4 and who updates: once, for as long as they keep the history. How many hold such a file is not known.
What it does
moveState reads whether audits are left and whether to wait. lastOlderWrite finds the last audit of the past 7 days that names no stored copy. moveBatch moves up to 100 audits in one immediate transaction, and moveInBatches sizes each batch to hold the lock about 100 ms. whenFree tries again past another connection's lock. olderPass sleeps at most an hour.
Risk
High. It rewrites every recorded audit row on a high-risk storage path, and it decides when an older Rerail starts reading [], which its remote sink then sends. A wrong batch loses a provenance.
Check
moveBatch: the insert stores the text the digest was taken of, and the update empties the row in the same transaction. TAKEN leaves rows that hold [] and audits an older Rerail wrote after the step. lastOlderWrite counts any audit with a null id in the window, those before the step included, and postponed runs it before each batch. whenFree gives up after 34 tries, about 5 s. olderPass rethrows a timer error that is no stop.
BEvery audit names a stored copyMedium riskAn audit without rules: 410 bytes at main, 414.04 here.
Problem
The wait must tell an older Rerail's audits from this version's. At main an audit without rules has a null id whoever wrote it, so an older Rerail that records only such audits could not hold the move back.
Who meets it
Anyone who runs an older Rerail beside this version in a checkout with no rules on, or whose rule catalog could not be prepared. Found by our independent check with 0.1.4 from npm, on Linux x64.
What it does
start calls storedRuleProvenanceId for every audit, an empty provenance included, so all audits without rules name one row of audit_rule_provenances that holds []. The audit's own row still holds []. The column's comment in schema.ts now says a null id marks a row an older Rerail wrote.
Risk
Medium. One line on the path every audit takes. A wrong mark makes the wait miss an older Rerail, or count this version's own audits and never move.
Check
The lookup and the insert run inside start's immediate transaction, as for any provenance. Every reader takes the stored copy or the row's own through coalesce, so [] reads the same from either. The delete trigger drops the shared [] row with the last audit that names it. The package root exports AuditRow: a null ruleProvenanceId there no longer means an empty provenance.
CThe daemon starts and stops itMedium riskWhile the move waits, the daemon's thread reads hourly: none at main, 30.7 ms at 20,000 audits.
Problem
The move must start without holding the thread that answers hooks, stop with the daemon, and leave a trace when it fails. Main's daemon starts no work of this kind.
Who meets it
Every daemon start on a database that still holds recorded audits to move, and every hour while the move waits. Once nothing is left, a start finds that with one read and takes no write lock.
What it does
#startProvenanceMove calls moveRuleProvenancesInWorker once the daemon has announced itself, and keeps its abort controller and its promise. close aborts the move and awaits it before the remote sink and the HTTP server stop. A failure goes to daemon.log through errorStack, with the worker's stack. A stop logs nothing.
Risk
Medium. The daemon is on every hook's path. A move that held its thread, or a stop that waited on the move, would delay hooks or a restart.
Check
The call comes after #announce, so the daemon serves before it reads for the move. close awaits the move first: its writable open can wait up to 5 s inside SQLite, where a stop does not reach it. The rejection handler writes to stderr and ends there, so a failed move never fails the daemon. #657 adds code at the same three places of this file.

Six smaller gaps, five limits that stay
  • Where the numbers were measured. The move, the writes during it and the kills ran at 768027db1 and d57eee7f3. Of the five commits since 768027db1, two change code, a stop during a busy retry and the failure's log line, and three change docs and comments only.
  • Windows 11. The tests that write audits as 0.1.4 does, with rules and without, pass there. The run with 0.1.4 from npm beside the real daemon was made on Linux x64 only.
  • The move thread's writable open still waits up to 5 s inside SQLite for the write lock, so a stop cannot reach it there. Not changed; a possible follow-up.
  • Read in the code, not run: the move starts at most an hour late after the computer sleeps; rerail.sqlite.pre-update holds each audit in full until a later version change replaces it; a start time past year 275,760 makes the wait line throw, and the daemon logs that failure once.
  • One Linux run failed one test of main: among the 22 files at 2f9ea64e0, database-baseline's "leaves adopting a file stamped 1 to the writer while a step that raises the floor is pending" timed out at 5 s. That file alone passed 32 of 32.
  • The first CI attempt at 2f9ea64e0 failed on test/cli/scrub-cli.test.ts, "loses no line a process appends to daemon.log or a ledger while it scrubs them", a test of main this change does not touch. It failed the same way on #657's CI. The second attempt passed.

Limits that stay.

  • The file keeps its size until a person runs rerail scrub. Behind scrub another process's write can fail at 5 s, at main and here alike: at 2,162 MB in use on Linux x64, 1,160 MB on Windows 11.
  • With only this version running, the move starts 7 days after the last audit recorded before the update.
  • An older Rerail reads [] for each audit this version records, as at main since #530. The audits it writes itself keep their provenance in their own row, and the move leaves them there.
  • While an older Rerail keeps recording, daemon.log gets the wait line again, at most once an hour: about 390 bytes a line, up to 24 lines a day.
  • A daemon killed during the move loses at most one batch's work and no audit: 10 kills each on Linux x64 and Windows 11 lost, doubled or left dangling none, and the next start moved the rest.

9. What we ask of you

Ask 1 rules on answer 1.

  1. May recorded audits move after the 7-day wait? Answer on #646, question 1. We recommend yes: an older Rerail recording weekly loses nothing.
  2. Is 7 days the right wait? We recommend yes: it covers an older Rerail used weekly.
  3. rerail scrub alone for the space, no automatic VACUUM (#646, question 2)? We recommend yes: no other process's write fails unasked.
